# spec-audit

Нативный инструмент для проверки Markdown-требований по коду и утверждениям тестов. Требования либо объявлены в ТЗ, либо явно приняты хостом из кандидатов. Существующая AI-сессия распределяет смысловой анализ между mapper/redteam; бинарник проверяет цитаты, ведёт состояние и строит JSON/HTML. Ключи и модельные API ему не нужны.

Первый рабочий срез, не сертификатор соответствия. Он различает дефект реализации, слабый тест, неизвестность и неоднозначную норму. Зелёный запуск не превращает эти состояния в PASS. Инструмент предназначен для разных проектов; SMSPlace — текущий пилот, не источник встроенных бизнес-правил.

## Быстрый старт

Поддерживаются только `darwin/arm64` и `linux/amd64`; на других платформах установщик отказывает до скачивания. Установка без sudo и без правки профилей оболочки — в `~/.local/bin` (переопределяется `SPEC_AUDIT_INSTALL_DIR`):

```bash
install_file=$(mktemp) && curl -fsSL https://github.com/StenHigh/spec-audit/releases/latest/download/install.sh -o "$install_file" && sh "$install_file"
```

Скрипт сверяет sha256 бинарника с `release-manifest.json` того же релиза. Граница доверия первой установки — HTTPS до GitHub Releases: подпись манифеста здесь не проверяется. Дальше обновляйтесь только подписанной командой:

```bash
spec-audit version
spec-audit update
```

`update` проверяет подпись Ed25519 манифеста встроенным публичным ключом, ставит только версию выше текущей и только ассет своей платформы, заменяет файл атомарно; равная или меньшая версия — `updated:false`. Сборка `go build` остаётся `dev` и в `update` отказывает.

Skill для AI-сессии встроен в бинарник и ставится в проект отдельной явной командой (`init` по-прежнему создаёт только YAML):

```bash
spec-audit skill install --dir /absolute/path/project --host both   # codex | claude | both
spec-audit skill update  --dir /absolute/path/project --host both
```

Появятся реальный каталог `.spec-audit/skill/` с receipt `.spec-audit-skill.json` и относительные ссылки `.agents/skills/spec-audit` и/или `.claude/skills/spec-audit`. Symlink на месте skill (прежняя ручная установка) заменяет только `skill install --replace`; `skill update` в этом состоянии отказывает всегда. Без `--replace` обе команды отказывают при чужой host-ссылке или локально изменённом управляемом файле; чужой каталог без receipt и реальный путь на месте ссылки не заменяются никогда, лишние файлы не удаляются, `.gitignore` и Git не трогаются. Отказ по состоянию не пишет ничего; ошибка ввода-вывода посреди записи сообщается, а повторный `skill install` завершает копию. Что делать с этими путями в Git, решает проект. Вариант «ничего в Git» — строки `.gitignore`:

```gitignore
/.spec-audit/
/.agents/skills/spec-audit
/.claude/skills/spec-audit
```

Но в изолированных worktree-сессиях агентов (Claude Code desktop создаёт их для сессий) игнорируемые файлы отсутствуют и `/spec-audit` не распознаётся. Если сессии открываются так, трекайте skill, ссылки и конфиг, оставив результаты локальными:

```gitignore
/.spec-audit/*
!/.spec-audit/skill/
!/.spec-audit/config.yaml
!/.spec-audit/scopes/
/.spec-audit/scopes/*/*
!/.spec-audit/scopes/*/config.yaml
```

При tracked-варианте после `spec-audit skill update` изменения skill коммитятся отдельно.

Удаление вручную: `rm -rf .spec-audit/skill .agents/skills/spec-audit .claude/skills/spec-audit` в проекте и `rm ~/.local/bin/spec-audit`; команды `uninstall` нет. Контракт — [§18 спецификации](docs/tool-spec.md#18-поставка-версия-обновление-и-установка-skill).

## Состояние и следующие шаги

Новому агенту: начните с [AGENTS.md](AGENTS.md); `CLAUDE.md` ссылается на тот же файл. Переписка и локальная память не нужны для продолжения разработки.

На 2026-09-16 работают scoped-аудит, declared/accepted-индекс, независимые роли, сохранение raw, согласование хоста и автономный HTML с графиками, темами и переходами в редакторы. Через хоста доступен аудит задачи трекера и её исправления; бинарник не импортирует и не изменяет issues. HTML принят владельцем. Поставка: подписанный релиз `v0.1.0`, `install.sh`, `update` и встроенный skill с `skill install|update` (`init` по-прежнему создаёт только YAML); в пилоте symlink на checkout заменён установленной копией. Accepted-набор ограничен 64 активными требованиями; единого аудита всего корпуса нет. PHP SDK: прежний `php-facts` остаётся syntax-only; новая команда `php-typed` даёт типизированные факты PHPStan/Larastan по [контракту](docs/php-sdk-contract.md) — подсказки для ролей и HTML, не связи и не PASS.

Очередь перенесена без смены приоритетов в [ROADMAP](.ai-factory/ROADMAP.md). [PHP/Laravel SDK с PHPStan/Larastan](docs/tool-spec.md#17-php-и-laravel-sdk) реализован по п.1–3 §17.2: контракт `sdk/3`, экспортёр в проверенном контейнере через `--autoload-file`, fail-fast изоляция Laravel bootstrap, записи SDK в state и подсказки в отчёте. Порядок §17.2 п.2 изменён решением владельца 2026-09-16: пилот — среда отладки, приёмка — синтетические примеры. Сравнение п.4 на пилоте дало нейтральный результат, поэтому `php-typed` остаётся опцией по требованию хоста: включать на scope с интерфейсами, биндингами контейнера, фасадами и Eloquent-магией или когда роли без SDK возвращают `implementation: unknown`; на прямолинейном коде пользы не измерено. Далее — рабочий цикл из чистой AI-сессии через установленный launcher. Спецификация определяет нормы, roadmap — порядок работы.

[Прежний PLAN](.ai-factory/PLAN.md) сохранён как история 29 завершённых задач. Он не перезаписывается и не используется как активный план. Notes/compact остаются экспериментом; переход со старого re-audit и преобразование бизнес-ТЗ требуют отдельных критериев приёмки, отражённых в roadmap и [спецификации применения](docs/smsplace-adoption.md).

## Разработка с AI Factory

AI Factory 2.19.0 инициализирован локально: 18 штатных development-skills в `.agents/skills/` и `.claude/skills/`, стандартные помощники Claude — в `.claude/agents/`. Это самостоятельные копии, не ссылки на SMSPlace. Новую сессию открывайте в корне spec-audit и вызывайте `$aif-warmup` в Codex или `/aif-warmup` в Claude Code; повторный init после клонирования не нужен. Если Codex ещё не показывает skill, перезапустите сессию — [правила обнаружения локальных skills](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills).

Типовой цикл: warmup → требование/приёмка в спецификации → `aif-plan full` → `aif-implement` → `aif-verify`; review и commit — по запросу. Для новой работы full/ultra создают отдельную ветку `codex/`. Базовая ветка сейчас `codex/bootstrap` — фактическая default branch репозитория; при её изменении обновляется конфиг.

| Настройка | Назначение |
| --- | --- |
| [.ai-factory/config.yaml](.ai-factory/config.yaml) | Русский язык, пути контекста/планов, Git workflow разработки |
| [.ai-factory.json](.ai-factory.json) | Реестр версии и файлов установки AI Factory; обновляется его CLI |
| Audit CONFIG, переданный `spec-audit` | Источники кода/ТЗ, runtime и reports_dir конкретного аудита; другой формат |

Fast-план использует `.ai-factory/ACTIVE_PLAN.md`, полные планы — `.ai-factory/plans/`; отсутствующие планы и optional-каталоги не создаются заранее. Общие правила и архитектура доступны из [AGENTS.md](AGENTS.md). Разделы `paths.*` задают адреса артефактов, а не утверждают, что каждый уже существует.

MCP и сторонние skills не подключались. Node использовался установленным AI Factory для setup и может потребоваться его helper-командам; это не зависимость готового spec-audit. Development-skills не входят в [поставляемый audit-launcher](skills/spec-audit/SKILL.md) и не устанавливаются им в бизнес-проект.

## Сборка и проверки

Разработка: Go 1.27.0; поддерживаемые ОС — macOS/Linux. Из этого репозитория:

```bash
go test ./tool
go vet ./tool
CGO_ENABLED=0 go build -o bin/spec-audit ./tool
```

Готовому бинарнику для init/index/reconcile/prepare/tasks/submit/retry/status/review/report не нужны Go, Node, Python, PHP или доступ к модели. `test` требует runtime проверяемого проекта: Go либо PHP в проверенном Docker Compose container. PHP на хосте не запускается. Тесты инструмента используют синтетические данные; Docker-протокол дополнительно проверяется подставным процессом, без доступа к SMSPlace.

Проверка внешнего эксперимента извлечения использует тот же валидатор и учёт reviewer, не новый production CLI:

```bash
SPEC_AUDIT_EXTERNAL_CONFIG=/absolute/path/config.yaml \
SPEC_AUDIT_LEGACY_RAW=/absolute/path/extractor.raw.json \
SPEC_AUDIT_LEGACY_GOLD=/absolute/path/gold.json \
SPEC_AUDIT_LEGACY_REVIEW=/absolute/path/reviewer.raw.json \
go test ./tool -run '^TestExternalExtractionReview$' -count=1 -v
```

Без внешних входов тест пропускается. Он проверяет хэши, цитаты и полный взаимный учёт оценок; смысловую оценку даёт reviewer, а не зелёный тест. Пропуски, добавленные нормы и возражения к эталону делают этот контроль красным.

Новый test-only контроль отдельно учитывает нормы и заметки:

```bash
SPEC_AUDIT_CONTEXT_CONFIG=/absolute/path/config.yaml \
SPEC_AUDIT_LEGACY_RAW=/absolute/path/extractor.raw.json \
SPEC_AUDIT_CONTEXT_NOTES=/absolute/path/notes.raw.json \
SPEC_AUDIT_CONTEXT_GOLD=/absolute/path/gold.json \
SPEC_AUDIT_CONTEXT_REVIEW=/absolute/path/review.json \
go test ./tool -run '^TestExternalContextReview$' -count=1 -v
```

Внешние тесты typed SDK используют собственные контейнеры синтетических примеров (нужен Docker; без переменных окружения пропускаются):

```bash
docker compose -f acceptance/php-sdk/plain/compose.yml --profile install run --rm install
docker compose -f acceptance/php-sdk/plain/compose.yml up -d app
docker compose -f acceptance/php-sdk/laravel/compose.yml --profile install run --rm install
docker compose -f acceptance/php-sdk/laravel/compose.yml up -d app
SPEC_AUDIT_TYPED_PLAIN_CONFIG=$PWD/acceptance/php-sdk/plain/config.yaml \
SPEC_AUDIT_TYPED_LARAVEL_CONFIG=$PWD/acceptance/php-sdk/laravel/config.yaml \
go test ./tool -run '^TestExternalTyped' -count=1 -v
```

`SPEC_AUDIT_TYPED_RECORD=1` перезаписывает фикстуры `tool/testdata/typed-*.json`; они пинятся к текущему экспортёру, поэтому после правки `tool/sdk-typed.php` их нужно перезаписать. `composer install` выполняется только в контейнере примера; `network_mode: none` у сервиса анализа — часть контроля SA-034, не свойство инструмента.

`TestExternalContextPacket` принимает `SPEC_AUDIT_CONTEXT_TASK` — один полный Task из prepare, проверяет lossless round-trip и сообщает только размеры. Необязательные `SPEC_AUDIT_CONTEXT_CONFIG` и `SPEC_AUDIT_CONTEXT_PACKET` (простое имя файла) сохраняют compact-пакет в reports_dir, только если такого файла ещё нет. Без входа контроль пропускается; обычный Result/submit не меняется. Эти Go-драйверы нужны для эксперимента, не для запуска готового бинарника.

## Релиз

Релиз публикует [`.github/workflows/release.yml`](.github/workflows/release.yml) по тегу `vX.Y.Z` (контракт — [§18 спецификации](docs/tool-spec.md#18-поставка-версия-обновление-и-установка-skill)). Матрица — только `darwin/arm64` и `linux/amd64`: каждая платформа собирается и квалифицируется нативно на runner той же платформы (`version` → `release:true`, `index` синтетического CONFIG, `skill install`/`update`, неизменность бинарника после `update`, отказ dev-сборки); cross-build без исполнения ассетом не становится. Публикует один job в окружении `release`: считает sha256, собирает `release-manifest.json`, подписывает его Ed25519 и создаёт GitHub Release с `install.sh`, манифестом, `release-manifest.sig` и двумя бинарниками.

Однократная настройка владельцем (нужен OpenSSL 3; системный LibreSSL macOS не подписывает `-rawin` — `brew install openssl@3`):

```bash
openssl genpkey -algorithm ed25519 -out spec-audit-release.pem
openssl pkey -in spec-audit-release.pem -pubout -outform DER | tail -c 32 | xxd -p -c 64
```

- Вывод второй команды (64 hex) — repository variable `SPEC_AUDIT_RELEASE_PUBLIC_KEY`; он встраивается в бинарник при сборке через `-ldflags -X main.releasePublicKeyHex`.
- Содержимое `spec-audit-release.pem` — secret `SPEC_AUDIT_RELEASE_SIGNING_KEY` **окружения** `release` с обязательным ревьюером; build-job ключа не видит. Локальную копию ключа храните вне репозитория.

Порядок выпуска: `go test ./tool && go vet ./...` зелёные на коммите → `git tag v0.1.0 && git push origin v0.1.0` → одобрить job `release` → на хосте `spec-audit update` (или первая установка через `install.sh`) должен показать новую версию. Dev-сборка (`go build`) остаётся `version: dev`, `release: false` и отказывает в `update` без сети — обновляется только релизный бинарник с именем `spec-audit`.

## Первый запуск

```bash
./bin/spec-audit init /absolute/path/audit.yaml
# Отредактируйте пути по контракту спецификации.
./bin/spec-audit index /absolute/path/audit.yaml
./bin/spec-audit prepare /absolute/path/audit.yaml first
./bin/spec-audit tasks /absolute/path/audit.yaml first
./bin/spec-audit report /absolute/path/audit.yaml first
```

init создаёт только отсутствующий YAML, не каталоги исходников. Относительные project_root/reports_dir считаются от CONFIG. Каждый ответ роли отправляется через `submit CONFIG RUN_ID TASK_ID RESULT_PATH`; retry сохраняет предыдущую попытку. Все команды возвращают JSON, LOG_LEVEL управляет диагностикой stderr. Успешная команда `test` возвращает receipt: проверяйте его `state`, а не только exit самого CLI.

После получения обеих ролей `review CONFIG RUN_ID` возвращает основу для полного решения хоста. Сохраните DECISION по [контракту §14](docs/tool-spec.md#14-контракт-согласования-аудита), вызовите `review CONFIG RUN_ID DECISION`, затем `report`. Отчёт показывает решение рядом с неизменёнными ролями. Изменение исходников, новая попытка или receipt делают прежнее решение outdated; история остаётся. Новые raw сохраняются побайтно, старые явно обозначаются legacy_canonical.

`report` также создаёт [карту проекта](docs/tool-spec.md#15-карта-проекта-для-человека): обзор областей внимания, поиск/фильтры норм и полный список выбранных файлов. Откройте выданный `report_html` в браузере: карточка нормы ведёт к сохранённому фрагменту ТЗ/кода/assertion, а фрагмент — обратно к связанным нормам. HTML автономен, без сети, сервера и checkout; полный код в него не копируется. Без JavaScript доступны графики, все раскрывающиеся блоки и внутренние ссылки, но не настройки и фильтры.

В «Графиках по разделам ТЗ» видны поддержка кодом, наличие тестов и отдельно достаточность проверок. Weak явно подписан «Тесты есть, но проверка частичная или слабая» и имеет свой фильтр. Каждая норма учитывается один раз по основному файлу ТЗ; клик по файлу отбирает его нормы. Проценты относятся только к этому run, не к строкам кода или всему продукту. Нет текущего согласования — «не оценено», а не 0% или историческая зелёная оценка.

В «Настройках» выберите Zed, PhpStorm, Cursor или VS Code, при необходимости замените локальные каталоги кода/тестов и ТЗ. Defaults берутся из CONFIG; для ТЗ показан снимаемый префикс snapshot, поэтому `TZ/` не удваивается. Рядом с цитатами появятся ссылки на начальную строку в редакторе. Они требуют установленного обработчика URI и открывают текущую рабочую копию, которая могла измениться. Тема по умолчанию системная, доступны светлая и тёмная. Выбор хранится только в браузере; при отказе storage работает до закрытия страницы. YAML и исходники не меняются.

Dev-only проверка интерфейса использует новый синтетический fixture и уже установленный Playwright/Chromium, не реальный бизнес-отчёт:

```bash
SPEC_AUDIT_HTML_FIXTURE=/tmp/spec-audit-ui-fixture.html go test ./tool -run '^TestReportUIFixture$' -count=1
SPEC_AUDIT_PLAYWRIGHT=/absolute/path/to/playwright \
SPEC_AUDIT_CHROMIUM=/absolute/path/to/chromium \
node tool/report_ui_test.cjs /tmp/spec-audit-ui-fixture.html
```

Это необязательный dev-check, не зависимость бинарника; ничего автоматически не устанавливается. Проверяются темы, обе ветви browser storage, четыре URI-профиля, экранирование, фильтры/якоря, клавиатурный фокус, узкое окно и отсутствие внешних запросов. Реальное открытие каждого IDE и клавиатурное подтверждение нативного select требуют проверки в пользовательской среде: macOS headless в контрольном примере не обрабатывает выбор стрелками.

Карта показывает весь инвентарь **данного snapshot**, не утверждает, что весь проект проверен. «Нет текущих связей» — повод разобрать файл, не доказательство лишнего кода. Вопросы ТЗ, различия ролей, слабые assertions и фактическое исполнение разделены; текущий итог хоста не стирает предварительные оценки и историю. Автоматический поиск всех противоречий ТЗ и неописанной функциональности не заявляется.

Без AI можно индексировать, просматривать задания/отчёты и явно запускать разрешённые тесты. Для смыслового аудита используйте лаунчер в текущей сессии. CONFIG и reports_dir размещаются в явно выбранной внешней области либо в разрешённой локальной `.spec-audit/`, исключённой из Git; исходники и результаты не пересекаются. Инструмент не пишет проектные планы, не создаёт issues и не исправляет код. Workflow разработки выбирает сам проект; настройки пилота описаны отдельно.

Для обычного Markdown задайте `index_mode: accepted`: `reconcile CONFIG` покажет источники и текущую базу решений, а `reconcile CONFIG RAW DECISION` применит явное решение хоста. Затем используются те же index/prepare/tasks/report. Полный пакет ограничен 64 кандидатами; [контракт и формат решения](docs/accepted-index.md#json-решения). Сам бинарник не извлекает смысл и не выдаёт кандидатам статус нормы автоматически.

## Приёмка и ограничения

Поставка 2026-09-16: релиз [`v0.1.0`](https://github.com/StenHigh/spec-audit/releases/tag/v0.1.0) собран и квалифицирован нативно на `ubuntu-latest` (x86_64) и `macos-latest` (arm64) в `release.yml`: `version` → `release:true`, `index acceptance/config.yaml`, `skill install`/`update`, неизменность бинарника после `update` (в `v0.1.0` этот шаг вызывал `update` у файла с именем ассета и проверил только отказ по имени; со следующего релиза workflow гоняет копию `spec-audit` по подписанному пути и сверяет публичный ключ с ключом подписи), отказ dev-сборки. На хосте владельца установка одной командой из «Быстрого старта» дала `0.1.0`/`release:true`, `update` → `updated:false`, sha256 файла равен манифесту; прежняя ручная копия заменена. В пилоте `skill install --host both --replace` заменил symlink реальным каталогом с receipt, host-ссылки сохранены (`kept`), `git status` пуст, повторный `skill update` → `updated:false`, `reconcile` read-only работает. Linux исполнялся только на runner GitHub Actions — нативного Linux-хоста у владельца нет; сквозная проверка из новой AI-сессии в пилоте — следующий этап roadmap.

[Пять независимых примеров](acceptance/corpus/rules.md) и [ожидания](acceptance/expected.json) зафиксированы хэшами до новой реализации. Автоматический тест проверяет механику; отдельные свежие роли не получают gold. Отчёты реальных локальных проходов — в `.local/`.

Контроль 2026-09-15: обе роли совпали с ожидаемыми состояниями всех пяти примеров; это не статистическая оценка точности. Самоприменение нашло дефекты отчёта и PHP-запуска; исправления закреплены регрессиями, исходные выводы сохранены. Автономные команды исполнены с пустым PATH на macOS/Linux ARM64; x86_64 проверен только сборкой. SDK и PHPUnit дополнительно испытаны в отдельном read-only контейнере без сети.

Отдельный legacy-контроль: два свежих извлечения дали 12 и 11 кандидатов. Независимый reviewer, сначала составивший собственную инвентаризацию, подтвердил сохранение 14/14 контрольных обязанностей в каждом ответе, без добавленных норм. Валидатор проверил цитаты и полный учёт оценок; сырые ответы сохранены без правки в `.local/legacy-control/`. Проверены шесть синтетических случаев и реальная проза нашей спецификации. Это приёмка небольшого набора, не готовый legacy-извлекатель в CLI и не доказательство точности на других ТЗ.

Самоприменение accepted-профиля: хост принял 40 кандидатов собственной спецификации. Mapper/redteam независимо нашли ложный отказ после публикации файла; он воспроизведён на реальных правах каталога и исправлен в общей функции записи, с двумя регрессиями. Сбой Sync после публикации теперь даёт предупреждение о неподтверждённой сохранности после сбоя питания, а не ложный отказ. Новый run `self-v2` завершён обеими ролями без конкретных противоречий реализации; собственный receipt подтверждает девять прошедших тестов. Исходные ответы и stale-run сохранены в `.local/accepted-index/`.

Это не полная приёмка: в том snapshot у шести требований хотя бы одна роль оставила `unknown`, у 15 — слабые или отсутствующие assertions; часть относится к человеческим и историческим гарантиям. Согласование хоста — `.local/accepted-index/reports/host-reconciliation.json`. Первый проход случайно показал ролям часть истории принятия; это отмечено в limitations, а launcher теперь передаёт только TaskBatch без manifest/state. Повторная оценка исправления не является новым слепым экспериментом.

Следующий контроль усилил точное сохранение raw/decision, семантических полей и причин, независимые hash-векторы, stale CAS на пустом active-наборе, append до 128 пакетов и ровно 32 MiB с отказом на один байт выше. Исторический declared-run закреплён неизменёнными manifest/state в `acceptance/declared-v01`, без повторного prepare. Три намеренные мутации во временных копиях (seed, обрезка raw, лимит +1) пойманы. Это новые регрессии, не ретроспективное улучшение оценок `self-v2`: после изменения тестов его отчёт остаётся историческим.

Бизнес-пилот External Identifier Mapping выявил ошибки классификации эталона и пропуски тестов при подборе контекста. Его отрицательные результаты сохранены. Позднее сравнение на одной редакции выполнено отдельно: старый и новый подходы нашли два одинаковых статических контрпримера. Превосходство по точности, скорости или цене не доказано; продуктовые тесты не исполнялись. Принято ограниченное внешнее применение по разделам с сохранением CI/trace; подробности и обычный рабочий цикл — в [спецификации применения](docs/smsplace-adoption.md).

Новый frozen-контроль отделил нормативный raw от notes. Он тоже не прошёл смысловую приёмку: сохранены 11/12 групп норм, один запрет остался только пояснением; ещё одно возражение относится к неполному эталону notes. На одинаковом принятом наборе из 18 кандидатов четыре свежие роли приняли полный/compact Task: исходные ответы прошли submit без ремонта. Lossless quote pool уменьшил canonical Task на 30,3%; сопоставимые роли совпали по реализации 36/36, по силе assertions — 31/36. Это не замер токенов/денег и не доказательство равной точности.

Четыре роли также совпали в находке, которую хост оставил неподтверждённой после чтения соседних норм о направлениях протокола. Значит, нужен достаточный контекст самого ТЗ, а не только больше кода и голосов. Raw JSON/HTML, отрицательный review и отдельное согласование — `.local/context-control/reports/`. Эти ошибки стали основанием следующего контроля, а не были скрыты исправлением старого gold. Экспериментальные notes/compact остаются test-only; graph/cache, новые зависимости, массовый перенос и отключение trace не добавляются.

Контроль границ выпуска: четыре свежие роли на двух вариантах правильно различили клиентскую ошибку, корректную обработку ответа поставщика и полный/частичный assertion (12/12 назначенных оценок совпали с заранее закреплёнными состояниями). Независимое извлечение сохранило три обязанности, включая человеческую и неопределённый срок; reviewer подтвердил обязательное пояснение и одну корректную дополнительную note. Это небольшой положительный контроль, не ретроспективное исправление отрицательных бизнес-прогонов и не доказательство общей точности.

Сравнение §17.2 п.4 на пилоте (2026-09-16, отдельное разрешение владельца, один accepted-раздел из 8 норм, одна редакция, по одному прогону fresh-context mapper/redteam на run): эталон связей хоста зафиксирован до run B. Итог: небольшой прирост найденных мест реализации без изменения полноты тестов, точности и времени — доказанного улучшения нет; данные в `.local/sdk-comparison/study.json`.

Не запускалось: трейты в синтетике, Linux-хост.

- Declared-профиль `REQ-...` сохранён. Accepted-профиль хранит принятие/reject/defer, rebind/revise и split/merge/retire; история не стирается, старые свидетельства не переиспользуются автоматически. Полнота относится только к принятому набору, не ко всему Markdown. Массовая переформатировка проверяемого ТЗ не требуется.
- Snapshot — хэши выбранных файлов, не копия и не ОС-песочница. Test ID и смысловая релевантность assertion остаются суждением агента/хоста.
- `delivery_complete` не означает соответствие. Разногласия показываются отдельно; финальное согласование выполняет хост. После изменения исходников нужен новый run.
- Статический HTML не отслеживает будущие изменения: перед решением обновляйте status/report.
- `php-facts` даёт syntax_only. Composer autoload и тесты — доверенный исполняемый код; оператор отвечает за изолированную среду. Инструмент не запускает тесты автоматически.
- `php-typed` (профили `php`/`laravel`) выполняется только по явному разрешению хоста; профиль `laravel` исполняет bootstrap приложения в контейнере под fail-fast окружением (`DB_CONNECTION=spec_audit_disabled`, `DB_SOCKET=`, `APP_CONFIG_CACHE` на несуществующий путь и др.), но не изолирует сеть — это обязанность оператора. Подсказки SDK не являются связями и не входят в метрики; основание анализа ограничено файлами snapshot и `vendor/` (покрыт `composer.lock`), запись bootstrap вне выбранных источников не обнаруживается. Известное ограничение: Larastan разрешает `app(Contract::class)` в привязанную реализацию — target показывает конкретный класс, не интерфейс.

Одна поддерживаемая сборка — `./tool`. Host-прототип перенесён в неё; ранние Core/PHPStan-пробы в `prototypes/core` — историческое исследование, не второй контракт продукта. В `.local/research/` сохранены прежние эксперименты и приватные снимки; `.local/` и `bin/` исключены из Git. Клонирование не восстанавливает локальные исследования/отчёты.

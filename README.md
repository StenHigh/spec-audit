# spec-audit

Нативный инструмент для проверки Markdown-требований по коду и утверждениям тестов. Требования либо объявлены в ТЗ, либо явно приняты хостом из кандидатов. Существующая AI-сессия распределяет смысловой анализ между mapper/redteam; бинарник проверяет цитаты, ведёт состояние и строит JSON/HTML. Ключи и модельные API ему не нужны.

Первый рабочий срез, не сертификатор соответствия. Он различает дефект реализации, слабый тест, неизвестность и неоднозначную норму. Зелёный запуск не превращает эти состояния в PASS. Инструмент предназначен для разных проектов; SMSPlace — текущий пилот, не источник встроенных бизнес-правил.

## Быстрый старт

Поддерживаются только `darwin/arm64` и `linux/amd64`; на других платформах установщик отказывает до скачивания. Установка без sudo и без правки профилей оболочки — в `~/.local/bin` (переопределяется `SPEC_AUDIT_INSTALL_DIR`):

```bash
install_file=$(mktemp) && curl -fsSL https://github.com/StenHigh/spec-audit/releases/latest/download/install.sh -o "$install_file" && sh "$install_file"
```

Скрипт сверяет sha256 бинарника с `release-manifest.json` того же релиза. Граница доверия первой установки — HTTPS до GitHub Releases: подпись манифеста здесь не проверяется. Дальше обновляйтесь только подписанной командой:

```bash
spec-audit version        # также --version, -V
spec-audit help           # также --help, -h: список команд JSON
spec-audit update
```

`update` проверяет подпись Ed25519 манифеста встроенным публичным ключом, ставит только версию выше текущей и только ассет своей платформы, заменяет файл атомарно; равная или меньшая версия — `updated:false`. Сборка `go build` остаётся `dev` и в `update` отказывает.

Skill для AI-сессии встроен в бинарник и ставится в проект отдельной явной командой (`init` по-прежнему создаёт только YAML):

```bash
spec-audit skill install --dir /absolute/path/project --host both   # codex | claude | both
spec-audit skill update  --dir /absolute/path/project --host both
```

`--dir` — корень проекта; пути `…/.spec-audit` и `…/.spec-audit/skill` нормализуются к корню, отказ «не установлен» называет полный путь (§24.5). Появятся реальный каталог `.spec-audit/skill/` с receipt `.spec-audit-skill.json` и относительные ссылки `.agents/skills/spec-audit` и/или `.claude/skills/spec-audit`. Symlink на месте skill (прежняя ручная установка) заменяет только `skill install --replace`; `skill update` в этом состоянии отказывает всегда. Без `--replace` обе команды отказывают при чужой host-ссылке или локально изменённом управляемом файле; чужой каталог без receipt и реальный путь на месте ссылки не заменяются никогда, лишние файлы не удаляются, `.gitignore` и Git не трогаются. Отказ по состоянию не пишет ничего; ошибка ввода-вывода посреди записи сообщается, а повторный `skill install` завершает копию. Что делать с этими путями в Git, решает проект. Вариант «ничего в Git» — строки `.gitignore`:

```gitignore
/.spec-audit/
/.agents/skills/spec-audit
/.claude/skills/spec-audit
```

Но в изолированных worktree-сессиях агентов (Claude Code desktop создаёт их для сессий) игнорируемые файлы отсутствуют и `/spec-audit` не распознаётся. Если сессии открываются так, трекайте skill, ссылки и конфиг, оставив результаты локальными:

```gitignore
/.spec-audit/*
!/.spec-audit/skill/
!/.spec-audit/config.yaml
!/.spec-audit/scopes/
/.spec-audit/scopes/*/*
!/.spec-audit/scopes/*/config.yaml
```

При tracked-варианте после `spec-audit skill update` изменения skill коммитятся отдельно.

Удаление вручную: `rm -rf .spec-audit/skill .agents/skills/spec-audit .claude/skills/spec-audit` в проекте и `rm ~/.local/bin/spec-audit`; команды `uninstall` нет. Контракт — [§18 спецификации](docs/tool-spec.md#18-поставка-версия-обновление-и-установка-skill).

## Состояние и следующие шаги

Новому агенту: начните с [AGENTS.md](AGENTS.md); `CLAUDE.md` ссылается на тот же файл. Переписка и локальная память не нужны для продолжения разработки.

На 2026-09-16 работают scoped-аудит, declared/accepted-индекс, независимые роли, сохранение raw, согласование хоста и автономный HTML с графиками, темами и переходами в редакторы. Через хоста доступен аудит задачи трекера и её исправления; бинарник не импортирует и не изменяет issues. HTML принят владельцем. Поставка: подписанный релиз `v0.1.0`, `install.sh`, `update` и встроенный skill с `skill install|update` (`init` по-прежнему создаёт только YAML); в пилоте symlink на checkout заменён установленной копией. Хосту доступны `validate` (проверки `submit` без записи) и журнал версий бинарника `tool-versions.json` в каталоге run. Accepted-набор ограничен 64 активными требованиями; единого аудита всего корпуса нет. PHP SDK: прежний `php-facts` остаётся syntax-only; новая команда `php-typed` даёт типизированные факты PHPStan/Larastan по [контракту](docs/php-sdk-contract.md) — подсказки для ролей и HTML, не связи и не PASS.

Очередь milestones по приоритету — [ROADMAP](.ai-factory/ROADMAP.md); журнал уроков и решений — [LESSONS](.ai-factory/LESSONS.md). [PHP/Laravel SDK с PHPStan/Larastan](docs/tool-spec.md#17-php-и-laravel-sdk) реализован по п.1–3 §17.2: контракт `sdk/3`, экспортёр в проверенном контейнере через `--autoload-file`, fail-fast изоляция Laravel bootstrap, записи SDK в state и подсказки в отчёте. Порядок §17.2 п.2 изменён решением владельца 2026-09-16: пилот — среда отладки, приёмка — синтетические примеры. Сравнение п.4 на пилоте дало нейтральный результат, поэтому `php-typed` остаётся опцией по требованию хоста: включать на scope с интерфейсами, биндингами контейнера, фасадами и Eloquent-магией или когда роли без SDK возвращают `implementation: unknown`; на прямолинейном коде пользы не измерено. Из уроков чистой сессии реализованы `validate`, журнал версий бинарника run и полный ответ `reconcile` после apply; отложены reference-only файлы ТЗ вне лимита 64 и разбиение больших accepted-наборов. Далее по roadmap — несколько разделов и обзор корпуса. Спецификация определяет нормы, roadmap — порядок работы.

[Прежний PLAN](.ai-factory/PLAN.md) сохранён как история 29 завершённых задач. Он не перезаписывается и не используется как активный план. Notes/compact остаются экспериментом; переход со старого re-audit и преобразование бизнес-ТЗ требуют отдельных критериев приёмки, отражённых в roadmap и [спецификации применения](docs/smsplace-adoption.md).

## Разработка с AI Factory

AI Factory 2.19.0 инициализирован локально: 18 штатных development-skills в `.agents/skills/` и `.claude/skills/`, стандартные помощники Claude — в `.claude/agents/`. Это самостоятельные копии, не ссылки на SMSPlace. Новую сессию открывайте в корне spec-audit и вызывайте `$aif-warmup` в Codex или `/aif-warmup` в Claude Code; повторный init после клонирования не нужен. Если Codex ещё не показывает skill, перезапустите сессию — [правила обнаружения локальных skills](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills).

Типовой цикл: warmup → требование/приёмка в спецификации → `aif-plan full` → `aif-implement` → `aif-verify`; review и commit — по запросу. Для новой работы full/ultra создают отдельную ветку `codex/`. Базовая ветка сейчас `codex/bootstrap` — фактическая default branch репозитория; при её изменении обновляется конфиг.

| Настройка | Назначение |
| --- | --- |
| [.ai-factory/config.yaml](.ai-factory/config.yaml) | Русский язык, пути контекста/планов, Git workflow разработки |
| [.ai-factory.json](.ai-factory.json) | Реестр версии и файлов установки AI Factory; обновляется его CLI |
| Audit CONFIG, переданный `spec-audit` | Источники кода/ТЗ, runtime и reports_dir конкретного аудита; другой формат |

Fast-план использует `.ai-factory/ACTIVE_PLAN.md`, полные планы — `.ai-factory/plans/`; отсутствующие планы и optional-каталоги не создаются заранее. Общие правила и архитектура доступны из [AGENTS.md](AGENTS.md). Разделы `paths.*` задают адреса артефактов, а не утверждают, что каждый уже существует.

MCP и сторонние skills не подключались. Node использовался установленным AI Factory для setup и может потребоваться его helper-командам; это не зависимость готового spec-audit. Development-skills не входят в [поставляемый audit-launcher](skills/spec-audit/SKILL.md) и не устанавливаются им в бизнес-проект.

## Сборка и проверки

Разработка: Go 1.27.0; поддерживаемые ОС — macOS/Linux. Из этого репозитория:

```bash
go test ./tool
go vet ./tool
CGO_ENABLED=0 go build -o bin/spec-audit ./tool
```

Готовому бинарнику для init/index/reconcile/prepare/tasks/submit/retry/status/review/report не нужны Go, Node, Python, PHP или доступ к модели. `test` требует runtime проверяемого проекта: Go либо PHP в проверенном Docker Compose container. PHP на хосте не запускается. Тесты инструмента используют синтетические данные; Docker-протокол дополнительно проверяется подставным процессом, без доступа к SMSPlace.

Проверка внешнего эксперимента извлечения использует тот же валидатор и учёт reviewer, не новый production CLI:

```bash
SPEC_AUDIT_EXTERNAL_CONFIG=/absolute/path/config.yaml \
SPEC_AUDIT_LEGACY_RAW=/absolute/path/extractor.raw.json \
SPEC_AUDIT_LEGACY_GOLD=/absolute/path/gold.json \
SPEC_AUDIT_LEGACY_REVIEW=/absolute/path/reviewer.raw.json \
go test ./tool -run '^TestExternalExtractionReview$' -count=1 -v
```

Без внешних входов тест пропускается. Он проверяет хэши, цитаты и полный взаимный учёт оценок; смысловую оценку даёт reviewer, а не зелёный тест. Пропуски, добавленные нормы и возражения к эталону делают этот контроль красным.

Новый test-only контроль отдельно учитывает нормы и заметки:

```bash
SPEC_AUDIT_CONTEXT_CONFIG=/absolute/path/config.yaml \
SPEC_AUDIT_LEGACY_RAW=/absolute/path/extractor.raw.json \
SPEC_AUDIT_CONTEXT_NOTES=/absolute/path/notes.raw.json \
SPEC_AUDIT_CONTEXT_GOLD=/absolute/path/gold.json \
SPEC_AUDIT_CONTEXT_REVIEW=/absolute/path/review.json \
go test ./tool -run '^TestExternalContextReview$' -count=1 -v
```

Внешние тесты typed SDK используют собственные контейнеры синтетических примеров (нужен Docker; без переменных окружения пропускаются):

```bash
docker compose -f acceptance/php-sdk/plain/compose.yml --profile install run --rm install
docker compose -f acceptance/php-sdk/plain/compose.yml up -d app
docker compose -f acceptance/php-sdk/laravel/compose.yml --profile install run --rm install
docker compose -f acceptance/php-sdk/laravel/compose.yml up -d app
SPEC_AUDIT_TYPED_PLAIN_CONFIG=$PWD/acceptance/php-sdk/plain/config.yaml \
SPEC_AUDIT_TYPED_LARAVEL_CONFIG=$PWD/acceptance/php-sdk/laravel/config.yaml \
go test ./tool -run '^TestExternalTyped' -count=1 -v
```

`SPEC_AUDIT_TYPED_RECORD=1` перезаписывает фикстуры `tool/testdata/typed-*.json`; они пинятся к текущему экспортёру, поэтому после правки `tool/sdk-typed.php` их нужно перезаписать. `composer install` выполняется только в контейнере примера; `network_mode: none` у сервиса анализа — часть контроля SA-034, не свойство инструмента.

`TestExternalContextPacket` принимает `SPEC_AUDIT_CONTEXT_TASK` — один полный Task из prepare, проверяет lossless round-trip и сообщает только размеры. Необязательные `SPEC_AUDIT_CONTEXT_CONFIG` и `SPEC_AUDIT_CONTEXT_PACKET` (простое имя файла) сохраняют compact-пакет в reports_dir, только если такого файла ещё нет. Без входа контроль пропускается; обычный Result/submit не меняется. Эти Go-драйверы нужны для эксперимента, не для запуска готового бинарника.

## Релиз

Релиз публикует [`.github/workflows/release.yml`](.github/workflows/release.yml) по тегу `vX.Y.Z` (контракт — [§18 спецификации](docs/tool-spec.md#18-поставка-версия-обновление-и-установка-skill)). Матрица — только `darwin/arm64` и `linux/amd64`: каждая платформа собирается и квалифицируется нативно на runner той же платформы (`version` → `release:true`, `index` синтетического CONFIG, `skill install`/`update`, неизменность бинарника после `update`, отказ dev-сборки); cross-build без исполнения ассетом не становится. Публикует один job в окружении `release`: считает sha256, собирает `release-manifest.json`, подписывает его Ed25519 и создаёт GitHub Release с `install.sh`, манифестом, `release-manifest.sig` и двумя бинарниками.

Однократная настройка владельцем (нужен OpenSSL 3; системный LibreSSL macOS не подписывает `-rawin` — `brew install openssl@3`):

```bash
openssl genpkey -algorithm ed25519 -out spec-audit-release.pem
openssl pkey -in spec-audit-release.pem -pubout -outform DER | tail -c 32 | xxd -p -c 64
```

- Вывод второй команды (64 hex) — repository variable `SPEC_AUDIT_RELEASE_PUBLIC_KEY`; он встраивается в бинарник при сборке через `-ldflags -X main.releasePublicKeyHex`.
- Содержимое `spec-audit-release.pem` — secret `SPEC_AUDIT_RELEASE_SIGNING_KEY` **окружения** `release` с обязательным ревьюером; build-job ключа не видит. Локальную копию ключа храните вне репозитория.

Порядок выпуска: `go test ./tool && go vet ./...` зелёные на коммите → `git tag v0.1.0 && git push origin v0.1.0` → одобрить job `release` → на хосте `spec-audit update` (или первая установка через `install.sh`) должен показать новую версию. Dev-сборка (`go build`) остаётся `version: dev`, `release: false` и отказывает в `update` без сети — обновляется только релизный бинарник с именем `spec-audit`.

## Первый запуск

```bash
./bin/spec-audit init /absolute/path/audit.yaml
# Отредактируйте пути по контракту спецификации.
./bin/spec-audit index /absolute/path/audit.yaml
./bin/spec-audit prepare /absolute/path/audit.yaml first
./bin/spec-audit tasks /absolute/path/audit.yaml first
./bin/spec-audit report /absolute/path/audit.yaml first
```

init создаёт только отсутствующий YAML, не каталоги исходников. Относительные project_root/reports_dir считаются от CONFIG. Перед отправкой ответ роли можно проверить `validate CONFIG RUN_ID TASK_ID RESULT_PATH` — те же проверки, что у `submit` (строгий JSON, полнота полей и ID, значения состояний, цитаты против snapshot), без записи в run; ошибка называет ID нормы; успех не заменяет `submit`, который заново проверит источники и дубликаты. Каждый ответ роли отправляется через `submit CONFIG RUN_ID TASK_ID RESULT_PATH`; retry сохраняет предыдущую попытку. Каждая успешная публикация state или согласования добавляет запись в `tool-versions.json` каталога run (команда, версия бинарника, время); `report` показывает их в `tool_versions` и в шапке HTML — смешанный run виден, повреждённый журнал не скрывается ([§19](docs/tool-spec.md#19-уроки-чистой-сессии-проверка-ответа-роли-провенанс-версии-ответ-reconcile)). Все команды возвращают JSON, LOG_LEVEL управляет диагностикой stderr. Успешная команда `test` возвращает receipt: проверяйте его `state`, а не только exit самого CLI.

`prepare` пишет список файлов и протокол роли один раз в `reports_dir/RUN_ID/dispatch/files.json` и `dispatch/protocol.txt` и каталог каждой роли `dispatch/<task_id>/` с `task.json` и `prompt.md` — промптом роли с абсолютными путями и командой `validate` (§24.2, §26.3, §30.1; `retry` восстанавливает оба, подсказки SDK — отдельный `sdk_hints.json`); `tasks` называет `expected`/`submitted`/`delivery_complete` (§30.3); `cite CONFIG PATH A B` печатает точную Citation строк A–B файла под `project_root` без записи (§31.1), промпт роли называет CITE и просит вести `validate.log` (§31.2); `index CONFIG summary` и `review CONFIG RUN_ID summary` — те же проверки без тел норм, файлов и `entries`: счётчики, `active_ids`, `scopes`, advisories; `roles[]`, `outcomes[]`, `agree`/`disagree`, состояние решения (§32); `anchors CONFIG` — до приёмки: где нормативные файлы упоминают якоря `A-NNN`/`§N.N` и какие строки spec-файлов их определяют, `undefined` — без определения (§33.1); `review … REQ-ID text` — читаемая сводка нормы в поле `text` (§33.4); `citations` фильтруется путём, нормой или ролью (§33.2); публикующая команда на run, подготовленном другой версией, пишет WARN (§33.3); `overview CONFIG...` — карта нескольких scope: freshness, принятый набор, последний run и последнее решение хоста со счётчиками, `totals` (§34; без заявления о полноте корпуса); `review … REQ-ID brief` — текст нормы со счётчиками цитат вместо списков (§35.2); `report.json` несёт `requirements[].navigation.host_states` (§36.1); `overview` — `contradicted[]` по решённому run (§34); `anchors` даёт `kind` и `references` у определений, `index … summary` — `accepted: {head, history_total}`, `brief` — без строк запусков (§37); `check`/`reconcile` называют `deferred`/`rejected`, `index … summary` — `last_deferred`; `anchors CONFIG [PATH...]` резолвит якоря в файлах вне snapshot (`outside`) и вложенные ссылки (`nested`); `oversize_reason` у scope подавляет advisory о размере (§38); второй пакет на том же scope — операция `keep` продолжает прежнюю норму без кандидата, пока её файлы не изменились (REQ-SA-048, `kept[]` в ответах); `anchors` разворачивает диапазоны `A-051–A-055` (§39); `previous_host` находится по содержанию нормы, переживает `keep` и изменение кода (`same_files` говорит, менялись ли источники), `tasks` даёт `pending_ids` (§40); отказ формы называет недостающие и лишние поля, `outcomes[].ambiguous_over_clear` называет роль, поставившую ambiguous принятой clear-норме, `matches[].likely_duplicate` помечает почти дословный повтор (§41); `matches[].text_similarity` ловит свод своими строками, `overview.contradicted_code[]` — кросс-scope память по строкам кода, отказ «цитата вне блока» называет допустимые диапазоны (§42); `related` в CONFIG даёт под каждой нормой `contradicted_elsewhere` — строки кода ролей, уже contradicted у соседних scope (§43); `corpus OUT_HTML CONFIG...` — одна статическая HTML-карта по всем scope: итоги, таблица scope со ссылками на `report.html`, нормы внимания со statement хоста, файлы под противоречиями, счётчик GAP по классам implementation/verification/specification — каждая норма один раз в самом тяжёлом классе (§45, §45.1); DECISION приёмки `version: 2` с `narrowed_statement` — сужение statement кандидата словами оригинала (REQ-SA-049, §46); `delta` в `overview`/`corpus` — что закрылось и открылось между решёнными run scope, `baseline_run` в CONFIG закрепляет точку «до» (§47); решение version 2 проходит ту же проверку полноты свидетельств, что version 3; `update` выставляет права до публикации; SIGINT/SIGTERM останавливают дочерние процессы (§48); `publish OUT_DIR CONFIG...` — статический сайт для заказчика: `index.html` (карта со списком решённых run по времени), `overview.json`, копии `report.html` всех решённых run (§49); `prepare CONFIG RUN_ID since PREV_RUN` — инкрементальный run: роли переоценивают только новые, GAP и затронутые нормы, остальные вердикты переносятся с провенансом и пометкой `carried` (§50, REQ-SA-050); отбор по цитируемым строкам и классам GAP, задания `incremental-N` по ≤ 24 норм, `plan CONFIG PREV_RUN` без создания run, причины переоценки в `outcomes`/`brief`/промпте (§51); contradicted-норма на неизменных строках переносится как `known_defect`, причины `new|implementation_gap|verification_gap|changed`, `delta.carried` (§52); `delta.worsened[]` и `summary.advisories[]` (§53); `rerun RUN_ID CONFIG...` — инкрементальные run по всем scope одной командой от `baseline_run`/последнего решённого (§54); журнал индекса version 2 хранит классификацию источников — перенос файла между `specs` и `references` делает индекс stale, старые журналы читаются (§55); память берёт только противоречащие цитаты и помечает `role_here`, `brief` сворачивает её в строку на норму, отказ типа JSON называет поле, `prepare` принимает заранее созданный каталог (§44); `index` в accepted-режиме называет `freshness: fresh` (§26.1), а `index`/`check`/`reconcile` дают `advisories` о якорях `§N.N`/`A-NNN` из текста норм без определения в spec-файлах snapshot (§26.2 — подсказка, не оценка; якорь, не названный в норме, не находится); другие файлы каталога принадлежат роли. После получения обеих ролей `review CONFIG RUN_ID` возвращает основу решения хоста, `roles[]` — список заданий с ролью, scope, попыткой и признаком доставки — и `outcomes[]` — состояния обеих ролей по каждой норме с признаком `agree` , их `limitations` и `previous_host` — последний вердикт хоста по той же норме из соседнего run с тем же snapshot и accepted head (§24.1, §25; подсказка для чтения, не оценка и не перенос вердикта). `validate CONFIG RUN_ID host DECISION` проверяет решение тем же путём, что `review`, ничего не записывая (§27, REQ-SA-047: `valid:true` означает, что `review` с этими байтами сейчас запишет; `duplicate:true` — байты уже в журнале); `outcomes[]` также несёт `previous_host.statement` и по каждой роли `citations`/`only_here` — ссылки на строки, которые цитирует только эта роль (§27.1–27.2). `review CONFIG RUN_ID REQ-ID` читает одну норму: роли (statement, limitations, полные цитаты), `outcome` с `previous_host`, вердикт хоста и запуски тестов (§29.1); `review CONFIG RUN_ID citations [PATH]` — индекс цитат run: кто (mapper, redteam, собственные цитаты хоста) и под какой нормой цитирует строки файла, без quote (§30.2); ответ `review … DECISION` повторяет `version`/`requirements`/`own_citations` (§29.2); при relevant-тестах штатного пути и contradicts-тесте ветки assertion нормы — contradicts (§14). `statement` вердикта может быть пустым только при `concur: both` и совпадении с оценками обеих ролей — тогда отчёт показывает «Совпадает с оценками обеих ролей.» (§28.3); `advisories` и `sdk` в ответах — всегда списки (§28.1). `draft CONFIG RUN_ID` печатает пустой черновик решения version 3 с текущим basis_sha256, `review_id` `host-review-NNN`, всеми нормами и нулевыми `counts` (§24, REQ-SA-045; ничего не записывает, до полной доставки и на stale-снимке отказывает). Заполните его (`version: 3` — как version 2 плюс собственные цитаты хоста `spec/code/tests` в вердикте по правилам §7, только там, где вердикт держится на строках, которых роли не цитируют; §25) или сохраните DECISION `version: 2` по [§23](docs/tool-spec.md#23-облегчённая-форма-host-decision-version-2-и-список-ролей): один вердикт на норму с `concur: mapper|redteam|both` (чьи текущие свидетельства принимает хост), statement хоста и `counts`, которые бинарник пересчитывает и при расхождении отклоняет; цитаты ролей не копируются. Полная форма `version: 1` по [контракту §14](docs/tool-spec.md#14-контракт-согласования-аудита) остаётся для случаев, когда хост цитирует то, чего роли не приводили. Вызовите `review CONFIG RUN_ID DECISION`, затем `report`: решение хоста показывается рядом с принятыми свидетельствами и подписью «свидетельства mapper / свидетельства redteam / свидетельства обеих ролей» — concur называет принятые свидетельства, не согласие роли с вердиктом (§24.3). Отчёт показывает решение рядом с неизменёнными ролями. Изменение исходников, новая попытка или receipt делают прежнее решение outdated; история остаётся. Новые raw сохраняются побайтно, старые явно обозначаются legacy_canonical.

`report` также создаёт [карту проекта](docs/tool-spec.md#15-карта-проекта-для-человека): обзор областей внимания, поиск/фильтры норм и полный список выбранных файлов. Откройте выданный `report_html` в браузере: карточка нормы ведёт к сохранённому фрагменту ТЗ/кода/assertion, а фрагмент — обратно к связанным нормам. HTML автономен, без сети, сервера и checkout; полный код в него не копируется. Без JavaScript доступны графики, все раскрывающиеся блоки и внутренние ссылки, но не настройки и фильтры.

В «Графиках по разделам ТЗ» видны поддержка кодом, наличие тестов и отдельно достаточность проверок. Weak явно подписан «Тесты есть, но проверка частичная или слабая» и имеет свой фильтр. Каждая норма учитывается один раз по основному файлу ТЗ; клик по файлу отбирает его нормы. Проценты относятся только к этому run, не к строкам кода или всему продукту. Нет текущего согласования — «не оценено», а не 0% или историческая зелёная оценка.

В «Настройках» выберите Zed, PhpStorm, Cursor или VS Code, при необходимости замените локальные каталоги кода/тестов и ТЗ. Defaults берутся из CONFIG; для ТЗ показан снимаемый префикс snapshot, поэтому `TZ/` не удваивается. Рядом с цитатами появятся ссылки на начальную строку в редакторе. Они требуют установленного обработчика URI и открывают текущую рабочую копию, которая могла измениться. Тема по умолчанию системная, доступны светлая и тёмная. Выбор хранится только в браузере; при отказе storage работает до закрытия страницы. YAML и исходники не меняются.

Dev-only проверка интерфейса использует новый синтетический fixture и уже установленный Playwright/Chromium, не реальный бизнес-отчёт:

```bash
SPEC_AUDIT_HTML_FIXTURE=/tmp/spec-audit-ui-fixture.html go test ./tool -run '^TestReportUIFixture$' -count=1
SPEC_AUDIT_PLAYWRIGHT=/absolute/path/to/playwright \
SPEC_AUDIT_CHROMIUM=/absolute/path/to/chromium \
node tool/report_ui_test.cjs /tmp/spec-audit-ui-fixture.html
```

Это необязательный dev-check, не зависимость бинарника; ничего автоматически не устанавливается. Проверяются темы, обе ветви browser storage, четыре URI-профиля, экранирование, фильтры/якоря, клавиатурный фокус, узкое окно и отсутствие внешних запросов. Реальное открытие каждого IDE и клавиатурное подтверждение нативного select требуют проверки в пользовательской среде: macOS headless в контрольном примере не обрабатывает выбор стрелками.

Карта показывает весь инвентарь **данного snapshot**, не утверждает, что весь проект проверен. «Нет текущих связей» — повод разобрать файл, не доказательство лишнего кода. Вопросы ТЗ, различия ролей, слабые assertions и фактическое исполнение разделены; текущий итог хоста не стирает предварительные оценки и историю. Автоматический поиск всех противоречий ТЗ и неописанной функциональности не заявляется.

Без AI можно индексировать, просматривать задания/отчёты и явно запускать разрешённые тесты. Для смыслового аудита используйте лаунчер в текущей сессии. CONFIG и reports_dir размещаются в явно выбранной внешней области либо в разрешённой локальной `.spec-audit/`, исключённой из Git; исходники и результаты не пересекаются. Инструмент не пишет проектные планы, не создаёт issues и не исправляет код. Workflow разработки выбирает сам проект; настройки пилота описаны отдельно.

Для обычного Markdown задайте `index_mode: accepted`: `reconcile CONFIG` покажет источники и текущую базу решений, а `reconcile CONFIG RAW DECISION` применит явное решение хоста и вернёт тот же view, что читающий вызов (`freshness` измеряется заново; `records[]` несут `revision`/`clarity`). Затем используются те же index/prepare/tasks/report. Полный пакет ограничен 64 кандидатами; [контракт и формат решения](docs/accepted-index.md#json-решения). Определяющие смысл документы, которые в этом scope не аудируются, задаются группой `references: {paths: [...]}` ([§20](docs/tool-spec.md#20-справочные-источники-тз-и-деление-большого-набора)): они хэшируются, цитируются кандидатами и ролями и делают индекс stale при изменении, но не порождают кандидатов — `reconcile` отклонит кандидата, у которого нет цитаты из нормативного файла. При scope больше 24 норм `index` возвращает `advisories`, а `index`/`prepare` пишут WARN: бинарник нормы не режет, хост задаёт явные `scopes` по подразделам ТЗ. Перед применением решения `check CONFIG RAW` выполняет все проверки apply без записи (журнал, source_set, точные цитаты, нормативная цитата) и для каждого кандидата даёт `matches` — до трёх прежних active ID по пересечению строк цитат с `overlap`/`shared_lines`/`fields_equal` (подсказка, не решение), а `check CONFIG RAW DECISION` предсказывает исход: будущие ID, rebind/revise, `retired`, `next_head`, `duplicate` ([§21](docs/tool-spec.md#21-уроки-второго-прогона-проверка-приёмки-без-записи-подсказки-сопоставления-изоляция-ролей)); успех `check` не гарантирует apply — источники и журнал проверяются им заново под блокировкой; в ответе с DECISION `base_index_current:true`, а `freshness` описывает текущий индекс до применения. Если подсказка указывает на норму, чья принятая формулировка по-прежнему верна, хост применяет `reanchor` (пустые title/verification): содержание, ID, revision и content hash сохраняются, цитаты переезжают к кандидату — счётчик редакций движется только при смысловой правке (`revise`); поле `unique_shared` показывает, держится ли подсказка на строках, общих с другими нормами ([§22](docs/tool-spec.md#22-уроки-третьего-прогона-перепривязка-с-сохранением-содержания-подсказки-диагностика-scopes)). После приёмки, изменившей ID, `index`/`prepare` называют scope и устаревшие ID. Сам бинарник не извлекает смысл и не выдаёт кандидатам статус нормы автоматически.

## Приёмка и ограничения

Чистая AI-сессия на пилоте 2026-09-16 (первая половина этапа roadmap): новая сессия Claude Code в checkout пилота через установленный launcher прошла scope `02-finance` полностью — извлечение 51 кандидата и DECISION (49 accept, 2 defer, 5 ambiguous), обе роли доставлены с первой попытки (mapper ≈507 k токенов / 27 мин, redteam ≈593 k / 36 мин при `scopes: []` — 49 норм × 2509 файлов), host review `current`: implementation supported 49/49, assertion relevant 42 / weak 6 / missing 1; `test`/`php-typed` не авторизованы, `semantic_completeness_proven=false`. Бизнес-код, ТЗ и CI не менялись (`git diff` бизнес-файлов с начала этапа пуст), `git status` чист. Известный инцидент: во время run из другой сессии бинарник обновлялся 0.1.0→0.1.3 и scope-конфиг переписан на относительный `project_root`; run остался `fresh` (source_set совпал), но версия бинарника в manifest/state не фиксируется — провенанс смешанного run не восстановить; это и другие уроки — в [ROADMAP](.ai-factory/ROADMAP.md). Вторая половина — независимый синтетический проект `spec-audit-synthetic` (копия корпуса приёмки: `rules.md` с 5 нормами, Go-код и тесты, declared-профиль, tracked skill 0.1.3) из новой сессии Claude Code: обе роли доставлены, хост авторизовал `test` — receipt `passed`, 4 теста, Go 1.27; host review `current`. Сверка с независимыми ожиданиями `acceptance/expected.json` (сессия их не видела): 13 из 15 полей совпали — REQ-DEMO-001…003 полностью (в том числе дефект с зелёным закрепляющим тестом), REQ-DEMO-004 assertion `unknown` вместо `missing` (mapper дал `missing`, redteam `unknown`), REQ-DEMO-005 assertion `weak` вместо `unknown` при верных `ambiguous`/`unknown`. Исходники синтетического проекта не изменены, `git status` чист. Один слепой проход — не статистическая оценка точности; обе сессии — Claude Code, ограничения Codex не проверялись.

- Declared-профиль `REQ-...` сохранён. Accepted-профиль хранит принятие/reject/defer, rebind/revise и split/merge/retire; история не стирается, старые свидетельства не переиспользуются автоматически. Полнота относится только к принятому набору, не ко всему Markdown. Массовая переформатировка проверяемого ТЗ не требуется.

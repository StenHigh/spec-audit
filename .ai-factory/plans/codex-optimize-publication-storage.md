## Уточнение владельца

Решение 2026-10-27 заменяет прежнее предложение архивировать сайты через `bundle sites`.
Сайты не сохраняются как постоянное основание аудита, включая новые переносимые пакеты.
Сайт генерируется из сохранённых отчётов; историческая публикация выбирает сохранённый run.
По умолчанию публикуются все существующие области выбранного каталога аудитов, с последними полными сохранёнными решениями.

Публикация показывает редакцию спецификации и основание кода на момент аудита.
Человек решает, когда запускать следующий аудит для сравнения кода с выбранной редакцией спецификации.
Изменение кода не запускает аудит автоматически, не меняет сохранённые выводы и не снимает их с публикации.
Метки актуальности по §80 и контроль редакции по §82 сохраняют свои отдельные значения.

Уточнение 2026-10-27: разные области могут иметь аудиты на разных редакциях спецификации.
Карта всегда показывает для каждой области редакцию её выбранного аудита.
Общий сайт не означает проверку всех областей на одной редакции.
Дата генерации сайта не обновляет редакции проведённых аудитов.

## Результат change

`publish` каждый раз генерирует сайт из сохранённых JSON-отчётов и проверенного основания run.
Сформированный OUT нужен для просмотра и размещения; инструмент не создаёт его скрытых резервных копий.
Сайты не попадают в новые bundles. Переносимый пакет сохраняет аудит, из которого сайт можно собрать заново.
Удаление OUT и старых HTML не требует нового AI-аудита.

По умолчанию сайт содержит последнее полное решение каждой обнаруженной области.
Новый незавершённый run не заменяет последнее пригодное сохранённое решение.
Исторический режим публикует явно выбранный run отдельной области в отдельный OUT.
Результат исторического режима не меняет выбор по умолчанию следующей публикации.

Новый site `result.json` ссылается на соседний `report.json`, вместо повторения полного отчёта и решения.
Штатная очистка удаляет доказанные старые копии сайтов, сохраняя отчёты, свидетельства и source-зависимости.
Повторная генерация сохраняет данные аудита; прежние bytes HTML, время генерации и оформление не являются гарантией.

```text
Каталог аудитов: области A, B, C
                 |
     сохранённые JSON-отчёты и основание
                 |
          выбор результатов
          +-- default: последние A/B/C
          +-- historical: CONFIG + run
                 |
          renderer текущего бинарника
                 |
          OUT: автономный сайт

bundle: данные аудита -> restore -> повторная генерация
скрытый архив сайта: отсутствует
```

## Зачем появились копии

| Представление | Назначение сейчас | Решение change |
| --- | --- | --- |

| Сохранённый `report.json` run | Публичное представление аудита; источник чтения и публикации | Сохранить |

| Полный report внутри site `result.json` | Самостоятельная оболочка машинного результата | Заменить ссылкой на соседний report |

| `._publications` и объекты всего сайта в каждой области | Точное восстановление сайта после удаления OUT | Прекратить новую автоматическую запись; старое освобождать явно |
| Bundle `sites` | Явное точное сохранение прежних сайтов | Убрать из нового write-контракта; старые пакеты читать по их прежней схеме |

| `report.sources` | Публичное происхождение, доступность и ссылки на сохранённые исходники | Сохранить |

Эти списки пересекаются, но не являются одинаковыми каталогами.
Их нормализация потребует отдельного изменения модели и пока не оправдана замером.

Приватные данные пилота и внешние потребители результата не исследовались.

## Выбранное устройство

### 1. Выбор областей и run перед генерацией

Новый основной маршрут: `publish OUT_DIR [--from AUDIT_ROOT] [--corpus-control FILE]`.
AUDIT_ROOT по умолчанию — текущий каталог, выбранный оператором для работы с аудитами.
Параметр `--from` задаёт другой корень явно; он не сохраняется как скрытая глобальная настройка.
Внутри корня обнаруживаются все самостоятельные reports-области с проверенным состоянием run, а не произвольные YAML-файлы.
Сохраняется явный маршрут `publish OUT_DIR CONFIG...` для ограниченной подборки; это осознанный фильтр, не основной default.

Поиск ограничен AUDIT_ROOT. Симлинки и выход за границу запрещены; известные objects, inputs, source-viewers, staging, VCS и OUT не обходятся.
Использовать существующие exact-path helpers и общие лимиты файлов/состояния; превышение лимита даёт явный отказ.
Найденный `RUN_ID/manifest.json` проверяется вместе с report/state/review; одно имя файла не доказывает наличие аудита.
Один физический reports_dir учитывается один раз, включая несколько версий `._inputs` одной внешней области.
Внешняя идентичность включает project/corpus/line/scope; локальная область сохраняет прежнюю принадлежность отдельному reports_dir.
Две независимые копии одной логической области требуют явного устранения неоднозначности, без молчаливого выбора по пути.

Переносимое размещение определяется обнаруженным reports_dir и проверенными рабочими CONFIG после restore.
Сохранённые абсолютные пути внутри старого manifest не превращаются в новое место чтения или записи.
Историческая идентичность manifest остаётся прежней; переписывать его ради нового расположения нельзя.
Нет checkout или рабочего CONFIG — разрешено чтение проверенного сохранённого основания; текущее наблюдение остаётся unchecked.

Для каждой области брать последний полный согласованный run с report, отражающим точное основание решения.
Порядок сохранить по §34: recorded_at записи prepare, затем RUN_ID при равном времени, среди пригодных завершённых run.
Строки spec_version непрозрачны; не сортировать R1/R2 или версии по словам и не угадывать актуальную внешнюю редакцию.
Более поздний pending run не вытесняет прежний полный результат; область без результата видна с явной причиной.
Повреждённое состояние не маскируется молчаливым выбором старого результата.
Внешний run требует подтверждённой независимой review-check по его точному основанию, как прежде.

Исторический маршрут: `publish OUT_DIR --run RUN_ID CONFIG [--corpus-control FILE]`.
Он принимает ровно один CONFIG, проверяет принадлежность run и публикует только этот сохранённый результат.
Селектор не сочетается с автоматическим `--from`; неверное сочетание даёт отказ до создания OUT.
Фильтр не изменяет accepted head, результаты, default-выбор, CONFIG или историю.
Общий сайт по умолчанию не копирует HTML всех исторических run: история хранится в данных и публикуется явно по запросу.

В обоих режимах статистика, вопросы, accepted head, версия спецификации и выводы выбранного результата берутся из его основания.
Исторический режим не подставляет нынешний accepted-index, вопросы новой спецификации, latest-run или сегодняшние GAP соседей.
Он обозначает исторический выбор и unchecked для текущей актуальности; новый renderer не означает новый аудит.
Контроль редакции задаётся публичным параметром §82; он не выбирает результаты и не сохраняется между командами.

«Последняя информация» означает последние сохранённые результаты аудита, а не автоматическую проверку сегодняшнего кода.
Сайт показывает run/snapshot, редакцию спецификации, основание кода, дату аудита и отдельную дату генерации.
Обычные наблюдения свежести допустимы по §80; они не заменяют решение и не запускают новый аудит.

### 1.0. Проверенная редакция у каждой области

В общей таблице областей добавить явную колонку «Проверено на редакции спецификации».
В карточке области и её отчёте повторить эту редакцию рядом с run и датой аудита.
Подпись обязательна в default и historical, с corpus-control и без него; она доступна без JavaScript.
Пример одной карты: область A — «проверено на R3», B — «проверено на R1», C — «проверено на R2».
Общая дата формирования сайта не заменяет даты аудитов областей.

Источник подписи — сохранённое основание выбранного run: его Report.External/Manifest.External и spec_version.
Текущее scope.External из свежего snapshot/импорта не может заменить редакцию проведённого аудита.
При расхождении сохранённых report и manifest нужна диагностика неверного основания, а не произвольный выбор версии.
Исторический selector показывает редакцию выбранного run, даже если последний аудит области выполнен на другой редакции.
Область без завершённого аудита получает подпись «Аудит не завершён», без утверждения о проверенной редакции.

Если редакция в основании не названа, показать «Редакция не указана» и доступные run/snapshot отдельно.
Не присваивать локальному аудиту выдуманный spec_version и не подставлять версию соседней области или контроля.
Хэши сохранённых документов могут раскрывать точное основание, но не выдаются за именованную редакцию.

Сравнение с выбранным контролем по §82 остаётся отдельным: например, «проверено на R1; на R3 не проверено».
Без явного контроля сайт не угадывает текущую редакцию и не вычисляет её по другим областям.
Разные обозначения редакций сами по себе не доказывают ухудшение кода или потерю силы сохранённого решения.
Перенос аудита и повторная генерация сохраняют редакцию каждой области; новый аудит назначает человек.

### 1.1. Renderer не зависит от сохранённых HTML

Убрать `recordPublication` из пути новой публикации, включая staging до финального rename.
Генерировать report HTML, corpus HTML, компактный result и viewer-ресурсы непосредственно в OUT.
Не читать прежний `report.html` как обязательный вход и не пропускать run только из-за отсутствия HTML.
Сохранённый report JSON, manifest, raw и решения не переписываются при публикации.

`RequirementNavigation.Host` имеет `json:"-"` и теряется при чтении JSON.
Перед HTML-рендерингом восстановить внутренние указатели из `HostReview.Latest` по ID норм, не создавая новых оценок.
Сохранить записанные navigation evidence и SDK-проекции; повторный buildNavigation не должен терять непубличные SDK facts.
Если нужны отдельные исторические данные manifest, брать manifest выбранного run, а не текущий snapshot.
Полные архивные источники брать по проверенным hashes из objects; citations сохраняет только цитаты.
Невозможность восстановить нужную часть представления должна иметь явную диагностику, без подстановки текущих исходников.

Явный прежний `report CONFIG RUN_ID` может выдавать HTML как результат команды.
Такой файл является воспроизводимым выводом, а не обязательной частью хранения/переноса аудита или резервной копией сайта.
Новый publish не создаёт дополнительные HTML внутри reports_dir и не использует их как cache.

Сборка выполняется через общий staging и публикуется в новый отсутствующий OUT одним rename для всех режимов.
Существующий OUT и другие публикации не изменяются при отказе или историческом выборе.
Archive/citations могут находиться в одном сайте: прежняя причина копирования всего сайта в citations-state устранена.
Source retention проверяется для каждой области; нельзя копировать полный источник в citations-страницу или её данные.
Размещение на хостинге и удаление сформированного OUT остаются отдельными действиями оператора.

### 1.2. Bundle переносит аудит, не сайт

Новая запись bundle получает schema_version 3 с явным audit-only контрактом.
Request schema 2 содержит `schema_version` и `configs`, без `sites`; старый request с непустым sites получает понятный отказ нового export.
Прежний request schema 1 с пустым sites можно принять как совместимый вход нового audit-only export.
Чтение/verify/restore прежних bundles v1/v2 сохраняет их точные bytes, включая уже существующие site areas.
Обычное чтение не преобразует старый архив и не создаёт новую копию сайта.

Новый export не включает OUT, `._publications`, publication-only objects, производный report HTML и восстановимые viewer HTML/bin.
Опись всех выбранных файлов и происхождение сохраняются, даже если для файла нет цитат.
В archive-профиле сохраняются необходимые полные source-объекты; в citations-профиле их не появляется.
Raw, решения, попытки, manifest, accepted ledger, review-check, SDK/receipts и JSON-отчёты сохраняются.
Исключение производных ресурсов требует проверки их роли, ссылок и hashes; неизвестные данные не удаляются по имени.

Независимый restore нового пакета должен дать те же данные аудита и возможность повторной генерации обычного и исторического сайта.
Сайт не требуется прикладывать к backup даже при освобождении прежних publication-копий.

### 2. Новый site result ссылается на полный report

Добавить отдельную `external-result-v4.schema.json` для публикуемой компактной оболочки.
Сохранить небольшие поля идентичности, basis, source retention, report basis, current freshness и paths.
Вместо полных `report` и `decision` записывать:

```json
{
  "schema_version": 4,
  "report_ref": {
    "path": "report.json",
    "sha256": "<SHA-256 точных опубликованных bytes>",
    "bytes": 80660
  },
  "decision_ref": {
    "path": "report.json",
    "pointer": "/host_review"
  }
}
```

Это фрагмент формы, не полный валидный result.
JSON pointer — адрес поля внутри JSON-документа.
Обе ссылки используют один report; hash и размер `report_ref` защищают также цель `decision_ref`.
Проверять совпадение run/snapshot/scope/basis оболочки и отчёта, а не только hash.
Пути остаются относительными, внутри каталога run; произвольные URL и выход из каталога запрещены.
Если исторический report не содержит `host_review`, оболочка задаёт `decision_ref:null`.
Нельзя добавлять отсутствующее поле в старый report только ради ссылки.

Hash считать по итоговым bytes файла, включая последний LF, после подготовки выбранного представления и сериализации.
Исторический report сохраняет данные выбранного аудита; wrapper сообщает historical_publication и unchecked по §80.
Новый HTML исторического run строится текущим renderer; прежний HTML не нужен.
Старые report/result не переписывать; новый result находится только в новом OUT.

CLI `external result CONFIG RUN_ID` пока сохраняет самостоятельную v3.
Он вычисляет свежую проекцию отчёта в памяти; сохранённый `report.json` может иметь другие bytes и наблюдение.
Поэтому ссылка на старый файл не заменяет его payload корректно.
Новый compact-режим CLI не нужен для устранения постоянных дублей и в этот change не входит.

### 3. Переход старого состояния через существующий cleanup

Расширить маршрут явным выбором: `cleanup plan ARCHIVE --publications ID...`.
Без флага прежняя очистка dispatch-дублей сохраняется.
ID — полный идентификатор старой публикации; план перечисляет все выбранные копии внутри включённых reports-областей.
Cleanup касается управляемых старых копий, не удаляет OUT хостинга, чужие файлы или существующие пользовательские bundles.
Отсутствующий ID, неполная опись, неизвестный владелец объекта или повреждённая зависимость дают отказ.

Новые plan/proof получают schema 2. Прежняя schema 1 сохраняет свой смысл и проверку точной ToolVersion.
После обновления бинарника оператор создаёт новые plan/proof.
Backup может быть новым audit-only bundle v3; обязательного резервного сайта не требуется.
Уже существующий legacy bundle также допустим как основание прежней истории; перепаковывать его для этой операции не нужно.

Plan фиксирует отдельно hash/bundle ID переносимого аудита и полный live-basis затрагиваемых reports_dir.
Audit-only пакет намеренно не содержит удаляемых site-объектов, поэтому сравнивать весь live tree напрямую с его Files нельзя.
Plan сохраняет проверенные описи выбранных публикаций, hashes/размеры кандидатов и зависимости без payload сайтов.
Verify сверяет эти описи с live state и доказывает сохранность audit state независимым restore.
Нельзя доверять произвольному пути из плана или объявлять неизвестный объект публикацией по имени.

Verify также моделирует удаление кандидатов в staging и проверяет оставшиеся run, источники, решения и независимые проверки.
Из восстановленного аудита генерируются default-сайт и выбранный исторический run; сравниваются данные, не старые bytes HTML.
Удаляемые объекты не должны быть единственным представлением данных аудита.
Временный restore/staging удаляется после проверки; постоянной копии сайта проверка не создаёт.

Порядок удаления: выбранные `._publications/<ID>.json`, затем только объекты без сохраняемых потребителей.
Объект защищают описи источников всех run и все оставшиеся публикации.
Кандидат должен принадлежать выбранной проверенной публикации; произвольные orphan objects не очищаются.
Опциональные старые viewer-копии могут стать кандидатами только после доказательства их восстановления из сохранённого отчёта и source-объектов.
Новые source-объекты, raw, JSON-отчёты и журналы не удаляются.

Apply выполняется под существующими блокировками и повторно сверяет полное live-основание перед удалением.
Прерывание оставляет валидную публикацию либо безопасный неиспользуемый объект.
Повтор допускает отсутствие только кандидатов точного plan/proof и разрешённые производные изменения.
Для legacy bundles `compareCleanupBasis` учитывает исчезновение `publication-*` site area после удаления последнего manifest выбранного ID.
Для audit-only bundle используется зафиксированная live-опись, а не список site-файлов архива.
Новая ссылка, новый run, изменившиеся bytes/CONFIG или неизвестное отсутствие требуют нового плана.
Новый постоянный журнал миграции не требуется; точный plan/proof и backup обеспечивают основание повтора.

После cleanup report JSON, данные аудита и источники продолжают читаться; default и исторический сайты генерируются повторно.
Точное прежнее оформление удалённых сайтов не является критерием восстановимости.
Эксплуатационная очистка выполняется только по отдельному решению оператора после просмотра плана.

# Однозначная привязка CONFIG и владение вложенными хранилищами

**Дата:** 2026-10-28 02:13 Europe/Berlin
**Файлы:** tool/publish.go, tool/bundle.go, tool/bundle_audit.go, tool/cleanup_publications.go, tool/publication_regression_test.go, tool/nested_publication_test.go
**Серьёзность:** high

## Проблема

Автопоиск выбирал первую из несовместимых CONFIG одной reports_dir.
Устаревшая привязка позволяла создать OUT внутри новых источников.
Родительский export повторно включал дочернее хранилище.
Audit-only validator отклонял его report.html, и безопасная очистка становилась недоступна.

## Причина

Дедупликация по reports_dir проверяла физическую принадлежность без сравнения конфигураций.
Файловый обход считал вложенные reports_dir обычными каталогами родителя.
Два отдельных metadata probes также считали дочернее хранилище родительским run.
Export и cleanup нуждались в одной явной границе владения файлами.

## Решение

Сравниваем нормализованные CONFIG через YAML, включая external.input/code_root.
Эквивалентные привязки объединяем; несовместимые отклоняем до создания OUT.
Общий nestedReportPaths исключает выбранные дочерние roots до чтения их bytes.
Его используют файловый обход, оба metadata probes, scanner публикаций и live-опись cleanup schema 3.
Scanner пропускает child root, включая вложение в ._publications, до чтения файлов.
Каталоги-предки допускаются только на пути к выбранному child; остальные неизвестные каталоги отклоняются.
Прежний обход schema 1/2 сохраняется.
Диагностика slog.Debug использует [FIX:publication] и [FIX:bundle-ownership].

## Предотвращение

При дедупликации физического ресурса проверяйте совместимость всех его привязок.
Сериализация сравнения должна сохранять поля, которые JSON намеренно исключает.
При смене границы обхода проверяйте отдельные metadata probes и всех потребителей описи.
Регрессии должны проверять оба порядка CONFIG и неизвестные файлы в дочернем root.
Матрица cleanup должна проверять каждый префикс удаления и повторный apply.

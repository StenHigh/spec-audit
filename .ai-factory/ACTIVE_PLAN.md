## Проблема и результат

Новая AI-сессия не получает короткий, однозначный маршрут подключения внешнего корпуса. Ошибки называют первый конфликт, но не объясняют требуемый выбор файлов. Это проблема одного поддерживаемого способа входа; она не определяет устройство всех аудитов.

После change сессия получает инструкцию и примеры из установленного skill. Штатный `external check` объясняет конфликт ролей и основания кода без изменения состояния.

Корпус — подготовленное дерево документов с манифестом. Манифест задаёт состав, роли и hashes файлов. AUDIT_INPUT связывает корпус с проверяемым кодом.

Launcher сначала определяет маршрут по явному CONFIG и цели пользователя:

```text
CONFIG + цель пользователя
          |
          +-- локальные источники -----> обычный аудит
          |
          +-- явный внешний вход -----> check/import -> обычный аудит
          |
          +-- сохранённый результат --> чтение истории
```

Следующая цепочка относится только к выбранному внешнему входу:

```text
Клиент: готовый корпус + манифест + профиль
                    |
Хост: CONFIG + AUDIT_INPUT
                    |
            external check
                    |
            external import
                    |
       рабочий CONFIG из ответа
                    |
    проверка индекса -> обычный аудит
```

## Обязательная универсальность

spec-audit остаётся самостоятельным инструментом аудита Markdown-спецификаций. Этот change улучшает диагностику и документацию существующего файлового контракта r1.

Обычный локальный аудит не требует `external`, AUDIT_INPUT, манифеста, портала или поставщика корпуса. Git проверяется только при явно выбранном git-basis. Snapshot-basis должен работать без Git-репозитория.

Поведение определяют CONFIG, выбранные источники и существующие контракты. Язык кода, расположение каталогов и расширения файлов не выбирают маршрут аудита автоматически. PHP SDK остаётся отдельной необязательной возможностью.

Названия проекта, мостов, каталогов и числа scope из отчёта служат только свидетельствами проблемы. Они не становятся defaults, проверками, командами, примерами или исключениями в ядре и поставляемом skill.

Внешний клиент здесь означает любую программу или оператора, которые готовят допустимый файловый вход. Ядро проверяет его без привязки к способу получения документов. Новый сетевой адаптер или система плагинов для этого change не нужны.

Диагностика описывает факт, ожидаемый контракт и допустимый следующий шаг. Она не исправляет проект, не выбирает границу scope и не принимает нормы автоматически.

| Проверяемый случай | Обязательный результат |
| --- | --- |
| Локальный CONFIG без external, доступные источники | Прежний аудит работает без внешнего комплекта и его метаданных. |
| Локальный CONFIG без external, отсутствующий источник | Ошибка объясняет путь; launcher не отправляет пользователя к обязательному import. |
| Внешний вход с git-basis | Проверка commit применяется только к выбранным code/tests. |
| Внешний вход с snapshot-basis без `.git` | Проверяется штатный digest; создание репозитория и Git-команды не требуются. |
| Допустимый внешний вход другого поставщика | Consumer использует тот же r1; специальные файлы или команды пилота не требуются. |
| Синтетические проекты с разными путями и языками кода | Общая диагностика работает без PHP runtime, SDK и условных веток по имени проекта. |
| Чтение сохранённых результатов без источников | История остаётся доступной; новый import нужен только для нового анализа, когда точные источники отсутствуют. |

Точное соответствие ролей — существующее требование, а не дефект, который следует обходить. Глобальный манифест с normative-файлами всех разделов может конфликтовать с прежними частичными CONFIG.

Change должен объяснять этот конфликт. Он не вводит переопределение ролей на уровне scope и не создаёт урезанный манифест от имени клиента.

Число scope не определяет объём переприёмки. После корректного подключения хост проверяет accepted freshness и выбирает штатные keep/relocate либо работу с кандидатом. Import сам не выполняет reconcile и не меняет ID/revision.

## Предлагаемое поведение

### 1. Обогащённый external check вместо новой doctor-команды

Сохранить `external check CONFIG AUDIT_INPUT`. Успешный stdout сохраняет прежний JSON. Отказ сохраняет ненулевой exit code и диагностику через существующий stderr.

После проверки безопасного и целостного входа вычислять полный конфликт выбора. Для каждой группы показать ожидаемые и фактические пути в стабильном порядке, по одному пути на строку. Затем показать недостающие, лишние и ошибочно выбранные в обе группы пути.

Фактическое множество ограничено файлами проверенного манифеста. Диагностика не объявляет развёрнутой описью файловой системы произвольные CONFIG-паттерны вне него.

Сообщение объясняет точное совпадение, include/exclude и возможность reference без расширения `.md`. Оно предлагает исправить выбор, но не применяет diff.

Для Git показать все доступные конфликты выбранных code/tests и их причины. Если Git не позволяет установить причину, сообщить об этом явно. Не подменять такую ошибку утверждением «ignored».

Независимые проверки ролей и Git можно объединить в одном отказе после проверки входа. Опасный путь, симлинк, неверный hash или повреждённая схема сохраняют ранний отказ.

Import использует те же проверки. Диагностика показывает различия выбора, а решение об изменении CONFIG принимает оператор. Проверка не определяет новую границу scope и не доказывает пригодность прежнего accepted-индекса.

### 2. Подсказка при недоступных источниках

В диагностике `index` и `overview` назвать CONFIG, выбранный путь, операцию и исходную причину. Не терять исходную ошибку при добавлении контекста.

При явном `external` или сохранённой привязке импорта указать соответствующий путь восстановления точного входа для нового анализа. При штатном release объяснить возможность чтения сохранённого решения без повторного подключения.

Для обычного CONFIG сообщить о проверке путей и доступности. Не добавлять обязательные manifest/import или предположение о внешнем корпусе. Явное поручение пользователя подключить внешний вход рассматривается отдельно. Не угадывать местоположение клиента и не сканировать домашний каталог.

### 3. Одна инструкция и полные примеры в поставке

Создать `docs/external-start.md` и включить его в `skillDocs`. Добавить переносимые ссылки из README, внешнего контракта и launcher. Инструкция должна работать без checkout spec-audit, пилота и памяти прежней AI-сессии.

Launcher сохраняет обычный маршрут локального аудита. Он направляет к новой инструкции только при явно выбранном внешнем входе. Создание AUDIT_INPUT не становится обязанностью каждой AI-сессии.

Инструкция внешнего входа содержит четыре шага:

1. Получить от клиента точные corpus/manifest/profile; проверить наличие исходного CONFIG и разрешённой области аудита.
2. Использовать готовый AUDIT_INPUT либо составить его из точных данных; проверить CONFIG относительно ролей и указать источник каждого поля.
3. Выполнить check; после устранения объяснённых конфликтов выполнить import и взять рабочий CONFIG из ответа.
4. Проверить состояние индекса; продолжить обычный аудит или объяснить, каких данных и решений пока нет.

В этой же инструкции дать заполненный синтетический CONFIG и полный JSON запроса r1. JSON не содержит комментариев или неописанных полей. Git-пример объясняет HEAD, выбранные bytes и ignored; snapshot-пример использует точный алгоритм и проверяемый digest-вектор.

Оба примера используют вымышленные нейтральные имена. Snapshot-пример работает без `.git`. Подготовка примеров не требует PHP, проектного bootstrap, SDK или специфичного producer.

Freshness неизвестного живого источника остаётся unknown; ссылки решений клиента остаются null, если клиент их не предоставил. Пример не создаёт принятие корпуса или соответствие норм.

Отдельно объяснить исходный CONFIG и рабочий CONFIG, returned import; роли файлов и границу scope; check/import/release и версии result/bundle. Не включать STORE, PHP-мост и команды конкретного поставщика.

## Критерии приёмки

| Сценарий | Требуемый результат |
| --- | --- |
| Локальный аудит без external на нейтральном проекте | Прежний цикл доступен без manifest, AUDIT_INPUT, поставщика корпуса и PHP runtime. |
| Snapshot-basis в каталоге без `.git` | Check/import проходят без создания репозитория и обращения к Git; неверный digest отвергается. |
| Другие нейтральные пути и язык code/tests, допустимое происхождение другого типа | Те же правила работают без специальных веток по пути, расширению или поставщику. |
| Несколько ошибок выбора, reference `.json`, выбранный archive | Первый вызов check показывает полный role-конфликт и правило совпадения; состояние не меняется. |
| Одновременно role-конфликт и безопасно проверяемые Git-конфликты | Один отказ сообщает оба класса; успех не подделывается. |
| Ignored-файл выбран; обычный git status пуст | Ошибка объясняет отсутствие файла в commit. Невыбранный ignored не вызывает отказ. |
| Повреждённый manifest/hash или симлинк | Прежний строгий ранний отказ; import ничего не публикует. |
| Источник отсутствует в обычном CONFIG | Сообщение называет путь и причину; оно не утверждает наличие внешнего корпуса и не требует import. |
| External release или недоступный checkout | Сохранённые выводы доступны; saved/unchecked согласованы с §80; новый анализ требует точных входов. |
| Чистый независимый каталог с установленным skill | Все необходимые материалы доступны локально. Оба примера r1 проходят штатный check после подготовки нейтрального fixture. |
| Новая AI-сессия получает бинарник, установленный skill и готовый синтетический вход | Сессия находит маршрут, объясняет намеренные конфликты, выполняет check/import и использует возвращённый CONFIG без чтения пилота. |
| Новая AI-сессия получает обычный локальный CONFIG | Сессия выбирает обычный аудит и не создаёт внешний комплект. |
| Готового входа или сведений клиента нет | Сессия точно называет недостающие данные; она не ищет STORE, не запускает fixture-producer и не выдумывает freshness. |
| Старый частичный scope конфликтует с глобальными ролями | Сессия объясняет несовместимость и останавливает миграцию; она не переписывает манифест или ledger. |

Для контроля новой AI-сессии фиксировать обращения к документации, повторные неудачные команды и общий путь. Детерминированный Go-тест не заменяет этот контроль. Численный выигрыш относительно отчёта нельзя обещать без сопоставимого измерения.

После изменений Go выполнить адресные регрессии, `go test ./tool`, `go vet ./tool` и сборку. Проверить прежние frozen-контракты и отсутствие изменений raw/ledger. Нативные платформы и реальную поставку клиента заявлять только после отдельного исполнения.

Change не проходит приёмку, если новый маршрут требует сведения пилота, внешний сервис, Git или PHP вне явно выбранной возможности. Отдельная успешная проверка на пилоте не заменяет синтетические проверки универсальности.

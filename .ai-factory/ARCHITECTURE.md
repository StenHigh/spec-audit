# Архитектура spec-audit

## Подход

Локальный Go CLI, один `package main` в `tool/` плюс data-only embed-пакет `dist` в корне ([embed.go](../embed.go)), логическое разделение по ответственности файлов. Нет отдельных сервисов, базы данных или принудительных package-слоёв. Это описание существующей структуры для продолжения разработки, не план её переписывания в Clean Architecture.

Основная граница — между детерминированной механикой бинарника, смысловым суждением AI-хоста и явно разрешённым runtime проверяемого проекта. Такой разрез сохраняет переносимый бинарник и позволяет развивать языковые SDK без бизнес-знаний в ядре. Нормативный контракт — [tool-spec](../docs/tool-spec.md).

## Где находится логика

| Файлы | Ответственность |
| --- | --- |
| [tool/main.go](../tool/main.go) | CLI, CONFIG, snapshot, задания/результаты, проверки источников (в т.ч. `validate` без записи), журнал версий `tool-versions.json` и безопасная запись состояния |
| [tool/specs.go](../tool/specs.go) | Markdown и объявленные требования |
| [tool/accepted.go](../tool/accepted.go), [tool/legacy.go](../tool/legacy.go) | Принятие кандидатов, ID/редакции, reconcile (единый view для чтения и apply) и проверка извлечения |
| [tool/review.go](../tool/review.go) | Согласование хоста, привязка к текущим результатам и сохранение истории |
| [tool/runtime.go](../tool/runtime.go) | Контролируемый запуск процессов, timeout, результаты тестов и receipts |
| [tool/php.go](../tool/php.go), [tool/sdk.php](../tool/sdk.php), [tool/sdk-typed.php](../tool/sdk-typed.php) | Docker-boundary; `php-facts` (syntax-only) и `php-typed` (PHPStan/Larastan-экспортёр, neon-обёртка, проверка envelope `sdk/3` и основания анализа) |
| [tool/report.go](../tool/report.go), [tool/report.html](../tool/report.html) | JSON/HTML, связи нормы–код–assertion, подсказки SDK с происхождением, текущий статус, навигация и настройки |
| [tool/update.go](../tool/update.go) | `version`, проверка подписанного release-manifest и `update` с атомарной заменой собственного файла |
| [tool/skill.go](../tool/skill.go), [embed.go](../embed.go) | Материализация встроенного launcher, receipt, `skill install|update` внутри `os.Root(DIR)`; embed — данные без логики |
| [scripts/install.sh](../scripts/install.sh), [.github/workflows/release.yml](../.github/workflows/release.yml) | Первичная установка и подписанный релиз с нативной квалификацией платформ |
| `tool/*_test.go`, [acceptance/](../acceptance/) | Регрессии, синтетические контроли и неизменяемые эталоны |
| [skills/spec-audit/](../skills/spec-audit/) | Поставляемый audit-launcher и протокол независимой роли |

Исторические пробы находятся в `prototypes/`; приватные snapshot/raw/report — в игнорируемой `.local/`. AI Factory и его development-skills не входят в runtime-протокол и поставку audit-launcher.

## Поток и границы зависимостей

1. CONFIG выбирает источники и область записи. Ядро строит проверяемый snapshot и declared/accepted-набор; accepted требует явного решения хоста.
2. `prepare/tasks` формируют ограниченные задания. Хост передаёт их независимым mapper/redteam, не подмешивая gold и старые вердикты; `submit` валидирует ответы и сохраняет raw.
3. Разрешённый `test` даёт отдельный receipt. `review` сохраняет согласование хоста поверх исходных результатов; `report` представляет данные, но не создаёт новый смысловой вердикт.

- Поставка — отдельная граница: `update` пишет только собственный исполняемый файл, `skill install|update` — только `DIR/.spec-audit/skill` и две host-ссылки; это явные операции владельца, не часть аудита (§18).
- AI-хост вызывает CLI по протоколу; бинарник не вызывает модель и не управляет трекером. Аудит задачи трекера сейчас организует хост, не GitLab-клиент в ядре.
- Факты SDK и результат процесса — свидетельства, не автоматическая сертификация требования. HTML потребляет сохранённые данные и не выполняет аудит самостоятельно.
- PHP допускается только через проверенный runtime; SDK использует зависимости проекта, а не требует PHP/Node на хосте. Условия исполнения — в [RULES.md](RULES.md).
- Внутри одного Go-пакета нет компиляторного запрета зависимостей между файлами. Сохраняй ответственность существующих helpers; не объявляй отсутствующие границы уже обеспеченными.

## Реализовано ограниченно: PHP/Laravel SDK

`php-facts` по-прежнему сохраняет отдельный `syntax_only` JSON. `php-typed` ([контракт](../docs/php-sdk-contract.md)) запускает PHPStan (с Larastan для профиля `laravel`) в проверенном контейнере: экспортёр и neon-обёртка записываются в уникальный контейнерный `/tmp`, классы грузятся через `--autoload-file`, результат приходит одним сообщением PHPStan и проверяется против manifest (цитаты по строкам, инварианты resolution↔targets, основание анализа в границах snapshot или `vendor/`). Сырой envelope хранится артефактом; запись в `State.SDK` делает прежний review outdated; `TaskBatch.sdk` отдаёт записи хосту, `report` показывает подсказки отдельно от связей и метрик.

Профиль `laravel` исполняет bootstrap приложения под fail-fast окружением (`laravelIsolationEnv`); сеть контейнера инструмент не изолирует. Приёмка — синтетические примеры в `acceptance/php-sdk/`; фикстуры `tool/testdata/typed-*.json` пинятся к экспортёру. Сравнение с SDK и без него на пилоте (§17.2 п.4) выполнено один раз с нейтральным результатом — доказанного улучшения нет. PHPStan-проба в `prototypes/core/` остаётся историей.

## Изменения кода

Следуй фактической структуре; не реорганизуй несвязанный код ради шаблона архитектуры. Например, исправление публикации состояния делается в общем `atomicWrite` с проверками его потребителей; правила исполнения процесса — в runtime-boundary, а не дублируются в SDK и отчёте.

Не добавляй второе ядро, registry плагинов «на будущее», прямой host PHP, бизнес-исключения или автоматический PASS из графа вызовов. Соглашения кода и тестов — [rules/base.md](rules/base.md).

# Рабочий контекст spec-audit

`CLAUDE.md` — симлинк на этот файл. Правь `AGENTS.md`, не заменяй ссылку копией. Отвечай пользователю по-русски.

## Назначение и граница

spec-audit — самостоятельный, не привязанный к бизнес-проекту инструмент аудита Markdown-спецификаций по коду и assertions тестов. SMSPlace — текущий пилот для обкатки, не архитектурная зависимость и не предел назначения инструмента.

Ядро, общий skill и протоколы не должны содержать бизнес-норм, путей, ID задач или специальных исключений пилота. Источники и ограничения приходят из CONFIG и выбранной спецификации; языковые особенности — из явно ограниченного SDK/runtime. Полезные уроки пилота закрепляй независимыми синтетическими регрессиями. Не строй систему плагинов «для всех языков» до конкретной потребности.

Инструмент только аудирует. Он не исправляет проверяемый код/ТЗ, не управляет задачами и не заменяет workflow разработки. AI-хост — существующая сессия: независимые роли делают смысловой анализ, Go-бинарник валидирует данные, хранит состояние и строит отчёт. Модельных API/ключей в бинарнике нет.

2. [Спецификация инструмента](docs/tool-spec.md) — источник норм: цели/границы и приёмка §12, текущие расширения §13–16, контракт CLI §1–10; следующий функциональный этап PHP/Laravel SDK — §17. Сначала уточняй изменяемое требование и проверку, затем меняй реализацию.
3. Остальное — по задаче из карты ниже. Не загружай всю историю `.local/`, прототипы или документацию пилота по умолчанию.

Явные решения владельца имеют приоритет; конфликт спецификаций обозначай, не разрешай его молча кодом. README и планы не заменяют требования. Необоснованные требования и неизвестность нельзя превращать в PASS.

## Реализация и проверки

- Go и версии зависимостей — в [go.mod](go.mod): Goldmark для Markdown, YAML для CONFIG. Новая зависимость требует конкретной необходимости. Для детерминированных команд готового бинарника не нужны Node/Python/Go; проектные тесты и необязательный UI dev-check требуют своей среды, описанной в README.
- Из корня инструмента на хосте: `go test ./tool`, `go vet ./tool`, `CGO_ENABLED=0 go build -o bin/spec-audit ./tool`. Изменения HTML проверяй также описанным в README синтетическим UI-check, если среда доступна; не устанавливай её молча.
- PHP SDK сейчас `syntax_only`; PHPStan/Larastan не интегрированы в рабочее ядро. PHP и PHP-тесты запускаются только с отдельным разрешением и в проверенном Docker-контейнере проекта, без host fallback. Прочие проектные тесты тоже требуют разрешения и подходящего runtime. Go-тесты самого инструмента не требуют бизнес-проекта.
- Запланированный PHP/Laravel SDK — адаптер проекта, не PHP-ядро: PHPStan для типов/символов, Larastan для Laravel, данные для подбора кода/тестов и навигации. `php-facts` пока пишет отдельный syntax-only JSON, не обогащает Task/HTML автоматически. Проба `prototypes/core/PublicCallProbeRule.php` — отправная точка исследования, не готовая интеграция. Довести цепочку по §17, не оставлять SDK вычеркнутым из плана ради универсальности.
- Поддержка macOS/Linux не означает, что каждая сборка исполнена на каждой архитектуре. В отчёте отличай build от запуска, статические assertions от receipt теста, частичный scope от всего корпуса. Accepted-индекс ограничен 64 активными требованиями.

## Сохранность и продолжение

- Не переписывай frozen §1–10 tool-spec, контракты accepted-index/legacy-extraction, `acceptance` gold/хэши и старые raw ради зелёного результата. Новая семантика — обоснованная редакция/расширение и отдельный контроль; результаты прежних прогонов остаются историей.
- Не переноси пилотные данные, абсолютные локальные пути, секреты и отчёты в общие инструкции или Git. Исторические упоминания пилота не становятся defaults инструмента.
- Аудит пишет только в разрешённую CONFIG рабочую область; установка skill/конфига — отдельная операция. Нельзя автоматически изменять Git, трекер задач, CI или прежние audit-инструменты проверяемого проекта. Коммит и push — по запросу пользователя.
- При завершении этапа обновляй состояние/следующий шаг в README и затронутый контракт. Не создавай новые handoff-дневники и дубли планов. Спецификация инструмента и спецификация применения к бизнес-проекту остаются разными документами.
- ISO-ready — направление подготовки документации, не заявление соответствия ISO. Общая точность, экономия времени/денег и полнота всего ТЗ пока не доказаны.

# Принятие требований из обычного Markdown

Версия: 1. Статус: ограниченное расширение v0.1, спецификация подготовлена до кода. Владелец — StenHigh. Формальное соответствие ISO не заявляется; основания структуры — в [основной спецификации](tool-spec.md#11-стандарты-и-открытые-решения).

## Назначение и границы

Ошибка при чтении ТЗ заставляет аудит проверять не ту обязанность. Поэтому найденный фрагмент сначала является кандидатом. Хост проверяет его смысл и явно решает, принять его, отклонить или оставить нерешённым. Инструмент хранит это решение и происхождение, но не доказывает его правильность.

Расширение добавляет принятый индекс к существующим scope → mapper/redteam → assertions → JSON/HTML. Оно не добавляет второй аудит, модельный API, сервер, БД, graph, автоматические issues или миграцию SMSPlace. Исходное ТЗ не переписывается.

## Ответственность и идентичность

Автор ТЗ определяет норму. Извлекатель предлагает кандидатов по [протоколу legacy-контроля](legacy-extraction.md#контракт-извлечения). Хост проверяет условия, исключения, неопределённость и все определяющие фрагменты; reviewer может помочь, но согласие агентов не является машинным доказательством. Бинарник проверяет структуру и целостность решения.

ID `C001` локален конкретному raw-ответу. Бинарник выдаёт постоянные `REQ-AI-001`, `REQ-AI-002`, … в порядке операций/targets; однажды выданный номер не используется снова. Смысловая редакция начинается с 1. Принятое содержание — title, condition, statement, verification, exceptions, clarity, unresolved. Content hash не включает ID, координаты или цитаты.

`verification` — предложенный хостом способ проверки, не новая обязанность продукта. Принятие ambiguous разрешено: известная обязанность и вопросы остаются в задании; роль не может объявить её clear без новой принятой редакции.

## Контракт поведения

1. Только успешный `reconcile CONFIG RAW DECISION` меняет принятый индекс. Весь raw, каждое решение и причины сохраняются без правки. Каждый кандидат получает ровно одну операцию, каждый прежний active ID — ровно одно явное продолжение/снятие. Пропуск не означает reject или retire. Пакет применяется целиком либо не применяется.
2. Принятие переносит все смысловые поля кандидата и все цитаты; title/verification явно задаёт хост. Reject/defer не создают requirement ID и остаются видны в истории и отчёте. Отклонённый ненормативный пример не является product gap. Неизвестность нельзя скрыть пропуском кандидата.
3. Rebind сохраняет ID, revision и content hash только при побайтово одинаковом принятом содержании. Координаты/цитаты могут меняться; хост отвечает за эквивалентность контекста. Даже эквивалентное перефразирование принятого содержания требует revise либо сохранения прежней принятой формулировки. Бинарник не вычисляет смысловую эквивалентность.
4. Revise сохраняет ID, увеличивает revision ровно на 1 и требует отличающегося content hash. Старое содержание и происхождение доступны через журнал. Любое изменение входного snapshot или принятого журнала делает прежний run stale; старые assessments/receipts автоматически не переносятся, даже при rebind.
5. Split заменяет одну active-норму минимум двумя новыми ID; merge заменяет минимум две одним новым ID. Предшественники становятся retired; каждый потомок хранит parents. Retire явно снимает одну active-норму с обязательной причиной. Исчезновение текста само не отменяет норму. Восстановление retired ID и исправление ошибочной идентичности отдельной операцией пока не поддерживаются; нужен новый ID и объяснение.
6. Решение привязано к raw SHA-256 и base_index. Новый пакет проверяется по всему текущему выбранному набору specs, его хэшам и точным цитатам, повторно перед записью. Изменение вводной/другого файла тоже делает пакет stale. Старый base_index отклоняется. Точный повтор уже принятого decision_id и тех же байтов — duplicate без записи; повтор ID с другими байтами — конфликт. Исторический duplicate не подтверждает свежесть исходников.
7. Один файловый lock сериализует записи индекса; compare-and-swap по base_index исключает потерянные обновления. После полного контроля размеров журнал публикуется атомарно. Отказ оставляет прежний индекс неизменным; возможен только служебный lock. Это не ОС-песочница, не криптографическая подпись автора и не защита от доверенного локального администратора.
8. Только active-набор поступает в прежнее распределение scope. ID и revision зафиксированы в manifest/task. Spec-цитата assessment должна входить в один из принятых диапазонов, а не просто существовать в ТЗ. Для accepted-профиля HTML/JSON показывают принятое содержание, все источники, revision и историю решений; база полноты — accepted requirements only, semantic completeness proven — false. Delivery complete не означает соответствие или рассмотрение всех обязанностей Markdown.

## YAML и команды

В CONFIG добавляется `index_mode: accepted`. Отсутствие поля сохраняет прежний declared-профиль и идентичность его snapshot; явное смешивание профилей не поддерживается. Все остальные source/report/runtime/scope guards остаются прежними. При принятом режиме Markdown читается как источник, REQ-заголовки не подмешиваются автоматически.

```bash
spec-audit reconcile /absolute/path/audit.yaml
# Хост извлекает кандидатов по source_set и сохраняет raw/решение в reports_dir.
spec-audit reconcile /absolute/path/audit.yaml /absolute/path/raw.json /absolute/path/decision.json
spec-audit index /absolute/path/audit.yaml
spec-audit prepare /absolute/path/audit.yaml accepted-first
spec-audit tasks /absolute/path/audit.yaml accepted-first
spec-audit report /absolute/path/audit.yaml accepted-first
```

Читающий reconcile не создаёт файлов: возвращает base_index, текущий source_set, active/retired records, историю и freshness. При недоступном источнике история остаётся доступной с unavailable; это не разрешает применение решения. До первой приёмки index/prepare отказывают. После дрейфа index/prepare отказывают до свежей полной приёмки; status/report прежнего run доступны как история.

В reports_dir хранится один `._accepted-index.json`: version=1 и commits с точными строками raw/decision. Его head вычисляется последовательно из прежнего head, SHA-256 raw и SHA-256 decision; пустой head — SHA-256 строки `accepted-index/1`. Это ревизия решений, а не доказательство правильности. История восстанавливается детерминированно; отдельной БД и копии исходного дерева нет.

## JSON решения

Все поля обязательны, регистр точный; неизвестные/повторные ключи, null и несколько документов запрещены. RAW сохраняет формат legacy-контроля: пути относительно project_root, source_set содержит весь выбранный набор specs, до 64 кандидатов/16 цитат на кандидат/4 MiB. Ни пустой ответ, ни согласие двух извлечений не доказывают полноту.

```json
{
  "version": 1,
  "decision_id": "accept-001",
  "base_index": "head из читающего reconcile",
  "raw_sha256": "SHA-256 точных байтов raw.json",
  "operations": [{
    "action": "accept",
    "previous": [],
    "targets": [{"candidate": "C001", "title": "Название нормы", "verification": "Как проверить известное требование"}],
    "reason": "Почему кандидат соответствует нормативным источникам"
  }]
}
```

| action | previous (только прежние active IDs) | targets |
| --- | --- | --- |
| accept | пусто | один кандидат, непустые title/verification |
| rebind / revise | один ID | один кандидат, непустые title/verification |
| split | один ID | 2–64 кандидата, у каждого title/verification |
| merge | 2–64 ID | один кандидат, title/verification |
| retire | один ID | пусто |
| reject / defer | пусто | один кандидат, title и verification — пустые строки |

Каждый пакет полностью учитывает текущие кандидаты и прежние active ID. Для неизменённой нормы нужен rebind; автоматическое сохранение старой нормы по сходству строк запрещено. Несколько извлечений хост рассматривает по отдельности; C001 разных raw не является одним объектом.

Ограничения среза: до 64 active-норм в одном полностью согласуемом пакете, до 128 операций и 128 принятых пакетов, журнал до 32 MiB; DECISION до 4 MiB. Общие лимиты файлов/manifest/state/scope продолжают действовать. По достижении предела нужен отдельно спроектированный следующий срез, не удаление истории или молчаливое усечение. Частичная приёмка большого корпуса и автоматический semantic cache здесь не реализуются.

## Приёмка

[12 независимых сценариев](../acceptance/accepted-index.json) фиксируются до реализации отдельно от прежних baseline. Проверяются принятие/reject/defer, relocation, revision, split/merge/retire, stale, replay, конкуренция, несколько фрагментов/файлов и существующий audit pipeline. Точные цитаты проверяет код; сохранение обязательств — независимый смысловой проход. Самоприменение к этой спецификации не заменяет внешние примеры и не доказывает точность на всём SMSPlace.

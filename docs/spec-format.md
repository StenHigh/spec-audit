# Единый формат ТЗ для работы с ИИ

Редакция 0.1, 2026-09-25. Стандарт записи спецификации требований (ТЗ), которую читают и проверяют ИИ-агенты: планирование, реализация, верификация, ревью и аудит spec-audit. Основа — характеристики хорошего требования ISO/IEC/IEEE 29148 (необходимое, однозначное, атомарное, проверяемое, трассируемое) и шаблоны формулировки EARS; ISO не задаёт синтаксиса, поэтому синтаксис — профиль Markdown spec-audit. Это подготовка к стандарту, а не заявление о соответствии. Формат машинно проверяется профилем declared spec-audit ([tool-spec §4](tool-spec.md#4-профиль-markdown), §67, §68): `spec-audit index CONFIG` отклоняет нарушение формы блока.

## 1. Главное правило

**Обязанность существует только в блоке нормы.** Текст вне блоков — пояснение: он помогает понять, но ничего не требует, не проверяется аудитом и не может быть основанием для реализации. Если при чтении пояснения видна обязанность, которой нет в блоке, это дефект ТЗ: её переносят в блок или удаляют.

## 2. Документы

| Вид | Что содержит | Формат |
|---|---|---|
| Требования (по доменам) | что система обязана делать | блоки норм, вопросов и определений (§3) |
| Глоссарий | термины и сквозные правила | блоки определений и норм (§3.3) |
| Протоколы и контракты | внешние API, форматы сообщений | блоки норм; схемы и примеры — в теле блока |
| Проектирование реализации | как устроено решение | обычный Markdown с разделами по модулям; ссылается на ID норм, сам норм не вводит |
| Внешние документы (поставщиков, стандарты) | чужие контракты | как есть, подключаются группой `references` |

Уточнения к правилам (FAQ) — не отдельный вид: нормативный ответ вливается в блок нормы, открытый — становится блоком вопроса. Производные отчёты (покрытие якорей, матрицы) в ТЗ не хранятся — их строит инструмент.

## 3. Блоки

Блок — заголовок третьего уровня с ID и названием, за ним поля — каждое на своей строке, в одном абзаце, без переноса. Пустая строка отделяет тело блока: таблицы, списки, схемы, примеры. Блок заканчивается следующим заголовком уровня 1–3. ID не меняется при перемещении блока и никогда не переиспользуется.

ID: `<ВИД>-<ПРОСТРАНСТВО>-<НОМЕР>`, пространство — заглавные латинские буквы/цифры, одно на файл (`FIN`, `WH`), номер — не менее трёх цифр.

### 3.1 Норма `REQ`

```markdown
### REQ-FIN-046 — Блокировка кошельков

Условие: Когда операция изменяет один или несколько кошельков, …
Требование: система должна блокировать изменяемый кошелёк `SELECT … FOR UPDATE`, а несколько кошельков — в стабильном порядке.
Проверка: инспекция — блокировка и порядок в сервисе операций.
```

- **Условие** — когда норма действует; записывается по шаблону EARS (§3.1.1).
- **Требование** — один наблюдаемый результат: «система должна …» / «система не должна …». Одна обязанность на блок; «и» между разными результатами — признак, что блок надо разделить. Исключения и границы — в этой же строке, не в пояснении.
- **Проверка** — метод (тест, инспекция, анализ, демонстрация) и наблюдаемый критерий. Проверка не добавляет условий, запретов и механизмов, которых нет в Требовании: если критерий требует больше нормы, неправ критерий.
- **Тело** — то, на что Требование ссылается («поля по таблице ниже», «формат — схема ниже»): таблица структуры, перечень значений, схема сообщения. Одна норма с таблицей вместо нормы на каждое поле. Пример в теле — в блоке кода с подписью «Пример (не норма)».

#### 3.1.1 Шаблоны EARS

Условие и Требование вместе образуют одну фразу по шаблону EARS (Easy Approach to Requirements Syntax). Шаблон выбирают по виду условия; ключевое слово — первое слово поля Условие.

| Шаблон | Условие | Требование | Пример |
|---|---|---|---|
| Всегда | `Всегда.` | система должна … | Всегда. / система должна вести кошельки только в USD. |
| Событие | `Когда <событие>, …` | система должна … | Когда попытка получила ответ `2xx`, … / система должна перевести запись в `success`. |
| Состояние | `Пока <состояние>, …` | система должна … | Пока allocation активна для доставки, … / система должна доставлять ей SMS. |
| Нежелательное | `Если <сбой или нежелательное событие>, то …` | система должна … | Если локальный commit не состоялся после успешного действия поставщика, то … / система должна сохранить supplier-cost fact. |
| Опция | `При наличии <функции/возможности>, …` | система должна … | При наличии у источника привязки по supplier-активации, … / система должна резолвить allocation по привязке. |
| Составной | ключевые слова в порядке `Пока …, когда …` (или `При наличии …, когда …`) | система должна … | Пока allocation активна, когда пришла повторная SMS, … / система должна доставить её без смены `fulfilled_at`. |

Правила: одно событие в «Когда»; «Если … то» — только для отказов, ошибок и нежелательного поведения (нормальный ход — «Когда»); «Пока» — длящееся состояние, а не момент; «Всегда» — норма без условия. Несколько событий или состояний через «или» — признак, что норм несколько, либо условие надо назвать одним термином (определение `DEF`).

Слова силы: «должна» — обязанность; «не должна» — запрет; «может» — разрешение, не обязанность. «Обычно», «как правило», «желательно», «например» в Требовании запрещены: либо норма, либо вопрос.

### 3.2 Вопрос `Q`

```markdown
### Q-FIN-002 — Что суммирует open_contingent_supplier_payout

Вопрос: какая величина суммируется по open contingent allocations — `agreed_supplier_payout_amount`?
Нормы: REQ-FIN-012
```

Вопрос — то, что текст оставляет открытым. Он живёт в ТЗ, пока владелец не ответит правкой текста; ответ превращает вопрос в норму или уточняет существующую, после чего блок вопроса удаляют. Вопросы видны заказчику отдельным разделом карты корпуса (tool-spec §68). Автор перевода или правки не решает неясность за владельца: неясное — вопрос, а не догадка в норме.

### 3.3 Определение `DEF`

```markdown
### DEF-GLO-073 — Нормализованный текст SMS

Определение: текст SMS после trim, замены переносов строк пробелами и схлопывания повторных пробелов.
```

Определение вводит термин и ничего не требует. Правило, записанное в глоссарии, — норма (`REQ-GLO-…`), а не определение. Нормы ссылаются на определение по ID. Блоки `DEF` инструментом пока не разбираются (текст вне REQ/Q), это соглашение формата.

## 4. Структура файла требований

```markdown
# Finance

Пространство ID: FIN. Назначение раздела — одна-две фразы (пояснение).

## §1.7.6A Supplier Cost Operation

Пояснение: зачем сущность и где участвует (не норма).

### REQ-FIN-022 — Поля записи
…
```

- Заголовки второго уровня сохраняют номер раздела (`§1.7.6A`): на него ссылаются другие документы и код.
- Сущность: пояснение назначения, затем нормы — структура (одна норма с таблицей), связи, инварианты — по норме на инвариант.
- Процесс: пояснение участников и потока, затем нормы — по норме на наблюдаемый результат шага или ветви; сам нумерованный поток остаётся пояснением.
- Перечисления и машины состояний: норма с таблицей значений или переходов в теле.
- Нефункциональные требования: нормы с измеримым критерием в Проверке.
- Открытые вопросы — блоки `Q` в конце раздела, к которому относятся.

## 5. Ссылки и трассировка

- На норму — по ID (`REQ-FIN-046`), на раздел — по номеру (`§1.8.3`), на определение — по ID (`DEF-GLO-073`). Ссылка на строку файла не используется: строки меняются.
- Код и тесты ссылаются на норму её ID. Хэш содержания нормы (content hash: ID, название, три поля) вычисляет инструмент — правка любого поля делает прежние свидетельства устаревшими.
- Норма, опирающаяся на документ другого вида (протокол, внешний контракт), называет его раздел в Требовании или теле; сам документ подключается в CONFIG группой `references` (tool-spec §67).

## 6. Изменение ТЗ

- Новая обязанность — новый блок с новым номером; изменение смысла — правка полей блока (ID сохраняется); отмена — удаление блока, номер не переиспользуется.

## 7. Перевод существующего ТЗ: смысл не меняется

Перевод — перенос с доказательством, а не переписывание. Цель одна: та же совокупность обязанностей в новой форме. Файл считается переведённым, только когда пройдены все ворота ниже.

1. **Только форма.** В изменении перевода нет смысловых правок: ни ответов на вопросы, ни исправлений, ни «улучшений». Замеченная ошибка ТЗ становится вопросом `Q`; смысл меняется отдельным изменением после перевода.
2. **Опись «до».** До перевода фиксируется независимый от переводчика список обязанностей файла: принятые нормы аудита (accepted-индекс) и записи индекса трассировки проекта с их цитатами. Перевод без описи не начинается.
3. **Полное покрытие.** Файл соответствия «прежний ID → новые ID» перечисляет каждую запись описи; запись без нового ID — потеря и блокирует перевод. Новый блок без прежнего ID допустим только как разделение прежней обязанности и называет её.
4. **Неясное — вопросом.** Всё, что в описи было неоднозначным или нерешённым, становится блоком `Q` со ссылкой на нормы; догадка в норме — дефект перевода.
5. **Независимая сверка.** Агент в свежем контексте, не видевший рассуждений переводчика, сравнивает оригинал, справочники, опись и перевод и строит своё соответствие: потери, расширения, сужения, молчаливые решения, нормы без опоры. Все находки закрыты правкой перевода или обоснованным отклонением. Опыт: 16 находок на 58 норм, чаще всего в поле «Проверка», — без этого шага ошибки остаются.
6. **Поведенческая сверка.** Полный аудит нового текста на том же коде, что последнее решение по старому: вердикты соответствующих норм совпадают. Каждое расхождение (новое противоречие, пропавшее противоречие, другой класс GAP) объяснено разницей формулировки или признано ошибкой перевода и исправлено.
7. **Решение владельца.** Владелец ТЗ принимает изменение по трём артефактам — соответствию, отчёту сверки и сравнению аудита, — а не по чтению всего diff.
8. **Идентичность.** Номера разделов (`§N.N`) и существующие якоря сохраняются как ID; ссылки из кода, тестов и других документов перепривязываются в том же изменении, гейт трассировки проекта зелёный.

## 8. Деление файлов

Файл — одна предметная область или один вид документа (§2). Делят файл только по смыслу, не по размеру:

- файл смешивает виды содержания (глоссарий, сквозные правила, роли, нефункциональные требования, перечисления, производные отчёты) — каждый вид в свой файл;
- в файле несколько независимых предметных областей, которые меняются и проверяются отдельно.

Большой файл одной области не делят: ID и поиск по ним делают размер несущественным для агента, а деление по размеру разрывает контекст нормы. Производные отчёты (покрытие якорей, матрицы) удаляются, а не переносятся — их строит инструмент; удаление фиксируется в соответствии как «производное, не обязанность».

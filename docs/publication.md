# Публикация, хранение и перенос результатов

Это руководство описывает действующее поведение начиная с v0.1.82.
Сайт генерируется из сохранённых отчётов; повторный AI-аудит для этого не нужен.
Нормативный контракт — [§83 спецификации](tool-spec.md#83-публикация-из-отчётов-без-хранения-сайтов).

Run — один сохранённый запуск аудита; RUN_ID обозначает его имя.
CONFIG — YAML-файл настроек области; reports_dir — каталог её сохранённых данных.
OUT — новый каталог создаваемого сайта.

```text
источники -> аудит -> сохранённые отчёты и свидетельства
                                  |
                    выбор областей и run -> новый сайт
                                  |
                       audit-only bundle -> restore
                                                |
                                         новый сайт
```

## Что сохраняется

| Данные | `archive` | `citations` |
| --- | --- | --- |
| Нормы, решения, цитаты, raw и история | Сохраняются | Сохраняются |
| Полные исходники выбранного среза | Сохраняются | Не архивируются |
| Временные копии внешнего импорта | Остаются | Освобождаются штатным `external release` |
| Архивы новых сайтов внутри reports_dir | Не создаются | Не создаются |

Режим `source_retention: citations` выбирается в исходном CONFIG для нового отдельного reports_dir.
Существующую область нельзя переключить удалением объектов или правкой журналов.
Archive и citations могут находиться на одном сайте; каждая область сохраняет свою политику.

Каталог OUT содержит готовый сайт для размещения.
Управляйте размещением и удалением OUT отдельно от хранения аудита.
Cleanup не удаляет произвольные каталоги хостинга.

## Последние результаты всех областей

В примерах `./audit-state` содержит уже сохранённые аудиты.
Замените пути и ID значениями своей установки.
Каждый OUT должен отсутствовать и не пересекаться с reports_dir и выбранными источниками.
Для external/citations запрещено также пересечение с project_root.
Локальный archive допускает OUT внутри project_root вне выбранных путей источников.

```sh
spec-audit publish ./site-latest-001 --from ./audit-state
```

Без `--from` поиск начинается в текущем каталоге.
Явные CONFIG ограничивают подборку:

```sh
spec-audit publish ./site-selected-001 ./audit-state/area-a/config.yaml ./audit-state/area-b/config.yaml
```

По каждой области выбирается последний полный аудит с проверенным сохранённым report.
Порядок задают время prepare и RUN_ID при равенстве; spec_version не сортируется.
Более новый незавершённый run не вытесняет прежний полный результат.
Причина ожидания видна в `latest.publication_pending`; область без полного результата показана как незавершённая.

Внешнему аудиту нужна независимая `review-check` с `conclusion: confirmed` по точному решению.
Повреждённые данные вызывают отказ, а не скрытый выбор старого результата.
Несовместимые CONFIG одной reports_dir также вызывают отказ.

Команда создаёт `index.html`, `overview.json` и ресурсы выбранных отчётов.
HTML и source-viewers генерируются заново; прежний report.html не требуется.
Сохранённые report JSON, raw и решения не переписываются.

## Отдельный исторический run

```sh
spec-audit publish ./site-history-001 --run run-001 ./audit-state/area-a/config.yaml
```

`--run` принимает ровно один CONFIG и несовместим с `--from`.
Отсутствующий или неполный run вызывает отказ без перехода к latest.
Повреждённые metadata других run не блокируют исправный выбранный аудит.
Исторический выбор действует только на этот вызов; следующий обычный publish снова выбирает latest.

Историческая публикация показывает `report_basis: historical_publication` и актуальность `unchecked`.
Она сохраняет выбранные нормы, GAP, цитаты, дату и редакцию спецификации.
Общий сайт не создаёт HTML всех исторических run автоматически.

## Редакция спецификации и актуальность кода

Каждая область показывает собственную подпись «Проверено на редакции спецификации», run и дату аудита.
Например, область A может быть проверена на R2, а область B — на R1.
Дата генерации сайта не обновляет дату аудита.
При отсутствии именованной редакции сайт явно сообщает об этом.

Для сравнения с выбранной редакцией создайте `corpus-control.json`:

```json
{"schema_version":1,"controls":[{"project":"example-project","corpus":"example-corpus","line":null,"spec_version":"R2"}]}
```

Значения project/corpus/line должны соответствовать вашему внешнему корпусу.
Версии сравниваются только на равенство; инструмент не выбирает контроль автоматически.

```sh
spec-audit publish ./site-control-001 --from ./audit-state --corpus-control ./corpus-control.json
```

| Метка | Значение |
| --- | --- |
| `checked` | Область проверена на выбранной редакции |
| `not_checked` | Область проверена на другой редакции |
| `incomparable` | Нет совместимого контекста, версии или полного решения |

Передайте контроль повторно при следующей публикации, включая публикацию после restore.
Контроль не запускает аудит и не меняет сохранённые результаты другой области.

Актуальность кода — отдельное наблюдение:

| `freshness` | Значение |
| --- | --- |
| `fresh` | Доступное основание успешно сверено со снимком run |
| `stale` | Обнаружено изменение bytes или основания |
| `unchecked` | Текущую актуальность не удалось проверить либо run выбран как исторический |

После штатного citations release доступность становится `released`, актуальность — `unchecked`.
Полное решение по неизменному основанию остаётся `saved`; его GAP и свидетельства сохраняются.
Изменение кода само по себе не запускает новый аудит: это решение человека.
При возврате точных исходников новая публикация пересчитывает наблюдение из проверенного state.
Настоящий stale receipt исполнения при этом не превращается в passed.

## Какие схемы читать

| Интерфейс | Текущая схема | Содержимое |
| --- | --- | --- |
| `external result CONFIG RUN_ID` | [external-result v3](schemas/external-result-v3.schema.json) | Самостоятельные report и decision |
| `result.json` внешней области сайта | [external-result v4](schemas/external-result-v4.schema.json) | Ссылки `report_ref` и `decision_ref` |
| Запрос `bundle export` | 2 | Абсолютные configs, без sites |
| Новый bundle | 3 | Аудит без сайтов |
| `cleanup plan ARCHIVE` | 1 | Доказанные dispatch-дубли |
| `cleanup plan ARCHIVE --publications ID...` | 2 | Явно выбранные старые копии сайтов |

Site result v4 ссылается на соседний report.json и поле `/host_review`.
Проверяйте SHA-256, размер и совпадение run/snapshot/basis.
Hash относится к точным bytes опубликованного файла, включая конечный перевод строки.
Прежние результаты и bundles читаются по своим версиям; новая публикация не переписывает их.

## Backup и восстановление

Создайте `bundle-request.json` с абсолютными путями рабочих CONFIG:

```json
{"schema_version":2,"configs":["/work/audit-state/area-a/config.yaml","/work/audit-state/area-b/config.yaml"]}
```

Включите все связанные CONFIG из `related`.
Внешние citations-входы перед export нужно штатно освободить через `external release`.
Непустой sites в старом запросе новый export отклоняет.

```sh
spec-audit bundle export ./bundle-request.json ./audit-backup.tar.gz
spec-audit bundle verify ./audit-backup.tar.gz
spec-audit bundle restore ./audit-backup.tar.gz ./restored-audit
spec-audit publish ./site-restored-001 --from ./restored-audit
```

NEW_DIR для restore должен отсутствовать.
Ответ restore перечисляет рабочие `configs`; они нужны для выборочной или исторической публикации.
Новый bundle сохраняет данные аудита и необходимые source-объекты archive.
Производные HTML/viewer-файлы и внутренние архивы сайтов в него не входят.
Сайты из старых bundles v1/v2 восстанавливаются по прежнему точному контракту.

## Безопасная очистка прежних копий сайтов

Этот маршрут нужен для управляемых копий, созданных прежними версиями publish.
Новые публикации таких копий не создают.
ID — полное 64-символьное имя выбранного manifest в `reports_dir/._publications/` без `.json`.
Не редактируйте manifest и не удаляйте общие объекты вручную.

Сначала создайте актуальный audit-only backup всех связанных областей.
Затем подготовьте PLAN и PROOF:

```sh
spec-audit cleanup plan ./audit-backup.tar.gz --publications FULL_PUBLICATION_ID > ./cleanup-plan.json
spec-audit cleanup verify ./audit-backup.tar.gz ./cleanup-plan.json > ./cleanup-proof.json
```

`FULL_PUBLICATION_ID` замените выбранным ID.
Plan и verify не удаляют данные.
Verify независимо восстанавливает аудит и проверяет возможность генерации сайта.

Оператор отдельно разрешает применение проверенного плана:

```sh
spec-audit cleanup apply ./audit-backup.tar.gz ./cleanup-plan.json ./cleanup-proof.json > ./cleanup-result.json
```

Apply сначала удаляет выбранные manifests, затем только объекты без сохраняемых потребителей.
Общие физические файлы, источники и невыбранные публикации защищены.
Частичное удаление допускает повтор того же apply; новые зависимости требуют нового плана.
Сохраните PLAN, PROOF и JSON результата вместе с backup.

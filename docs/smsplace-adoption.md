# Применение spec-audit к SMSPlace

Версия: 0.4, 2026-09-16. Статус: принят аудит по разделам; локальная установка — встроенный skill релизного бинарника, skill/ссылки/конфиг трекаются в Git пилота по решению владельца 2026-09-16 (редакция REQ-SMS-001), результаты аудита остаются вне Git; не новая редакция бизнес-ТЗ и не разрешение на массовую миграцию.

SMSPlace — текущий пилот универсального инструмента. Бизнес-знания, пути, GitLab и pri-fly в этом документе относятся только к пилоту: они не становятся defaults ядра, общего skill или будущих проектов. Преобразование бизнес-ТЗ под spec-first/ISO-ready оформляется отдельным изменением этой спецификации применения и самого бизнес-ТЗ; оно не выполняется автоматически при разработке spec-audit.

## Цель для менеджера

Вынести стоимость и служебный контекст аудита за пределы продукта, сохранив возможность понять, где бизнес-требование действительно подтверждено и где тест оставляет пробел. Инструмент не должен создавать ложные продуктовые задачи или требовать поддерживать второй ручной источник требований.

## Граница владения

| Объект | Где остаётся истина |
| --- | --- |
| Бизнес-требования, протоколы, деньги, уточнения | Существующий `/TZ` и объявленная в SMSPlace иерархия источников |
| Реализация и тесты | Репозиторий SMSPlace |
| Изменение кода | Рабочий процесс pri-fly; не функция spec-audit |
| Задачи продукта | GitLab проекта |
| Механика внешнего аудита | Репозиторий spec-audit и его [спецификация](tool-spec.md) |
| Конфиг, прогоны, snapshots, observations, HTML | `.spec-audit/` в SMSPlace, исключённая из Git; прежние внешние прогоны остаются историей |

Бизнес-код и `/TZ` остаются read-only. Отдельным решением 2026-09-15 владелец разрешил `.spec-audit/` внутри SMSPlace и подключение уже существующего skill для самостоятельного использования. Только при настройке разрешены записи локального конфига, ссылок на инструмент/skill и исключений Git; во время аудита записи ограничены этой игнорируемой рабочей областью. Планы AI Factory и новые CELL в продукте не создаются.

## Требования применения

### REQ-SMS-001 — Без служебных артефактов в истории продукта

Условие: выполняется аудит SMSPlace или разрешённая владельцем локальная настройка.

Требование: результаты аудита (`reports`, история, отчёты разделов) остаются в игнорируемой части `.spec-audit/` либо в явно выбранной внешней рабочей области и не попадают в Git. Код инструмента не переносится в бизнес-модули; второй launcher не создаётся. Редакция 2026-09-16 (решение владельца): установленная копия skill `.spec-audit/skill/` с receipt, относительные ссылки `.agents/skills/spec-audit` и `.claude/skills/spec-audit`, `.spec-audit/config.yaml` и `scopes/*/config.yaml` (с относительным `project_root`, без абсолютных путей хоста) трекаются в Git пилота — иначе они отсутствуют в изолированных worktree-сессиях агентов и `/spec-audit` не распознаётся. Обновление skill (`spec-audit skill update`) меняет tracked-файлы и фиксируется отдельным chore-коммитом.

Проверка: до/после аудита `git status` пуст; `git check-ignore` подтверждает игнорирование `.spec-audit/reports`, `.spec-audit/history` и `scopes/*/reports`; tracked-набор ограничен skill, ссылками и конфигами; CLI отклоняет пересечение исходников и reports_dir.

### REQ-SMS-002 — Без изменения бизнес-норм

Условие: аудитор обнаружил неоднозначность или неполное свидетельство.

Требование: результат должен сохраняться как вопрос/ограничение аудита, не изменяя `/TZ` и не превращаясь автоматически в GitLab issue.

Проверка: норму, кодовый дефект и недостаточную силу теста можно различить в отчёте; внешних записей в GitLab нет.

### REQ-SMS-003 — Ограниченный предмет сравнения

Условие: владелец разрешил прикладной пилот на SMSPlace.

Требование: пилот должен сравнивать старый и новый подход на одном зафиксированном небольшом scope с одинаковой редакцией требований и кода.

Проверка: записаны snapshot, точные границы scope, известные ограничения и сопоставимые результаты, без утверждения статистического выигрыша по одному запуску.

### REQ-SMS-004 — Явное принятие извлечённых норм

Условие: старое ТЗ не содержит объявленных норм в профиле v0.1.

Требование: структурные Markdown-фрагменты должны оставаться кандидатами до независимой проверки сохранения смысла и принятия владельцем.

Проверка: число AST-узлов/строк не выдаётся за полноту требований; сгенерированный индекс не становится самостоятельным ручным ТЗ.

### REQ-SMS-005 — Сохранение текущих гарантий

Условие: действует ограниченная граница применения, принятая владельцем 2026-09-15.

Требование: действующие trace/re-audit и CI-гейты SMSPlace должны оставаться без изменений.

Проверка: этот этап не удаляет маркеры, индексы, CELL, guards, jobs или проверки CI.

### REQ-SMS-006 — Проверенный PHP runtime

Условие: разрешён анализ PHP или отдельный тестовый запуск.

Требование: PHP должен исполняться только в фактически проверенном контейнере SMSPlace, а запуск тестов общей БД — последовательно после отдельного разрешения хоста.

Проверка: чужой checkout/mount отклонён; host PHP не используется; синтаксический SDK не выдаётся за runtime evidence.

## Последовательность принятия

1. Завершить срез инструмента на независимых примерах и собственной новой спецификации.
2. Выбрать один прикладной scope; согласовать атомизацию без потери условий, обязательности и исключений.
3. Выполнить внешний read-only аудит и сравнить с действующим процессом; отдельно измерить ложные findings и пропуски, не только скорость.
4. Только после принятия результата решать, что переносить/отключать в продукте. Миграция обратима и имеет отдельный план.

Решения владельца 2026-09-15: сначала принят внешний повседневный аудит выбранных разделов, затем разрешены локальная `.spec-audit/` и подключение существующего skill. Старые CI и trace сохраняются. Приёмка инструмента задана в [§12 основной спецификации](tool-spec.md#12-контракт-ближайшего-выпуска). Контроль REQ-SMS-003 выполнен с ограничениями в отдельном same-edition запуске ниже; прежний A/B представления Task его не заменяет. Изменения бизнес-кода и PHP-тесты по-прежнему требуют отдельного разрешения.

Полное отключение старого trace требует отдельного решения о каждой сохраняемой гарантии. Этот документ не объявляет старый CI или исторические артефакты ненужными и не разрешает их удаление.

Это контекстное разделение, не ОС-песочница. Хост и selector не объявляются слепыми участниками.

Независимый spec-only эталон зафиксирован до извлечения. Новый extractor получил только фрагменты ТЗ; автор эталона проверил raw после его фиксации. Его оценка: сохранены 13 нормативных групп, все 29 кандидатов поддержаны; усиленных, лишних норм и смысловых дублей не обнаружено. Это суждение reviewer, не машинное доказательство полноты. Формальный `TestExternalExtractionReview` не пройден: G14 попал в знаменатель как требование, хотя является ограничением знания и сохранён в raw.limitations. Ещё два возражения относятся к смешению нормы с отсутствием контракта повторных команд и с правилами самого эксперимента. Gold, raw и отрицательный результат сохранены без подгонки.

Хост отдельно принял 28 норм. C005 отклонён именно как самостоятельная обязанность реализации: пояснение чтения примеров не требует blacklist публичных строк; его исходный смысл остаётся в журнале и ТЗ. Это отличается от классификации reviewer, а не переписывает его результат. Два unresolved по выбору ветви нормализации сохранены как ambiguous. Связанные требования о namespace и исходном/нормализованном значениях передаются вместе: их отдельная проверка без соседних ограничений была бы неполной.

Все конфиги, raw, решения и отчёты остаются в `.local/sms-pilot/`, исключённом из Git. Runtime — none: ни PHP, ни Artisan, ни тесты общей БД не запускаются; код и assertions исследуются статически. Даже полная доставка ответов не означает подтверждённое исполнение или отсутствие дефектов.

Две свежие роли получили собственные задания по 28 принятым нормам и выбранную копию файлов, без gold, старых CELL и истории принятия. Оба исходных ответа приняты валидатором с первой попытки без правки. Удаление trace-метаданных не обеспечило полной слепоты: в обычных комментариях остались исторические пояснения. После явного согласования восьми разногласий хост оставил 18 норм со статическим подтверждением реализации, девять unknown и один конкретный статический контрпример, найденный обеими ролями. Это оценки ограниченного пакета, не сертификат продукта; исполнение всех тестовых свидетельств — not_recorded. Подробности, исходные оценки и основания согласования находятся в `.local/sms-pilot/reports/host-reconciliation.json`, JSON/HTML — в `reports/mapping-v1/` той же рабочей области.

Старый trace прочитан только после фиксации обоих raw. Его mapping-вердикты относятся к 30 июля, а точный audit snapshot не установлен; код и ТЗ с тех пор менялись. REQ-SMS-003 в части одинаковой редакции не выполнено: сравнение точности, стоимости и ускорения не состоялось. Найден конкретный случай, где старый PASS_HIGH на весь набор инвариантов подкреплён лишь assertion отдельного поля конфигурации; это предел данного свидетельства, не оценка всего старого подхода. Одновременно найдены два релевантных тестовых файла, отсутствовавших в новой выборке, включая прямую проверку enum. Поэтому missing в пакете не означает отсутствие проверки в проекте. Поздние находки сохранены отдельно, зафиксированный run не переписан; бизнес-задачи не создавались.

Измерены 189 922 байта выбранных файлов и около 264 КБ файлов вместе с заданием на каждую роль; два raw-ответа занимают около 294 КБ. Окно параллельного аудита — 747 секунд, включая диспетчеризацию, инструменты и ожидание результата хостом, не чистое время моделей. Usage, денежная стоимость и сопоставимый старый замер недоступны. Повторы цитат заметны, но сокращать их с потерей соседних условий нельзя.

Новый spec-only gold создан до свежего извлечения. Получены 18 нормативных кандидатов и девять notes. Отдельный reviewer-учёт: 11/12 нормативных групп preserved, одна partial — архитектурный запрет остался только в context. Все 18 сформулированных кандидатов обоснованы. Пять групп notes сохранены, но дополнительное корректное пояснение отсутствует в frozen gold: одно gold objection, формальный unsupported не означает выдуманного содержания. `TestExternalContextReview` отказал; отрицательные исходы сохранены. Хост принял 18 кандидатов только для одинакового ограниченного сравнения, не объявляя полноту ТЗ.

Свежий selector самостоятельно нашёл вынесенные helper и test на синтетическом примере, затем искал по PHP-дереву. Первый результат сохранён; одна адресная доработка по enum/type/cast/schema добавила пять файлов с прямыми assertions, включая пропущенный enum-test. Общая выборка осталась 45 PHP-файлов: пять транзитивных зависимостей не включены, непросмотренные кандидаты и недоступные данные названы явно. Это refinement, не новый слепой проход и не доказательство полного покрытия.

`full-v2` и `compact-v2` получили одинаковые 18 норм, 50 файлов и snapshot. Перед dispatch проверено точное восстановление всего Task, включая исключения, unresolved, revision и источники. Два полных canonical Task занимают 168146 байт, два compact — 117214: меньше на 30,3% без смыслового сокращения. Разрешённые исходники занимают 647087 байт; стартовые PHP-диапазоны — 197078 из 628867 байт полных PHP-файлов. Это размеры доступного материала, не фактически прочитанные токены. Окно четырёх параллельных ролей — 1044 секунды с инструментами/диспетчеризацией/ожиданием. Usage, деньги и speedup недоступны.

Все четыре raw прошли неизменённый submit с первой попытки. В сопоставлении по роли specification/implementation совпали 36/36, assertion labels — 31/36; один запуск не доказывает семантическую эквивалентность или преимущество точности. JSON/HTML обоих run сохраняют оценки ролей, а отдельный `reports/host-comparison.json` — согласование каждой нормы. Особенно важен общий неподтверждённый вывод: четыре роли перенесли правило входящего public протокола на supplier response. После фиксации всех raw хост прочитал соседние нормативные разделы о направлениях Partner API и exact-key наблюдении; они сохранены отдельно в `reports/supplementary-context.json` с исходными хэшами и не подмешаны в первоначальный snapshot. Применимость этого запрета к выбранному пути не установлена: не объявлены ни product gap, ни доказанная корректность. Согласие ролей не компенсирует неполную выборку самого ТЗ.

Go test/vet, адресный race и native build проверены на macOS ARM64. PHP, Artisan и продуктовые тесты не исполнялись; execution остаётся not_recorded. Источники SMSPlace и старые baseline сохранены, бизнес-артефакты и issues не создавались. REQ-SMS-003 остаётся открытым: этот A/B сравнивает представления нового инструмента, а не старый re-audit на той же редакции.

Следующий малый контроль выполнен отдельно в [основной спецификации, A2–A3](tool-spec.md#124-конечная-приёмка-и-статус): роли различили request/response и full/partial assertion; извлечение сохранило обязанности отдельно от rationale и вопроса. Реализовано явное согласование хоста через review с историей и JSON/HTML. Положительный синтетический результат не переписывает отрицательный контроль этого бизнес-snapshot. ## Сравнение на одной редакции, 2026-09-15

В `.local/comparison-20260915/study.json` зафиксирован завершённый с ограничениями контроль Foundation §1.7.2B: бизнес-commit `f4ea779740472bdd1098b2e6b72ef0f455a770d7`, общий PHP-инвентарь 2499 файлов, snapshot новой ветки `69add983b530b2ece71c374f9160ebf8d6fc5f577dca5c46046ed4fa4e09b032`. Старой ветке доступны полное ТЗ и дополнительные не-PHP файлы, новой — выбранные смыслообразующие проекции и PHP. Это одинаковая редакция общих источников, но не одинаковый информационный бюджет.

Оба подхода нашли два статических контрпримера: несовпадение Unicode-нормализации записи и поиска; конфликт назначений внутри импорта словаря, скрытый успешным обновлением. Новый путь извлечение → принятие 16 норм → две роли → отдельный review → JSON/HTML завершён без ремонта raw. Итог хоста: 12 supported, 2 contradicted, 2 unknown; 15 weak assertions и один relevant. Исполнение продуктовых тестов — not_recorded; одна исходная разница ролей сохранена после согласования.

REQ-SMS-003 / A5 закрыты как ограниченный сравнительный запуск, не доказательство статистического превосходства. Цена и токены неизвестны; окна времени несопоставимы как speedup. Неисполненные тесты и диагностические ограничения старой ячейки не скрыты. Новые задачи и изменения SMSPlace не создавались; исходные отрицательные контроли сохранены. HTML-карта принята владельцем отдельным ручным просмотром.

Один run соответствует одной редакции: обе роли, неизменённые raw и полный review с человеческим пояснением проблемы/влияния/следующего действия. Уже выполненная правка не требует искусственно восстанавливать дефект или ждать повторной разработки.
3. Findings с проблемой, влиянием, точными цитатами и предлагаемой проверкой передаются разработческому процессу pri-fly. По уточнению владельца 2026-09-15 spec-audit предназначен только для аудита: не меняет код/ТЗ и не запускает pri-fly. Исправление и его разрешения находятся за границей инструмента.
4. После изменения кода — новый run без переноса старых assessments/receipts. Если ТЗ не менялось, повторное принятие индекса не нужно; если изменился любой выбранный spec-файл, требуется полное явное reconcile/rebind/revise. Старый run остаётся историей. Тесты — только по REQ-SMS-006; без разрешения остаётся not_recorded.
5. Новый review и HTML показывают, что закрыто, что осталось weak/unknown и чем подтверждён запуск. С релиза 0.1.8 решение хоста записывается в форме `version: 2` (вердикт и `concur` на норму, `counts` сверяет бинарник) — без копирования цитат ролей; полная форма `version: 1` — только для собственных свидетельств хоста. С релиза 0.1.9 каталоги ролей `dispatch/<task_id>/` создаёт `prepare`, `review` отдаёт таблицу расхождений `outcomes[]`, а черновик решения печатает `draft CONFIG RUN_ID` — хост сохраняет его в `dispatch/host/` и заполняет. С релиза 0.1.11 черновик — `version: 3`: собственные цитаты хоста добавляются внутрь вердикта по норме, где они нужны (возврат к v1 не требуется); `outcomes[]` показывает limitations ролей и `previous_host` — прошлый вердикт хоста на том же snapshot и accepted head, только как подсказку. С релиза 0.1.12 список файлов лежит один раз в `dispatch/files.json`, `index` называет `freshness`, а `index`/`check`/`reconcile` подсказывают о якорях ТЗ (`§N.N`, `A-NNN`), не определённых в spec-файлах snapshot; случай 060 (якорь не назван в тексте нормы) подсказка не покрывает — читать смежные разделы по-прежнему задача хоста. С релиза 0.1.14 перед `review … DECISION` хост вызывает `validate CONFIG RUN_ID host DECISION` — те же проверки без записи; `outcomes[]` несёт statement прошлого решения и `only_here` — строки, которые цитирует только одна роль. С релиза 0.1.15 statement согласной нормы можно оставить пустым (бинарник подставит «Совпадает с оценками обеих ролей.»), а протокол mapper прямо требует contradicted при противоречии в достижимой ветке. С релиза 0.1.16 норму читают целиком командой `review CONFIG RUN_ID REQ-ID`, а правило «contradicts важнее relevant» записано в §14. Статус GitLab не меняется автоматически. Рабочая приёмка требует свежий отчёт по живому checkout, воспроизводимые команды и отсутствие изменений бизнес-исходников или служебных записей вне разрешённой рабочей области; она не означает готовность всего корпуса.

`fresh` означает совпадение снимка с локальным `project_root`, а не актуальность удалённой `development`. Во время run checkout не обновляют; обнаруженное внешнее изменение делает старый результат историческим и требует нового run. Снимок-копия также явно называется историческим, не живым.

Исправление уже выполнено другим разработчиком: задача назначена `garpik`, комментарий от 14 сентября указывает на влитый !1157 / `186bc8057` и ожидание QA. `opened` не означает, что нужно заново писать код; spec-audit проверяет готовую редакцию и не закрывает задачу автоматически.

### Локальный запуск выбранного раздела

Рабочий каталог команд — checkout spec-audit. Для #130 используется `.local/daily-smsplace/pricing-factor.yaml`: `project_root` указывает на живой SMSPlace, `reports_dir` — на внешний `.local/daily-smsplace/pricing-factor-reports`, `runtime.kind=none`. Пять полных spec-файлов доступны как контекст; приняты восемь норм, не весь pricing-корпус. Полные файлы нужны и для проверки свежести: даже правка вне выбранного абзаца делает принятый индекс stale.

```bash
./bin/spec-audit status .local/daily-smsplace/pricing-factor.yaml pricing-factor-v2
./bin/spec-audit report .local/daily-smsplace/pricing-factor.yaml pricing-factor-v2
```

Для прежних внешних прогонов хост читает `skills/spec-audit/SKILL.md`, передавая ему явные абсолютные пути бинарника и CONFIG. CONFIG, raw, принятый индекс и отчёты в `.local` не входят в Git: одно клонирование инструмента их не восстанавливает. Новая локальная установка описана ниже; исторические конфиги и raw не перемещаются и не переписываются.

После отдельного изменения кода через pri-fly хост сначала обновляет status/report старого run. Если выбранное ТЗ не менялось, продолжение использует прежний принятый индекс:

```bash
./bin/spec-audit index .local/daily-smsplace/pricing-factor.yaml
./bin/spec-audit prepare .local/daily-smsplace/pricing-factor.yaml pricing-factor-v3
```

`pricing-factor-v3` — пример нового ещё не занятого ID, не выполненный сейчас проход. Далее нужны свежие mapper/redteam, submit обоих raw, отдельный review и report по протоколу лаунчера; один prepare не является повторным аудитом. Если изменилось ТЗ, сначала полный reconcile. Старые ответы/receipts не копируются, stale нельзя обойти retry или заменой hash.

### Самостоятельное использование из SMSPlace

Бинарник установлен релизным `install.sh` в `~/.local/bin/spec-audit` вне бизнес-проекта и обновляется `spec-audit update`. Skill встроен в бинарник: с разрешения владельца 2026-09-16 `spec-audit skill install --dir <checkout> --host both --replace` заменил прежний symlink на checkout инструмента реальным каталогом `.spec-audit/skill/` с receipt; ссылки `.agents/skills/spec-audit` и `.claude/skills/spec-audit` остались относительными (`kept`). Зависимость от checkout spec-audit снята; повторный `skill update` — `updated:false`. Первая новая сессия Claude Code в пилоте не увидела `/spec-audit`: desktop-сессии работают в изолированном worktree, где игнорируемых файлов нет. Решение владельца 2026-09-16 — трекать skill, ссылки и конфиг (коммит `chore` в `development`); отчёты и история остаются игнорируемыми. `init CONFIG` по-прежнему создаёт только YAML; установка skill — отдельная явная команда ([§18](tool-spec.md#18-поставка-версия-обновление-и-установка-skill)). Бизнес-код, ТЗ и CI не менялись; проверка из новой AI-сессии — следующий этап.

В `.spec-audit/config.yaml` заданы `/TZ`, PHP-код и тесты, `runtime.kind=none`. Это карта расположения источников, а не принятый полный индекс. Для каждого запрошенного раздела skill использует `.spec-audit/scopes/<scope>/config.yaml` с необходимыми нормативными источниками; индекс, raw, решения и HTML живут в соседнем `reports/`. Новая область не переиспользует принятый индекс другой области. Лимит 64 активных требований остаётся; составной запрос делится явно, без заявления полноты всего ТЗ.

Из корня SMSPlace проверка настройки без ИИ и без записи:

```bash
spec-audit reconcile .spec-audit/config.yaml
```

Первый ответ `freshness=uninitialized` означает, что нормы ещё не извлечены и не приняты, а не что ТЗ пустое. Смысловой запуск в сессии: `$spec-audit проверь раздел TZ/final_tz/04-pricing-engine.md` в Codex или `/spec-audit проверь раздел TZ/final_tz/04-pricing-engine.md` в Claude Code. Хост читает необходимые соседние нормы, принимает ограниченный набор, запускает независимые роли и делает review; бизнес-код и GitLab не меняются.

Для доступа к предыдущему отчёту из той же папки разрешена ссылка `.spec-audit/history/pricing-factor` на прежний внешний каталог: это история, не новый аудит и не перенос raw. Ни конфиг, ни отчёты, ни локальные ссылки не восстанавливаются клонированием Git. Полное `/TZ` и `.spec-audit` не передаются субагентам вместе: каждая роль получает только свой Task и разрешённые исходники.

HTML с графиками и настройками принят владельцем ручным просмотром 2026-09-15. Это приёмка интерфейса в его среде, не проверка каждого редактора на всех ОС.

## Обкатка PHP/Laravel SDK

Запланированное расширение задано в [§17 спецификации инструмента](tool-spec.md#17-php-и-laravel-sdk); оно предназначено для Laravel-проектов вообще. Для SMSPlace ожидаемая польза — точнее находить реализацию за сервисами/интерфейсами, Eloquent и связанный тестовый контекст, не добавляя бизнес-правила в SDK.

На 2026-09-16 в `composer.json` SMSPlace уже объявлен Larastan, а `phpstan.neon.dist` подключает его, baseline и собственные проектные правила. Это существующая проверка бизнеса, **не интеграция со spec-audit**. Рабочий `php-facts` использует php-parser, а локальный CONFIG по-прежнему имеет `runtime.kind=none`.

Порядок пилота: сначала независимые PHP/Laravel-примеры инструмента, затем согласованный небольшой scope SMSPlace на одной редакции ТЗ/кода, с SDK и без него. Перед запуском отдельно разрешить Larastan bootstrap и проверить Docker mount/изоляцию. Учесть фактические includes, stubs и локальные overrides анализатора; его штатный `tmpDir: storage/framework/cache/phpstan` не использовать для служебных записей аудита. Временный конфиг/кеш/выгрузка — только в разрешённой audit-области. Composer, CI, baseline и проектные PHPStan rules не правятся; при несовместимой среде нужен отказ и отдельное решение, а не обход guards. Рабочие БД/очереди/сервисы при bootstrap не используются.

Связи SDK служат подсказками, не автоматической заменой `/TZ`, `@tz`, тестов или прежних CI-гарантий. Выполнение этого плана не разрешает менять бизнес-код и не означает, что старый trace уже можно удалить.

# Спецификация spec-audit

Редакция документа: 1.1, 2026-09-17. Владелец продукта — StenHigh. Разделы 1–10 сохраняют контракт реализованного v0.1; разделы 12–16 задают рабочий выпуск, статус приёмки — §12.4. Редакция 0.6 восстановила план PHP/Laravel SDK (§17); 0.7 добавила §18 — поставку через подписанный релиз; 0.8 добавила §19 — уроки чистой сессии (`validate`, журнал версий бинарника run, ответ `reconcile` после apply, протокол роли) по решению владельца 2026-09-16; 0.9 добавила §20 — справочные источники ТЗ и деление большого набора по решению владельца 2026-09-17; 1.0 добавила §21 — уроки второго прогона (`check` без записи, подсказки сопоставления, изоляция роли) по решению владельца 2026-09-17; 1.1 добавляет §22 — уроки третьего прогона (`reanchor`, `unique_shared`, диагностика `scopes`, признак `base_index_current`) по решению владельца 2026-09-17. Текущие форматы, §6 и `init` не меняются. Это не заявление о полной приёмке или ISO-conformance. Изменение требований требует явного обоснования; зелёный тест не разрешает подгонять норму под реализацию.

Точка входа в нормативный комплект — этот документ и явно связанные контракты. [Принятый индекс](accepted-index.md) сохраняет свой frozen baseline. [Применение к SMSPlace](smsplace-adoption.md) задаёт только ограничения применения, не нормы инструмента или продукта. Эксперименты, README и план — свидетельства и навигация, не новые требования. При конфликте сначала применяется явное решение владельца; неразрешённый конфликт документов нельзя молча разрешить кодом.

Расширение [принятого индекса](accepted-index.md) добавляет отдельный `index_mode: accepted` и `reconcile`. Без этого поля действует прежний declared-профиль и совместимость его run; правила ниже не требуют переписывать legacy-ТЗ в REQ-блоки.

## 1. Зачем нужен инструмент

Менеджеру недостаточно знать, что рядом с требованием найдены код и тест. Тест может проверять другую ветвь, использовать слабое сравнение или закреплять дефект. Нужен отчёт, который показывает, какая обязанность рассмотрена, на чём основан вывод и чего для уверенности не хватает.

Первый выпуск проверяет этот подход на небольшом разделе, а не обещает автоматически сертифицировать весь продукт. Пользователь задаёт источники и ограничения в YAML, запускает бинарник вручную или через skill. Смысловой анализ выполняют независимые агенты существующей сессии; бинарник проверяет происхождение данных, ведёт состояние и формирует JSON/HTML.

Полезное отличие от списка trace-связей: отдельные состояния требования, реализации, релевантности assertion и фактического исполнения. Недостаток тестов не равен дефекту продукта.

## 2. Область и исключения

В срез входят: локальный конфиг; структурное чтение Markdown; объявленные адресуемые требования; scope × mapper/redteam; точные цитаты; собственные receipts запуска тестов; PHP syntax-only SDK в Docker; возобновление/устаревание; один отчёт из общей модели данных.

Не входят: модельные API и ключи в бинарнике; автоматическое создание issues; изменение проверяемого кода или ТЗ; массовая миграция старого ТЗ; сервер/БД; граф зависимостей; универсальная система плагинов; автоматический сертификат соответствия; доказательство экономии токенов.

Обычный Markdown без профиля можно структурно прочитать, но нельзя объявить автоматически полным индексом обязательств. В baseline v0.1 семантическая атомизация отсутствует; ограниченная приёмка кандидатов теперь задаётся отдельным контрактом расширения. v0.1 испытывается на явно размеченной новой спецификации и независимых примерах. Это не требование переписать SMSPlace.

## 3. Термины и ответственность

| Термин | Значение |
| --- | --- |
| requirement | Объявленная норма с постоянным ID, условием, требуемым результатом и способом проверки |
| scope | Ограниченное множество requirement IDs, назначенное каждой из двух ролей |
| snapshot | Относительные пути и хэши выбранных источников плюс версия протокола/профиль; не копия файлов и не ОС-песочница |
| assessment | Суждение агента об одной норме с цитатами и ограничениями; не машинно доказанная истинность |
| assertion | Конкретная проверка ожидаемого результата в тесте; имя теста, комментарий и @tz её не заменяют |
| receipt | Запись фактически запущенного бинарником тестового процесса, привязанная к snapshot и runtime |
| stale | Источники или смысловая конфигурация отличаются от snapshot; прежние выводы доступны только как история |

Автор спецификации определяет нормы. Хост выбирает scope, разрешает запуск SDK/тестов и согласует противоречия. Mapper систематически сопоставляет нормы, код и assertions; redteam независимо ищет опровержения. В v0.1 окончательное согласование остаётся вне автоматического вердикта CLI.

## 4. Профиль Markdown

Это локальный формат проекта, не синтаксис, предписанный ISO. Норма — top-level заголовок третьего уровня `### REQ-<NAMESPACE>-<NUMBER> — <название>`, где namespace состоит из заглавных латинских букв/цифр, number содержит не меньше трёх цифр. Под ним ровно по одной непустой однострочной записи `Условие:`, `Требование:`, `Проверка:`. Заголовки в code fence или blockquote — примеры, не нормы. Следующий top-level заголовок уровня 1–3 завершает блок. Остальная проза — пояснение, не дополнительный ручной индекс.

`Требование:` описывает один наблюдаемый результат. Условия, исключения и границы должны быть явными; измеримые критерии предпочтительнее слов «быстро» и «удобно». Смысловую атомарность и проверяемость оценивает человек/агент: структурная валидация этого не доказывает. ID не меняется от перемещения строки; изменение нормы меняет её content hash. Один ID не может принадлежать двум scope данного run.

## 5. Требования первого среза

Поля могут идти подряд в одном Markdown-абзаце. Пояснение отделяется пустой строкой: продолжение поля на следующей строке не принимается как однострочная запись профиля.

### REQ-SA-001 — Безопасная инициализация

Условие: пользователь вызывает `init CONFIG`.

Требование: инструмент должен создать шаблон YAML только по отсутствующему пути, не перезаписывая существующий файл или символическую ссылку.

Проверка: повторный init отклонён, байты исходного конфига не изменились.

### REQ-SA-002 — Однозначная конфигурация

Условие: операция читает YAML-конфиг.

Требование: инструмент должен отклонить неизвестные/повторные поля, несколько YAML-документов и недопустимые источники согласно контракту раздела 6.

Проверка: негативные варианты конфигурации не создают готовый run и не изменяют прежние результаты.

### REQ-SA-003 — Переносимая идентичность

Условие: одинаковые выбранные файлы, профиль и назначения scope перенесены вместе в другой каталог.

Требование: инструмент должен сохранить snapshot ID независимо от абсолютного корня проекта и физического каталога отчётов.

Проверка: два одинаковых дерева в разных каталогах имеют один ID; изменение входного файла, профиля или назначения scope меняет ID.

### REQ-SA-004 — Адресуемый индекс

Условие: index читает спецификацию в профиле раздела 4.

Требование: инструмент должен вернуть каждую объявленную норму ровно один раз с её условием, формулировкой, способом проверки, content hash и точной ссылкой на исходный блок.

Проверка: Unicode/CRLF, перестановка строк, code fence, blockquote, дубликаты ID и неполный блок; отсутствие объявленных норм не выдаётся за доказательство отсутствия обязательств.

### REQ-SA-005 — Полный учёт назначенных норм

Условие: submit принимает ответ роли на scope.

Требование: инструмент должен принять ответ только при точном равенстве множества assessment IDs назначенному множеству requirement IDs.

Проверка: отсутствующий, повторный или чужой ID отклонён; невозможность оценки выражается явным unknown/ambiguous, а не пропуском строки.

### REQ-SA-006 — Привязка цитат

Условие: агент представил assessment в declared-профиле; для accepted-профиля допустимые диапазоны заданы контрактом расширения.

Требование: инструмент должен отклонить цитату, не совпадающую с исходными строками своего snapshot и категории, а цитату спецификации — также находящуюся вне блока назначенного требования.

Проверка: чужое требование с реальной цитатой, сдвинутый диапазон, выдуманный текст, traversal, symlink и код вместо теста отклонены.

### REQ-SA-007 — Раздельная сила свидетельств

Условие: отчёт содержит assessment нормы.

Требование: инструмент должен представлять качество нормы, поддержку реализацией, релевантность assertion и выполнение теста отдельными состояниями по разделу 7.

Проверка: корректный код со слабым зелёным тестом не превращается в product gap; зелёный тест дефектного поведения не превращается в соответствие.

### REQ-SA-008 — Исполнение подтверждается процессом

Условие: хост явно вызывает test для разрешённого runtime.

Требование: инструмент должен создать receipt из наблюдаемого запуска согласно разделу 8, не принимая высказывание агента или импортированный JSON за факт собственного исполнения.

Проверка: успешный, упавший, пустой, прерванный запуск и изменение snapshot до/после дают разные состояния; фильтр без реально выполненных тестов не даёт passed.

### REQ-SA-009 — PHP только в проверенном контейнере

Условие: хост явно запрашивает PHP facts или PHPUnit.

Требование: инструмент должен выполнять PHP только в проверенном project container по правилам раздела 8, без fallback на PHP хоста.

Проверка: отсутствующий контейнер, чужой mount, некорректный SDK-envelope или недоступный parser дают отказ; исходники и цитаты SDK сверены до использования.

### REQ-SA-010 — Устаревание не скрывается

Условие: источники изменились после prepare.

Требование: инструмент должен показывать сохранённый run как stale в status/report и запрещать добавление новых assessments или исполнений к прежнему snapshot.

Проверка: HTML/JSON обновляются с явным stale; история не теряется, свежий вывод не выдаётся, нужен новый run.

### REQ-SA-011 — Повторная попытка

Условие: хост повторяет submit или вызывает retry задания.

Требование: инструмент должен применять протокол попыток раздела 9 без потери ранее принятых ответов.

Проверка: одинаковый submit идемпотентен, другой ответ той же попытки отклонён, retry увеличивает attempt, поздний ответ старой попытки отклонён.

### REQ-SA-012 — Целостность состояния

Условие: процессы одновременно изменяют один run.

Требование: инструмент должен сохранять каждое успешное изменение без потерянных обновлений, используя ограниченные по размеру атомарные записи.

Проверка: конкурентный submit разных ролей сохраняет оба ответа; превышение размера отклоняется до публикации непрочитываемого state.

### REQ-SA-013 — Честный отчёт

Условие: пользователь вызывает report для любого существующего run.

Требование: JSON и HTML должны показывать каждую объявленную норму, обе роли, pending/stale и раздельные свидетельства, не выдавая автоматический PASS или сертификат.

Проверка: незавершённый run сохраняет строки ожидающих норм; HTML экранирует пользовательский текст; доставка всех ответов не снимает необходимость согласования.

### REQ-SA-014 — Детерминированное автономное ядро

Условие: вызываются init/index/prepare/tasks/submit/status/retry/report.

Требование: эти операции должны работать нативным бинарником на macOS/Linux без Node, Python, PHP, Go toolchain и модельного API во время исполнения.

Проверка: готовый бинарник проходит детерминированный сценарий с пустым PATH; SDK/тестовые команды отдельно требуют runtime проверяемого проекта.

### REQ-SA-015 — Изоляция служебных записей

Условие: инструмент выполняет любую операцию.

Требование: инструмент должен записывать служебное состояние на хосте только в явный CONFIG при init или в reports_dir, не изменяя выбранные исходники, Git, задачи и установленную конфигурацию агента.

Проверка: сравнение входных байтов до/после; stdout содержит JSON, диагностический stderr управляется LOG_LEVEL и не содержит цитат/секретов/сырых ответов.

## 6. YAML и CLI

```yaml
version: 1
project_root: .
specs:
  paths: [specs]
  include: ['*.md']
code:
  paths: [src]
  exclude: ['*_test.go']
tests:
  paths: [tests]
reports_dir: .spec-audit/reports
runtime:
  kind: none
  service: ''
  paths: []
  tests: []
  timeout_seconds: 30
scopes: []
```

CONFIG — доверенный ввод владельца, а не инструкция из анализируемых файлов. project_root и reports_dir разрешаются относительно каталога CONFIG; абсолютные пути допустимы. paths каждой группы — существующие файлы/каталоги относительно project_root. include/exclude — glob только имени файла (`filepath.Match`), не язык рекурсивных путей; отсутствующий include означает все имена. Файл не может одновременно попасть в разные категории. Пустая группа tests допустима. specs/code непусты. Символические ссылки и специальные файлы не входят в снимок. reports_dir не должен пересекаться с выбранными входными деревьями; внутри project_root отдельный служебный каталог допустим.

scopes: список `{id, focus, requirements: [REQ-...]}` снабжает каждую норму ровно одним владельцем. Пустой scopes назначает все объявленные нормы одному scope `all`. Неизвестные, повторные или нераспределённые IDs отклоняются. Лимиты первого среза: 16 scope, 64 нормы на scope, 512 норм суммарно, 25000 входных файлов/512 MiB, файл 32 MiB, CONFIG 1 MiB, ответ роли 4 MiB, state 32 MiB. Нормы не разрезаются по числу токенов; слишком большой scope требует осознанного деления.

CLI: `init CONFIG`; `index CONFIG`; `prepare CONFIG RUN_ID`; `tasks CONFIG RUN_ID`; `submit CONFIG RUN_ID TASK_ID RESULT_PATH`; `retry CONFIG RUN_ID TASK_ID`; `status CONFIG RUN_ID`; `report CONFIG RUN_ID`; `test CONFIG RUN_ID EXECUTION_ID`; `php-facts CONFIG RUN_ID FILE...`. prepare не перезаписывает run. RUN_ID, TASK_ID, EXECUTION_ID — локальные slug, не пути. Ошибка команды — non-zero exit и JSON error в stderr; логирование использует LOG_LEVEL=debug/info/warn/error, по умолчанию info. Успешная команда — один JSON-документ в stdout.

## 7. Контракт ответа и отчёта

Ответ роли содержит `task_id, attempt, snapshot_id, scope, role, summary, assessments, limitations`. Все поля обязательны, unknown/duplicate/case-changed поля и null отклоняются. Каждая assessment содержит `requirement_id, specification, implementation, assertion, statement, spec, code, tests, limitations`.

| Поле | Допустимые значения / смысл |
| --- | --- |
| specification | clear / ambiguous — оценка определённости нормы агентом |
| implementation | supported / contradicted / unknown — статическая оценка, не runtime verdict |
| assertion | relevant / weak / contradicts / missing / unknown — суждение о тестовой проверке |
| spec, code | Массив полнострочных цитат `{path,line_start,line_end,quote}`; spec непустой, supported/contradicted требуют code |
| tests | Массив `{test_id,citation}`; relevant/weak/contradicts требуют конкретный тестовый источник; test_id связывает с receipt |
| limitations | Что не доказано; unknown/ambiguous не скрывается отсутствием строки |

Цитата не доказывает интерпретацию. test_id и принадлежность assertion соответствующему тесту остаются проверяемым суждением агента/хоста; совпадение имени в receipt не доказывает эту смысловую связь. ID исполнения Go — `import/path::TestName`, PHPUnit — `ClassName::methodName` (с суффиксом dataset, если он есть в JUnit). Неизвестный test_id отображается как not_recorded. Receipt другого snapshot не засчитывается. Противоречащие роли показываются рядом и требуют согласования, а не усредняются.

Отчёт содержит `delivery_complete`, `freshness`, `requirements_total`, pending tasks, все строки норм, список executions и `host_reconciliation_required: true`. Итоги и ограничения роли представлены один раз на task; строка нормы показывает последнюю запись для каждого test_id, а общий список executions сохраняет полную историю, включая предыдущие неудачи. База полноты — **объявленные требования данного профиля**, не все возможные обязательства естественного языка. Итогов automatic PASS/compliant нет. Позднейшие изменения источников после генерации статического HTML не могут обновить его сами: перед решением нужен свежий вызов status/report, а на странице указаны snapshot и время генерации.

## 8. Runtime и PHP SDK

kind=none отключает исполнение. kind=go разрешает фиксированный запуск `go test -json -count=1` внутри project_root; paths задаёт локальные пакеты, tests — точные имена функций для фильтра, не shell-команду. Go нужен лишь как runtime проверяемого Go-проекта. kind=docker-php использует Docker Compose service (по умолчанию app), локальные PHPUnit paths/tests и таймаут 1–120 секунд. Произвольный исполняемый файл или shell из конфига не принимается.

PHP-процесс запускается через проверенный container ID: фактический mount project_root → `/var/www/html`, workdir тот же, ровно один работающий контейнер. Внутри контейнера действует отдельный timeout; убийство docker CLI само по себе не считается остановкой PHP. PHPUnit не пишет result cache/coverage; JUnit — в уникальном контейнерном /tmp. Сам бинарник не пишет в бизнес checkout. Тесты и Composer autoload — доверенный исполняемый код проекта, а не песочница: оператор отвечает за изолированную тестовую среду, поэтому launcher не запускает тесты без разрешения хоста и не допускает параллельные тесты общей БД.

Дополнительная защита CLI сериализует PHPUnit для разных run одного reports_dir и повторно сверяет snapshot после ожидания. Это не блокировка общей БД между разными конфигами/reports_dir или внешними test runners: их согласует хост. Таймаут теста не расходуется на проверку контейнера и чтение/удаление JUnit; эти служебные стадии ограничены отдельно.

Receipt фиксирует ID, snapshot, время, runtime/version, команду без секретов, exit code, фактически завершённые test IDs/statuses, хэши/размер вывода и состояние passed/failed/incomplete/no_tests/stale. passed возможен только при успешном процессе, корректном отчёте, хотя бы одном passed-тесте, отсутствии failed и совпадении входного snapshot до/после. Это доказательство запуска в записанной среде, не полноты и не корректности продукта. Повторный EXECUTION_ID не перезаписывает receipt. Повторный запуск требует нового ID.

PHP facts — syntax_only. SDK разбирает данные, не подключает выбранные source files; Composer autoload при этом выполняется. Envelope содержит точные байтовые диапазоны/хэши, фактическую версию/reference php-parser, хэш composer.lock и SDK. Бинарник проверяет схему, точное множество запрошенных файлов, текущие исходники и цитаты перед записью. SDK не гарантирует полноту динамических вызовов и не доказывает силу PHPUnit assertions. Отдельная PHPStan-проба остаётся исследовательским материалом.

## 9. Состояние и безопасность

Один run имеет неизменяемый manifest и задания scope × role. Ответ хранится по task/attempt, submit одинаковых данных идемпотентен. retry отзывает текущий ответ задания и увеличивает attempt, сохраняя предыдущий файл как историю. Производные отчёты инвалидируются после изменения state. Файловая блокировка сериализует изменение одного run; запись через temp + rename. Полное восстановление после power loss не заявлено.

Переносимый snapshot включает относительные источники/хэши, распределение требований, конфиг анализа и версию протокола/парсера; физические корни исключаются. Безопасное переиспользование семантических ответов между разными run в v0.1 не реализуется. Изменение runtime-версии не превращает исторический receipt в подтверждение новой среды: версия записана в нём явно.

Источник, assessment и SDK output считаются недоверенными данными. Никакие инструкции в них не запускаются. Пути не выходят из назначенных корней; HTML использует экранирование; проверки размеров выполняются до публикации state. Доверенные локальные пользователи могут изменить state — криптографическая подпись и защита от администратора машины не обещаны.

## 10. Приёмка и предел утверждений

До реализации подготавливаются синтетические случаи с независимыми ожидаемыми выводами: корректная реализация/сильная проверка; корректный код/слабая проверка; неверный код/зелёный закрепляющий тест; отсутствие достаточного свидетельства; неоднозначная норма. Дополнительно проверяются чужая цитата, пропуск ID, stale, retry, неполный run, пустой и неуспешный runtime.

Автоматический контрактный тест проверяет механизмы, а не интеллект агента. Отдельный свежий проход mapper/redteam не получает ожидаемые ответы. Его результаты сравниваются с зафиксированными примерами; ошибки не исправляются хостом незаметно. Один успешный проход не доказывает статистического повышения точности. Самоприменение к этой спецификации дополняет независимые примеры, но не заменяет их.

Технологическое решение среза: Go, stdlib для процесса/JSON/HTML/файлов; уже испытанные Goldmark и YAML; существующий PHP parser проекта через SDK. Одна поддерживаемая сборка, исторические прототипы не становятся вторым источником норм. Для macOS/Linux проверять нативное исполнение в доступной архитектуре и отдельно обозначать только кросс-компиляцию остальных; не приравнивать сборку к исполнению.

## 11. Стандарты и открытые решения

Структура ориентирована на requirements engineering из [публичного описания ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html). Полный платный текст не читался; формальное соответствие не установлено. Практические критерии адресуемости, явных допущений и проверяемости сверены с [NASA Appendix C](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) и [публичной памяткой INCOSE](https://www.incose.org/docs/default-source/working-groups/requirements-wg/guidetowritingrequirements/incose_rwg_gtwr_v4_summary_sheet.pdf). Наш синтаксис, состояния отчёта и границы первого среза — решения этого проекта, не цитаты стандартов.

На 2026-09-15 [официальная карточка ISO](https://www.iso.org/standard/72089.html) обозначает 29148:2018 опубликованным стандартом, подлежащим пересмотру; DIS 29148 ещё разрабатывается. Основа нашей подготовки — опубликованная редакция 2018, не проект DIS. [Открытый ISO OBP](https://www.iso.org/obp/ui?_escaped_fragment_=iso:std:iso-iec-ieee:29148:ed-2:v1:en) различает соответствие процессам, содержанию информационных объектов и адаптированное соответствие. Эта карта — подготовка к будущей проверке, не постатейная матрица соответствия.

Полный текст стандарта не приобретался и целиком не проверялся. До такой проверки нельзя писать «соответствует ISO» или «сертифицирован». Будущий аудит сначала фиксирует редакцию и область заявления, затем сопоставляет каждый применимый пункт с документом/свидетельством и закрывает пробелы. NASA используется как открытая практическая памятка, не замена ISO. Зафиксированные ниже ID, источники, обоснования, приёмка и история уменьшают объём будущей переработки; гарантии лёгкой сертификации нет.

## 12. Контракт ближайшего выпуска

### 12.1 Цели и сценарий использования

Основной пользователь — владелец или команда проекта, работающие в существующей AI-сессии, например Codex/Claude Code. Менеджер потребляет итог, разработчик проверяет цитаты и контрпримеры. Агент-хост организует работу, но не считается независимым владельцем бизнес-норм. ТЗ и код остаются источниками; трекер задач и workflow разработки выбирает проект. spec-audit только аудирует и отдаёт обоснованные findings: не исправляет код, не синхронизирует задачи и не запускает инструменты разработки автоматически.

Инструмент предназначен для разных проектов. Ядро и общий launcher не должны содержать названий/путей конкретного проекта, бизнес-норм, ID задач или исключений под пилот. Эти знания поступают из CONFIG, выбранных источников и отдельного договора применения. Особенности языка/фреймворка отделяются в ограниченные SDK/runtime; текущий PHP SDK даёт только syntax_only. Независимость от проекта требуется сейчас, поддержка всех языков и универсальная система плагинов — нет. Пилот служит проверкой полезности и источником независимых регрессий, не доказательством пригодности для любого проекта. Исторические упоминания в frozen baseline и свидетельствах не задают defaults рабочего инструмента.

| Цель | Пользовательский результат | Покрывающие требования |
| --- | --- | --- |
| G1 — вынести обслуживание аудита из продукта | Самостоятельный бинарник; CONFIG/состояние/отчёты в разрешённой изолированной области — внешней либо локальной игнорируемой `.spec-audit/`; PHP только при разрешённом контейнерном запуске | SA-001…003, SA-009, SA-014…015 |
| G2 — не проверять выдуманную или потерянную обязанность | Сохранены условия/исключения; применимость и неизвестность видны | SA-004…006, SA-016…018; accepted-index |
| G3 — получить объяснимый результат | Отдельны код, assertions и исполнение; хост обосновывает итог рядом с исходными ролями | SA-007…008, SA-013, SA-019…021 |
| G4 — продолжать работу без потери истории | Попытки и решения сохраняются; устаревший вывод не становится текущим | SA-010…012, SA-020 |
| G5 — видеть состояние проекта и находить основание решения | Карта выбранных источников, проблемных норм и переходы ТЗ ↔ код ↔ assertions | SA-022…026 |

Нормальный сценарий: владелец задаёт CONFIG и раздел ТЗ → хост извлекает кандидатов и проверяет контекст → явно принимает индекс → готовит задания → независимые mapper/redteam → проверяет и сохраняет raw → при разрешении запускает тесты → записывает обоснованное согласование → показывает JSON/HTML. Новый контекст, меняющий смысл, требует нового принятия/prepare; в старый snapshot он не подмешивается.

Без ИИ бинарник выполняет механические команды. Он не вызывает модель и не объявляет семантическую полноту. Изменения кода после отчёта требуют нового run. Безопасность исполнения тестов зависит также от изоляции проекта; snapshot не является sandbox.

### 12.2 Правила ведения требований

Стабильный ID и поля §4 сохраняются. Для каждого нового требования ниже отдельно указаны источник и обоснование. Общие атрибуты: владелец StenHigh; приоритет Must для согласованного выпуска; стадия — задано для реализации, а состояние фактической приёмки ведётся в §12.4. Изменение смысла оформляется новой редакцией с причиной и влиянием на тесты/интерфейсы; старые экспериментальные gold и хэши не переписываются. Существующие SA-001…015 остаются baseline v0.1, не получают фиктивную историю утверждения задним числом.

Обязанность отделяется от обоснования и примера. Предпочтителен один наблюдаемый результат; контекст, исключения и зависимости могут иметь несколько источников. Если обязанность известна, неизвестный порог или человеческий исполнитель не отменяет её. Нерешённый вопрос хранится с владельцем, влиянием и событием закрытия; план не может закрыть его галочкой вместо решения.

### 12.3 Границы и открытые решения

Аудит не меняет существующие CI-проверки, прежние инструменты, отчёты и маркеры проверяемого проекта. Их перенос или удаление требуют отдельного решения владельца проекта. Graph/cache, автоматические issues, универсальная система плагинов и доказательство абсолютной безошибочности не входят в выпуск; это не отменяет независимость ядра и launcher от бизнес-проекта (§12.1). Настройка и установка требуют отдельного разрешения: `init` создаёт только YAML; установка и обновление skill — отдельные явные команды `skill install|update` по [§18](#18-поставка-версия-обновление-и-установка-skill), реализованы и приняты на релизе `v0.1.0` (README «Приёмка и ограничения»).

| Вопрос | Владелец / событие закрытия | Влияние до ответа |
| --- | --- | --- |
| OQ-01: аудит выбранных разделов или весь корпус одной командой | Закрыт StenHigh 2026-09-15: «закрепляем и продолжай самостоятельно выполнять» после предложения ограниченного применения | Принят аудит выбранных разделов. Не единый индекс всего продукта; предел 64 active-норм сохраняется |
| OQ-02: вид будущего ISO-conformance и доступ к полному стандарту | StenHigh; перед формальной оценкой соответствия | Не блокирует разработку; ISO-conformance не заявляется |
| OQ-03: разрешения конкретного проекта | Владелец проверяемого проекта; до установки или исполнения проектного кода | Аудит не даёт разрешения на бизнес-записи, установку или тесты. Для текущего пилота действуют отдельно зафиксированные [условия применения](smsplace-adoption.md) |

Для ограниченного аудита можно использовать отдельные CONFIG/reports_dir по разделам; это не единый индекс всего продукта и не способ скрыть пропущенные межраздельные зависимости. Лимиты §6 и accepted-index остаются действующими, превышение требует явного выбора границы, не усечения.

## 13. Требования расширения

### REQ-SA-016 — Сохранение обязанности

Условие: хост принимает кандидатов из обычного Markdown.

Требование: процесс принятия должен сохранять каждую обнаруженную обязанность вместе с её условиями, исключениями и неопределённостью, не заменяя её ненормативной заметкой.

Проверка: парные случаи обязательства/пояснения, человеческой обязанности и неизвестного порога; источник не усиливается и не теряется, решение хоста проверяется отдельно от схемы JSON.

Источник: G2; запрос владельца о spec-first; отрицательный контроль извлечения 2026-09-15. Обоснование: правильная проверка неверно извлечённой нормы не отвечает на вопрос продукта. Зависимость: accepted-index.

### REQ-SA-017 — Граница применимости

Условие: роль оценивает реализацию по принятому набору источников.

Требование: роль должна обозначить реализацию как unknown, если применимость нормы к рассматриваемому участнику, направлению взаимодействия или условию не установлена.

Проверка: одинаковый код обработки неизвестного идентификатора при норме для client request и при явно заданной норме для supplier response; соседние определения включены до prepare, одинаковые слова не заменяют проверку области действия.

Источник: G2; согласование контекстного контроля 2026-09-15. Обоснование: соглашение ролей не делает перенос правила между протоколами корректным. Зависимость: SA-006, SA-016. Это правило роли/хоста, не автоматический смысловой классификатор.

### REQ-SA-018 — Полнота утверждения теста

Условие: роль присваивает assertion значение relevant.

Требование: роль должна обосновать проверку всех существенных результатов назначенной нормы на её применимых условиях; проверка только части составной обязанности должна оставаться weak.

Проверка: пары полного и частичного assertion, зелёный тест ошибочного поведения; факт исполнения берётся только из receipt и не меняет силу assertion.

Источник: G3; запрос владельца о сопоставлении требований с assertions. Обоснование: проверка одного поля не подтверждает все инварианты. Зависимость: SA-007…008.

### REQ-SA-019 — Явное согласование аудита

Условие: все назначенные ответы ролей получены и хост отправляет решение по §14.

Требование: бинарник должен принять только полное обоснованное решение для каждой нормы, привязанное к текущему основанию аудита, и сохранить точные входные байты решения без изменения исходных ролей.

Проверка: неполный/повторный/чужой ID, неточная цитата, чужой run, изменённое основание, пустое обоснование и попытка до завершения ролей отклоняются без изменения журнала.

Источник: G3; требование владельца получать понятный итог. Обоснование: результат не должен оставаться только в ручном файле хоста. Зависимость: SA-005…006, SA-012.

### REQ-SA-020 — Актуальность согласования

Условие: после записанного решения изменились источники, попытки ролей или записи исполнения.

Требование: бинарник должен показывать прежнее согласование как outdated, сохраняя его историю и требуя нового явного решения для текущего аудита.

Проверка: retry, новый receipt, изменение источника и конфликт параллельных решений не дают прежнему решению статус current.

Источник: G4; SA-010…012. Обоснование: согласование относится к конкретным свидетельствам, а не только ID нормы.

### REQ-SA-021 — Итог рядом со свидетельствами

Условие: формируется JSON/HTML run с историей согласования.

Требование: отчёт должен показывать последнее решение хоста и его актуальность отдельно от неизменённых исходных ролей, не объявляя автоматического соответствия или доказанной полноты ТЗ.

Проверка: обе роли, их разногласия, host-обоснование, unknown/weak/not_recorded, устаревшая история и экранирование HTML видны в одном отчёте.

Источник: G3; SA-013. Обоснование: менеджер должен видеть вывод и его предел, разработчик — проверяемое основание.

## 14. Контракт согласования аудита

Для новых submit бинарник сохраняет первые принятые байты роли в прежнем results-файле и необязательный raw_sha256 в Entry. Семантически равная повторная отправка остаётся duplicate, но не заменяет первые байты; оставшийся после прерванной публикации results-файл используется только при равном Result. Read проверяет hash и соответствие state. Старые Entry без hash остаются legacy_canonical: их исходное форматирование неизвестно и не восстанавливается. Согласование старого run допустимо с явной отметкой этого ограничения; нельзя объявлять его exact raw. Retry снимает hash текущей попытки, сохраняя прежний файл. Новый бинарник читает старые run; чтение расширенного state старым бинарником не обещается.

Новая команда `review CONFIG RUN_ID [DECISION]` не заменяет `reconcile`: reconcile принимает требования, review принимает итог аудита. Без DECISION возвращается контекст согласования: run_id, snapshot_id, basis_sha256, delivery_complete, freshness, требования, entries, executions и история решений. Этот режим доступен и для stale-истории; запись требует fresh и полной доставки. Сам вызов CLI не доказывает личность автора: reviewer — подпись оператора, не криптографическая идентификация.

DECISION — строгий UTF-8 JSON до 4 MiB со всеми полями: `version:1, review_id, run_id, snapshot_id, basis_sha256, reviewer, summary, assessments, limitations`. review_id — slug; reviewer и summary непусты. assessments содержит ровно одну обычную Assessment §7 на каждую норму, с теми же правилами цитат/неоднозначности. statement объясняет выбор хоста с учётом разногласий. Нельзя добавлять execution status или новые нормы. Если нужен ранее отсутствовавший нормативный контекст — новый принятый индекс и run, а не цитата вне snapshot.

Основание: SHA-256 от Go `json.Marshal` объекта `{snapshot_id, state, review_head}` в указанном порядке. state — текущий State с entries/executions без производных отчётов; review_head — SHA-256 точных байтов последнего принятого DECISION либо пустая строка. Оно меняется также после нового решения хоста, чтобы параллельные решения не теряли друг друга. Это compare-and-swap, не доказательство правильности оценки.

Под общим lock run хранится `host-reviews.json`: `{version:1, records:[<точная UTF-8 строка DECISION>,...]}`, до 64 решений и 32 MiB целиком. Массив append-only; один и тот же review_id с теми же байтами — duplicate без записи, с другими — конфликт. Исторический duplicate не делает решение current. Проверки размеров/схем/цитат, CAS и повторная сверка snapshot происходят до атомарной публикации. Производные отчёты инвалидируются до изменения журнала; отказ не меняет журнал или роли.

Актуальность последнего решения проверяется относительно state/snapshot и review_head его предшественника. Состояния: missing / current / outdated. Read/report валидируют журнал и не скрывают повреждение как отсутствие решения. Старый run без журнала остаётся доступен без миграции. JSON/HTML сохраняют историю и исходные роли; `host_reconciliation_required` становится false только при current, но `semantic_completeness_proven` остаётся false. Отсутствие автоматического PASS сохраняется; это явное суждение хоста, а не сертификат бинарника.

## 15. Карта проекта для человека

Менеджеру нужна обозримая картина доработок, разработчику — переход от проблемы к конкретному месту ТЗ, кода и теста. Карта дополняет существующий отчёт, а не вводит второй аудит. Ручные `@tz` не требуются: связи берутся из проверенных цитат принятого индекса и assessments. Наличие маркера или ссылки само по себе не свидетельствует о соответствии.

### REQ-SA-022 — Полный видимый инвентарь

Условие: report строится для существующего run, включая незавершённый или stale.

Требование: JSON/HTML должны содержать каждый выбранный файл manifest с категорией, относительным путём и хэшем, отдельно от множества норм данного run и их состояния аудита.

Проверка: нецитированный файл кода, документ без принятых норм, пустая группа tests и ожидающая норма остаются видимыми; счётчики совпадают с manifest, исключённые конфигом файлы не включаются.

Источник: G5; запрос владельца о картине проекта. Обоснование: просмотр только найденных связей скрывал непроверенные области. Зависимость: SA-003, SA-013.

### REQ-SA-023 — Двусторонняя навигация

Условие: у нормы или assessment есть сохранённая цитата.

Требование: HTML должен позволять перейти от нормы к точному сохранённому диапазону ТЗ, кода или assertion и обратно к связанным нормам, показывая автора связи и test_id для тестового свидетельства.

Проверка: несколько норм на один файл/диапазон, отдельная цитата хоста, Unicode в пути и повторные цитаты; каждый внутренний якорь разрешается, цитата доступна без исходного checkout.

Источник: G5; прежний сценарий ТЗ ↔ код и человекочитаемый trace HTML. Обоснование: путь к файлу без диапазона и перехода неудобен для проверки вывода. Зависимость: SA-006, SA-021.

### REQ-SA-024 — Поиск областей внимания

Условие: человек просматривает карту.

Требование: HTML должен предоставлять поиск по ID, тексту и путям, отбор по scope и отдельные фильтры проблем реализации, слабых/отсутствующих assertions, вопросов к ТЗ, unknown, pending, разногласий ролей и отсутствия текущего согласования; файлы должны отбираться по категории и наличию текущих связей.

Проверка: фильтры комбинируются, показывают число результатов и пустое состояние; принятая неоднозначность/открытый вопрос видны до ответа ролей; переход по прямому якорю открывает скрытую фильтром цель.

Источник: G5; запрос владельца о местах доработок. Обоснование: последовательное чтение полного журнала не даёт обзора. Зависимость: SA-022…023.

### REQ-SA-025 — Честное основание карты

Условие: карта сводит сохранённые оценки и связи.

Требование: карта должна явно различать текущее решение хоста, предварительные оценки ролей и историю, не превращая отсутствие связи в дефект, разногласие ролей в противоречие ТЗ или ссылку на тест в подтверждённое исполнение.

Проверка: current/outdated/missing review × fresh/stale × pending/доставленные роли; устаревшая host-only связь не скрывает отсутствие текущих связей; relevant без receipt остаётся not_recorded, а разные мнения видны и после согласования.

Источник: G3…G5; ограничения прежнего trace. Обоснование: удобная визуализация не должна усиливать достоверность исходных данных. Зависимость: SA-007…008, SA-020…021.

### REQ-SA-026 — Автономная безопасная страница

Условие: отчёт открывают в браузере вне рабочей AI-сессии.

Требование: навигация, цитаты и фильтры должны работать в одном HTML без сервера, CDN, сети и доступа к checkout, с экранированием недоверенного текста и доступными с клавиатуры штатными элементами управления.

Проверка: автономный браузерный просмотр, узкое окно, поиск/фильтры/обратный переход, строка с HTML/JavaScript отображается как текст; без JavaScript все свидетельства доступны через штатные раскрывающиеся блоки и ссылки.

Источник: G1, G5; запрос владельца о переносимом бинарнике. Обоснование: для чтения результата не нужна ещё одна система. Зависимость: SA-014…015.

### 15.1 Правила представления и границы

- Единственный вход — прежний `report CONFIG RUN_ID`; добавляется производная `navigation` в JSON. Manifest, Result, ReviewDecision, snapshot и receipts не меняются. Существующая история остаётся доступной.
- Инвентарь — все файлы **выбранного snapshot**, не весь диск или исключённые конфигом части проекта. Карта одного run показывает все его scope; объединение разных run и полная семантическая индексация всего проекта этим не заявляются. OQ-01 и A6 закрыты отдельным решением владельца, не самим наличием карты.
- Текущий host review задаёт основу фильтров оценок; без него показываются доступные роли без усреднения. Pending учитывается отдельно. Разногласие — различие состояний specification/implementation/assertion между доставленными ролями; это не автоматическое обнаружение противоречий между документами.
- «Вопросы к ТЗ» включает ambiguous и принятые unresolved; содержание проблемы и цитаты читаются в карточке. Для сопоставления конфликтующих норм можно открыть обе карточки. Автоматический поиск всех междокументных конфликтов не входит в этот срез.
- «Нет текущих связей» означает отсутствие сохранённой привязки, пригодной для текущего snapshot. Это может быть технический код, ещё не разобранная функциональность или кандидат на незаданное поведение. Дефект и отсутствие нормы требуют смыслового разбора, а не подсчёта ссылок. Исторические связи отображаются отдельно и не считаются текущими.
- Основная ссылка ведёт на встроенный сохранённый фрагмент с точным path:line и происхождением. Полные исходники не копируются; сервер исходников не нужен. §16 добавляет необязательную ссылку на локальный редактор, не заменяя цитату. Нецитированные методы специально не выдумываются из имени файла. Семантический поиск по всему коду не обещается.
- У исполнения сохраняются собственные статусы/receipt и отдельная история; ни единого «процента соответствия», ни зелёного общего PASS. Snapshot, время генерации, fresh/stale и статус review всегда показаны. Статическая страница не обнаруживает изменения после генерации.

### 15.2 Приёмка среза

До реализации заданы проверки SA-022…026: pending/без tests; общий диапазон нескольких норм; отдельное host-свидетельство; current → retry/outdated → stale; фильтры и прямые ссылки; Unicode/HTML-injection; прежний declared-run и accepted-run. Проверяются Go-регрессии, браузерный просмотр и повторная генерация из копии реального сохранённого run без правки его исходных raw. Результат фиксируется в существующем плане; пользовательская полезность не выдаётся за статистическую точность аудита. Бизнес-репозиторий остаётся read-only.

## 16. Достаточность тестов и настройки HTML

Причина редакции 0.4 — запрос владельца 2026-09-15: слабые проверки трудно заметить, не хватает обзора по ТЗ, переходов в редактор и тёмной темы. Это расширение представления, не повторный смысловой аудит. Старые оценки, журналы и snapshot не изменяются.

### REQ-SA-027 — Видимая неполнота проверок

Условие: HTML показывает оценку assertion.

Требование: отчёт должен явно различать наличие тестового свидетельства, частичную или слабую проверку (weak), достаточность по оценке автора (relevant), противоречащую проверку, отсутствие подходящей проверки и неизвестность, независимо от факта исполнения.

Проверка: supported + weak + passed остаётся частичной проверкой; relevant без receipt не означает запуск; missing/unknown с цитатой не теряют признак наличия свидетельства. Weak виден в закрытой карточке текущего решения и отдельном фильтре.

Источник: G3, G5; запрос владельца. Обоснование: наличие теста не означает проверки всех существенных результатов нормы. Зависимость: SA-007…008, SA-018, SA-021.

### REQ-SA-028 — Сводка по источникам ТЗ

Условие: report строится для любого сохранённого run.

Требование: JSON/HTML должны показывать общую сводку и графические доли по файлам ТЗ, отдельно считая поддержку кодом, требования с противоречием реализации, наличие тестовых свидетельств и достаточность assertions по текущему согласованию хоста; знаменатели, неизвестность и отсутствие текущей оценки должны быть явными.

Проверка: одна норма с несколькими источниками не удваивает общий итог; файл без норм имеет неопределённую долю, а не 100%; pending/outdated/stale не дают текущих положительных числителей; клик по строке файла отбирает его нормы.

Источник: G5; запрос владельца об обзоре как в trace-matrix. Обоснование: доля ссылок на тесты скрывала слабость проверок. Зависимость: SA-022…026.

### REQ-SA-029 — Открытие локального источника

Условие: пользователь выбрал в HTML локальные каталоги и редактор.

Требование: HTML должен строить безопасные ссылки на файл и начальную строку для Zed, PhpStorm, Cursor и VS Code, предварительно заполняя каталоги из конфигурации генерации и сохраняя встроенную цитату как независимый источник истории.

Проверка: разные каталоги кода/ТЗ, перенос проекта, пробелы/Unicode/URL-разделители и неверный путь; смена выбора меняет все ссылки, не записывает CONFIG или исходники и не запускает редактор без клика. Недоступность browser storage не ломает навигацию.

Источник: G1, G5; запрос владельца. Обоснование: для проверки вывода нужен удобный переход в рабочую копию. Зависимость: SA-015, SA-023, SA-026.

### REQ-SA-030 — Системная и выбранная тема

Условие: человек читает HTML в браузере.

Требование: отчёт должен следовать теме системы по умолчанию и позволять выбрать светлую или тёмную тему, сохраняя читаемость свидетельств, графиков и элементов управления без внешних ресурсов.

Проверка: system реагирует на изменение prefers-color-scheme; явная тема его перекрывает; выбор восстанавливается при доступном storage, при недоступном страница продолжает работать; проверены узкое окно и клавиатура.

Источник: G5; запрос владельца. Обоснование: длительное чтение отчёта должно соответствовать рабочей среде пользователя. Зависимость: SA-026.

### 16.1 Подсчёт и границы

- Расширяется только производная `navigation`: сводка, строки файлов ТЗ и defaults локальных ссылок. Исторические manifest/Result/review/receipts не мигрируют. Сводка использует только `fresh` + `current` host review; предварительные роли и история остаются в карточках и прежних фильтрах, но не становятся текущей готовностью.
- Знаменатель — все нормы выбранного run, включая несогласованные и unknown. Норма относится ровно к одному основному `Source.Path` (первая цитата принятого требования); дополнительные источники не увеличивают счёт. В старом snapshot нет дерева заголовков, поэтому «раздел» здесь — файл ТЗ, а не восстановленный заголовок из изменившегося checkout. Выбранные файлы без основных норм остаются видимыми. Объединения run или полноты всего /TZ нет.
- «Код + достаточные тесты» — число норм с clear, supported, relevant и без принятых открытых вопросов. Это статическая оценка хоста, не автоматический PASS, не готовность к релизу и не успешный запуск. Счётчики GAP означают требования с contradicted, не число уникальных дефектов/задач трекера. Test presence — непустой массив Tests; он независим от relevant/weak/missing/unknown. Проценты не являются line/branch coverage или долей проверенных ветвей внутри одной нормы.
- Для кода/тестов исходная база — актуальный CONFIG.project_root. Для ТЗ база — этот корень плюс общий каталог выбранных spec-файлов manifest; его точный относительный префикс показан в UI и снимается один раз. Пользователь меняет локальные базы, не пути snapshot. При нескольких несмежных каталогах общий каталог может быть корнем проекта. Ввод — абсолютные POSIX-каталоги macOS/Linux до 4096 символов; `~`, URL, traversal и управляющие символы отклоняются.
- Редактор выбирается из закрытого списка URI-схем, путь кодируется как данные. Браузер/ОС должны разрешать и иметь зарегистрированный обработчик; установленность и открытие файла HTML проверить не может. Локальный файл и номера строк могли измениться после snapshot. Ссылки не устанавливают плагины и не вызывают shell. «Capilot» требует уточнения названия; произвольная URI-схема не добавляется.
- Тема сохраняется как browser preference; каталоги/редактор — в ключе по исходному корню проекта. Нельзя считать localStorage безопасным хранилищем: значения проверяются перед применением; при отказе сохранения остаётся работающий выбор текущей страницы. Нет server/CDN/телеметрии. Без JS графики, числовые таблицы и цитаты доступны, настройки/фильтры — нет.

Форматы переходов сверены с [VS Code URLs](https://code.visualstudio.com/docs/configure/command-line#_opening-vs-code-with-urls), [обработчиком Zed](https://github.com/zed-industries/zed/blob/main/crates/zed/src/zed/open_listener.rs) и [JetBrains URL navigation](https://youtrack.jetbrains.com/articles/SUPPORT-A-2159/How-to-open-a-source-file-with-line-and-column-specified-from-an-URL). Cursor использует профиль file-навигации семейства VS Code; реальный обработчик каждого редактора требует пользовательской проверки в его среде. Эти ссылки — справочная основа адаптеров, не новые нормы продукта.

### 17.1 Зачем и что уже есть

Цель для менеджера — реже пропускать реализацию и связанные тесты, когда они спрятаны за интерфейсом, общим сервисом или возможностями фреймворка. SDK должен помогать находить конкретные методы и места использования; оценка выполнения бизнес-требования и достаточности assertions остаётся за аудитом. Это ожидаемая польза, которую нужно измерить, а не доказанное улучшение точности.

Сейчас [sdk.php](../tool/sdk.php) через php-parser находит объявления методов и обычные/статические вызовы, возвращая имена, точные диапазоны и цитаты. [Go-граница](../tool/php.go) проверяет контейнер, схему `sdk/2`, исходники, composer.lock и хэш SDK. `php-facts` сохраняет отдельный JSON; он ещё не обогащает автоматически TaskBatch, связи тестов и HTML. PHPStan/Larastan в этом пути не вызываются.

[PublicCallProbeRule.php](../prototypes/core/PublicCallProbeRule.php) исследует тип получателя, возвращаемый тип и доступную цель вызова через публичные API PHPStan. Он выводит факты как диагностические сообщения, оставляет `framework_origin` пустым и не подключён к рабочему CLI. Его наличие не означает готового экспортёра или полной карты вызовов.

Планируемое разделение:

| Компонент | Ответственность |
| --- | --- |
| PHP SDK + php-parser | Адресуемые PHP-символы и точные исходные фрагменты |
| PHPStan | Типы выражений и доступные статически разрешённые цели вызовов |
| Larastan — профиль PHP SDK | Laravel-типы и отражение поддерживаемых механизмов фреймворка; без правил конкретного бизнеса |
| Go-ядро | Проверка происхождения, snapshot, хранение и передача ограниченного набора фактов |
| AI-хост и роли | Подбор контекста, связь требования с кодом/assertions и обоснованный итог; HTML показывает происхождение связей |

Техническая опора: публичные [Scope API](https://phpstan.org/developing-extensions/scope) и [Collectors](https://phpstan.org/developing-extensions/collectors), а не чтение внутреннего кеша PHPStan. У [Larastan](https://github.com/larastan/larastan) есть Laravel-aware анализ; [документация возможностей](https://github.com/larastan/larastan/blob/3.x/docs/features.md) описывает, в частности, Eloquent-типы и отношения. Это основание проектного решения, не гарантия разрешения любого фасада, binding или динамического вызова. Поддерживаемые случаи и версии SDK предстоит закрепить на контрольных примерах.

### REQ-SA-031 — Типизированные связи без выдуманных целей

Условие: пользователь явно выбрал PHP SDK и, для Laravel, профиль с Larastan.

Требование: SDK должен возвращать адресуемые объявления и места вызовов с доступной типовой информацией и происхождением; отличать синтаксис от вывода анализатора. Неразрешённый, неоднозначный, виртуальный или внешний target должен оставаться явно ограниченным свидетельством: декларация интерфейса не объявляется единственной runtime-реализацией, а виртуальному методу не выдумывается файл. PHP-профиль без Laravel не требует Larastan.

Проверка: одноимённые методы разных классов, наследование, интерфейс без известной реализации, динамическое имя, внешний/виртуальный метод; отдельно — заранее выбранные Laravel-примеры Eloquent, facade и container binding с ожидаемыми ограничениями.

Источник: §17.1, G2…G3. Обоснование: поиск по имени теряет типовой контекст; ложная точная ссылка опаснее честной неизвестности. Зависимость: SA-006, SA-009.

### REQ-SA-032 — Факты доходят до аудита и человека

Условие: для snapshot доступны проверенные SDK-факты.

Требование: выбранные факты должны помогать собирать ограниченный контекст кода и кандидатов тестов для Task и отображаться в навигации с явным происхождением. Они не принимают нормы автоматически и не заменяют чтение assertions. Вызов нужного метода в тесте — кандидат связи, не доказательство relevant; отсутствие ребра не доказывает missing. Смысловая связь ТЗ ↔ код/тест возникает из цитат и оценки роли/хоста, а не из PHPStan. Ручные trace-маркеры не требуются.

Проверка: тест с подходящим вызовом, но слабым assertion остаётся weak; одноимённый посторонний метод не подменяет цель; общий helper не теряет значимый контекст. Подсказка SDK и подтверждённая аудитором связь различимы в Task/HTML. Без SDK прежний аудит работает с явным ограничением, без ложного заявления полноты.

Источник: §17.1, G3, G5. Обоснование: отдельный JSON фактов сам по себе не улучшает рабочий цикл. Зависимость: SA-018, SA-021…025, SA-031.

### REQ-SA-033 — Проверяемое происхождение и совместимость

Условие: SDK-факты импортируются или повторно используются.

Требование: версия формата, выбранные файлы/диапазоны, версии SDK/анализаторов и основание анализа должны проверяться Go-ядром. В основание входят composer.lock, используемые конфиги/расширения анализатора и значимые источники типизации, включая объявленные bootstrap/stubs/модели/миграции. Изменение основания не позволяет переиспользовать прежние факты как текущие или сохранять прежнее согласование текущим. Данные вне выбранной области должны иметь явную границу происхождения, не становиться незаметно доступными цитатами. `sdk/2`, прежние run и raw остаются совместимой историей, без ретроспективного обогащения.

Проверка: подмена пути/цитаты/lock/config, смена SDK или контекста типизации, неполный/оборванный экспорт, чужой snapshot и старый syntax-only run; старые выводы не «зеленеют» после обновления фактов. Ошибки PHPStan и факты экспортёра учитываются отдельно: lint-диагностика не становится GAP ТЗ автоматически.

Источник: §17.1, G4. Обоснование: корректный тип зависит не только от текста одного метода. Зависимость: SA-010…012, SA-020, SA-031…032.

### REQ-SA-034 — Явный безопасный запуск адаптера

Условие: требуется запуск PHPStan/Larastan через SDK.

Требование: запуск разрешает хост, только в проверенном Docker runtime выбранного проекта, с фиксируемыми версиями, ограничениями времени/вывода и выделенной рабочей областью. Установка/обновление Composer-зависимостей, изменение проектного CI/config и host-PHP fallback не выполняются автоматически. Отсутствие зависимости, несовместимость или ошибка bootstrap дают явный отказ/неполный результат, не успешный пустой граф. Кеши и временные конфиги не пишутся в бизнес-исходники; изоляция должна исключать обращения к рабочим БД, очередям и внешним сервисам.

Larastan поднимает контейнер приложения, поэтому его запуск нельзя считать простым чтением исходников; это отдельно отмечено в [официальном описании](https://github.com/larastan/larastan). Разрешение syntax-only SDK или тестов не означает автоматического разрешения framework bootstrap. Невозможность обеспечить нужную изоляцию блокирует этот запуск, но не обычный аудит по исходникам.

Проверка: неправильный mount, отсутствующий анализатор, bootstrap с попыткой записи/сетевого доступа, недоступная среда; нет скрытой установки и записи в бизнес-проект. Версии и параметры контейнера задаются проектом, названий и путей пилота в общем SDK нет.

Источник: §17.1, G1. Обоснование: bootstrap способен выполнять проектный код, несмотря на название «статический анализ». Зависимость: SA-009, SA-014…015, SA-033.

### 17.2 Порядок реализации и приёмка

1. Зафиксировать точные JSON/CONFIG/Task-контракты, набор поддерживаемых конструкций, лимиты, совместимость версий и отрицательные ожидания до изменения кода. Не придумывать уже доступные CLI-флаги: текущий `php-facts` остаётся syntax_only до отдельного расширения.
2. Реализовать минимальный экспорт/валидацию на независимом PHP-примере, затем Laravel-профиль на синтетическом приложении. PHP остаётся внутри контейнера, Go — ядром. Наличие Larastan в другом проекте не закрывает эту приёмку.
3. Довести проверенные факты до контекста ролей и навигации; пройти SA-031…034, включая ложных кандидатов тестов, unknown и stale. Одного успешного PHPStan/экспорта недостаточно.
4. После отдельного разрешения сравнить аудит с SDK и без него на одной редакции ограниченного пилотного scope: найденные/пропущенные связи и assertions, ложные findings, время, размер контекста и накладные расходы bootstrap. Эталон не подстраивать под экспорт; отрицательный результат сохранить. Установка SDK не означает доказанного улучшения.

Следующий агент начинает с пункта 1, а не с переноса старого trace или запуска полного бизнес-корпуса. Точный контейнерный профиль и разрешения пилота — в [спецификации применения](smsplace-adoption.md#обкатка-phplaravel-sdk).

## 18. Поставка: версия, обновление и установка skill

Причина редакции 0.7 — решение владельца 2026-09-16: инструмент поставляется как подписанный релиз GitHub с явными командами `version`, `update`, `skill install|update` и скриптом первичной установки `install.sh`. Статус: реализовано и принято 2026-09-16 на релизе `v0.1.0` — нативная квалификация обеих платформ в workflow, установка на хосте владельца, замена ручной копии в пилоте; свидетельства и ограничения (Linux только на runner) — в README «Приёмка и ограничения». Сквозной цикл из чистой AI-сессии через установленный launcher — отдельный этап. Frozen §1–10 и §6 не меняются; `init CONFIG` по-прежнему создаёт только YAML (REQ-SA-001, §12.3) — установка skill остаётся отдельной явной командой, не флагом `init`. Образец дизайна — открытый инструмент Pri-Fly (`install.sh` + manifest с sha256, `update` с проверкой Ed25519); это образец, не норма.

Отношение к REQ-SA-015: `update` пишет только собственный исполняемый файл, `skill install|update` — только каталог `DIR/.spec-audit/skill/` и две относительные host-ссылки. Это отдельные явно вызванные операции владельца, не служебные записи аудита; во время аудита они не выполняются. Встроенные в бинарник документы launcher (`SKILL.md`, протокол роли, зеркало §14, контракты принятого индекса, legacy-извлечения и PHP SDK) — собственные контракты инструмента, не бизнес-нормы проверяемого проекта. Известное решение владельца: контракты принятого индекса и legacy-извлечения содержат навигационные ссылки на README/спецификацию checkout и на документ применения пилота как внешний указатель; файлы заморожены хэшами и при встраивании не редактируются, поэтому в установленной копии эти ссылки вне копии не разрешаются. Линт самодостаточности (нет `](../`, все относительные ссылки существуют, нет абсолютных путей и ID задач) применяется к собственным текстам launcher; к встроенным документам — только отсутствие абсолютных путей и ID задач.

### REQ-SA-035 — Подписанный релиз и явное обновление

Условие: пользователь вызывает `version` или `update` без аргументов.

Требование: `version` возвращает `{"version","release","os","arch"}`, где `release` истинно только в сборке с версией вида `X.Y.Z` и встроенным публичным ключом Ed25519. `update` выполняет проверки строго в порядке: манифест `release-manifest.json` (≤ 1 MiB, лимит `maxConfig`) → подпись `release-manifest.sig` (ровно 64 байта) → проверка Ed25519 над точными байтами манифеста → строгий JSON `{"schema_version":"spec-audit-release/1","version":"X.Y.Z","assets":[{"os","arch","file","sha256"}]}` без лишних/повторных полей → версия строго больше текущей по трём числам, иначе успешный no-op `{"updated":false}` без записи → ассет с точным совпадением `os`/`arch` текущей сборки и именем `spec-audit-<os>-<arch>` → файл ассета (≤ 32 MiB, лимит `maxFile`) → SHA-256 файла равен `sha256` манифеста → атомарная замена собственного исполняемого файла (temp + rename в каталоге бинарника, права 0755, общий `atomicWrite`). Сборка из исходников (`version` = `dev` или без ключа) и исполняемый файл с именем, отличным от `spec-audit`, отказывают до любого обращения к сети. Один общий таймаут HTTP-клиента на запрос, достаточный для скачивания ассета на медленном канале (в редакции 0.7 — 15 минут; 120 с в v0.1.0/v0.1.1 обрывали загрузку); статус ответа вне 2xx — отказ. Сообщения об ошибках и журнал не содержат URL, байтов ответа и содержимого файлов (практика `main.go`: входные данные не попадают в логи через диагностику декодера). Любой отказ на любом шаге оставляет исполняемый файл байт-в-байт прежним.

Ключи: приватный ключ Ed25519 хранится только секретом окружения `release` GitHub Actions и используется единственным публикующим job; публичный ключ встраивается в бинарник при сборке через `-ldflags -X`. Подпись — 64 сырых байта над файлом манифеста, совместимая с `openssl pkeyutl -sign -rawin` (OpenSSL 3) и `crypto/ed25519.Verify`. Бинарник не содержит модельных API и секретов (§12.1).

Проверка: dev-сборка и переименованный бинарник — отказ без сетевого вызова; неверная подпись, повторные/лишние поля манифеста, версия не `X.Y.Z` — отказ до скачивания ассета; равная и меньшая версия — `updated:false`; отсутствие ассета платформы, несовпадение sha256, превышение лимита, HTTP 404 — отказ с неизменённым бинарником; успешный путь — байты заменены, права 0755, следующий `version` показывает новую версию; тексты ошибок без URL и байтов ответа; подпись OpenSSL 3 принимается Go.

Источник: решение владельца 2026-09-16, ROADMAP «Воспроизводимый выпуск macOS/Linux». Обоснование: без подписи и sha256 обновление доверяет любому ответу сети; без явной команды обновление стало бы скрытой служебной записью. Зависимость: SA-014, SA-015, SA-038.

### REQ-SA-036 — Явная непривилегированная первичная установка

Условие: пользователь выполняет `install.sh` из релиза.

Требование: скрипт — POSIX `sh` с `set -eu`, без `sudo`, без правки shell-профилей и системных каталогов; параметры `SPEC_AUDIT_RELEASE_BASE` (по умолчанию GitHub `releases/latest/download`) и `SPEC_AUDIT_INSTALL_DIR` (по умолчанию `$HOME/.local/bin`). Платформа определяется `uname` и должна быть `darwin/arm64` или `linux/amd64`, иначе отказ до обращения к сети. Скрипт скачивает манифест и ассет одного и того же релиза, извлекает `sha256` ассета из манифеста без внешних JSON-инструментов, проверяет его `shasum -a 256` или `sha256sum` (нет ни одного — отказ), затем публикует файл staged-переименованием с правами 0755 и печатает подсказку о PATH и следующем шаге (`spec-audit skill install --dir <проект> --host codex|claude|both`). При любом отказе временные файлы удаляются и бинарник не установлен. Скрипт не подменяет установку сборкой из исходников и не устанавливает языковой runtime.

Граница доверия первой установки — HTTPS до GitHub Releases: подпись манифеста при первой установке не проверяется, это заявлено явно, а не скрыто. Дальнейшие обновления идут только через подписанный `update` (REQ-SA-035).

Проверка: неподдерживаемая платформа — отказ без сети; `sha256` ассета не совпадает с манифестом — отказ, staged-файл удалён, в `SPEC_AUDIT_INSTALL_DIR` ничего нет; успешная установка через `SPEC_AUDIT_RELEASE_BASE=file://…` без сети; `sh -n` и, при наличии, `shellcheck` без замечаний.

Источник: решение владельца 2026-09-16, образец Pri-Fly. Обоснование: одна команда установки без привилегий снимает зависимость пилота от checkout инструмента, не расширяя права скрипта. Зависимость: SA-035, SA-038.

### REQ-SA-037 — Установка skill только по явной команде

## 19. Уроки чистой сессии: проверка ответа роли, провенанс версии, ответ reconcile

Причина редакции 0.8 — прогон из чистой AI-сессии 2026-09-16 (пилот и синтетический проект): хосту пришлось писать собственный валидатор формы ответа роли; версия бинарника, которой выполнялись команды run, нигде не фиксируется; ответ `reconcile` после применения решения не содержит `freshness`; протокол роли предписывал Codex-специфичный инструмент записи. Раздел вводит две нормы и два уточнения расширениями: frozen §1–10 (в том числе список CLI §6, контракт ответа §7 и неизменяемый manifest §9) и контракт [принятого индекса](accepted-index.md) не редактируются. Пункты о reference-only файлах ТЗ вне лимита 64 кандидатов и о разбиении больших accepted-наборов решены владельцем 2026-09-17 в §20.

### REQ-SA-039 — Проверка ответа роли без записи

Условие: хост вызывает `validate CONFIG RUN_ID TASK_ID RESULT_PATH` для существующего run.

Требование: команда выполняет ровно те проверки, что `submit` до первой записи: лимит 4 MiB и строгий UTF-8 JSON (§6, §7), полный набор полей без null и лишних ключей, допустимые значения состояний, полный учёт назначенных ID (REQ-SA-005), привязка цитат к текущему snapshot с чтением источников (REQ-SA-006), канонический размер. Она не создаёт results-файл, не меняет entry/attempt, state, производные отчёты и журналы; дерево run остаётся байт-в-байт прежним. Устаревший snapshot и неизвестный TASK_ID отклоняются так же, как у `submit`; `project_root` обязателен. Успех возвращает `{"valid":true,"task_id","attempt","already_submitted"}` и не гарантирует последующий `submit`: источники, состояние и дубликаты проверяются им заново. Ошибка формы для конкретной оценки называет ID нормы; содержимое цитат и ответа в текст ошибки и журнал не попадает (REQ-SA-015).

Проверка: валидный ответ → `valid:true`; каждая мутация формы отклоняется тем же текстом, что у `submit`; байты `state.json`, `results/` и `report.*` до/после идентичны, новых записей в каталоге run нет; stale-run — отказ; вызов через процесс отдаёт JSON в stdout, отказ — JSON в stderr.

Источник: прогон чистой сессии 2026-09-16 (хост писал валидатор вручную), ROADMAP «Уроки чистой сессии». Обоснование: роли проходили `submit` с первой попытки только благодаря локальной предпроверке; дублировать её вне бинарника — источник расхождений. Зависимость: SA-005, SA-006, SA-012, SA-014, SA-015.

### REQ-SA-040 — Журнал версий бинарника run

Условие: пишущая команда (`prepare`, `submit`, `retry`, `test`, `php-typed`, `review` с DECISION) успешно публикует state или журнал согласования run.

Требование: в каталоге run ведётся append-only файл `tool-versions.json` = `{"version":1,"records":[{"command":"<команда>","tool_version":"<версия бинарника>","recorded_at":"<RFC 3339 UTC>"}]}` до 32 MiB. До публикации state/host-reviews команда читает и проверяет журнал (строгий JSON, полный набор полей), формирует новую запись и проверяет размер — любой отказ на этом шаге оставляет run нетронутым, повреждённый или переросший журнал отклоняет пишущую команду. После успешной публикации записываются только уже проверенные байты; сбой этой записи — предупреждение в журнале диагностики, не отказ (публикация state — точка фиксации, §9). Команды без публикации state (`status`, `report`, `review` без DECISION, `validate`, `tasks`, `php-facts`) записей не добавляют и не предупреждают о смене версии, но проверяют журнал и не скрывают повреждение как отсутствие (как `host-reviews.json`, §14). Старые run без файла читаются без миграции; `snapshot_id`, основание согласования §14, байты `manifest.json` и `state.json` от журнала не зависят. Запись с версией, отличной от предыдущей, допускается с предупреждением: смена версии после `update` легитимна, но провенанс смешанного run должен быть виден. `report` показывает список версий (`tool_versions`); версия `dev` фиксируется как есть и не является уникальной идентичностью сборки.

Проверка: prepare → два submit → review дают четыре записи в порядке команд; отклонённый submit не создаёт и не меняет файл; read-only команды не меняют байты журнала; копия исторического run без файла обслуживается, `report` без `tool_versions`; повреждённый журнал отклоняет submit до записи state и отклоняет `report`; сбой записи после публикации — предупреждение при успешной команде; смена версии — предупреждение и обе версии в отчёте; `snapshot_id`, основание review и байты manifest неизменны.

Источник: инцидент 2026-09-16 — во время run пилота бинарник обновлялся 0.1.0→0.1.3, провенанс восстановить нельзя. Обоснование: поле в manifest меняло бы переносимую идентичность (REQ-SA-003), поле в state — основание §14 и читаемость run старым бинарником; отдельный журнал по образцу §14 ничего из этого не затрагивает. Зависимость: SA-003, SA-012, SA-013, §9, §14.

### 19.1 Ответ reconcile после применения решения

`reconcile CONFIG RAW DECISION` при первом применении возвращает те же поля, что читающий вызов (`base_index`, `source_set`, `records`, `history`, `journal`, `freshness`, `semantic_completeness_proven:false`), плюс `accepted:true` и `duplicate:false`; `freshness` измеряется повторным сканом источников под удерживаемой блокировкой, а не предполагается: если ТЗ изменилось между проверкой и записью, ответ честно показывает `stale`. Точный повтор решения по-прежнему возвращает `duplicate:true` и `freshness_checked:false` без `freshness` — исторический duplicate не подтверждает свежесть. Каждая запись `records[]` дополнительно несёт `revision` и `clarity`, равные `requirement.accepted.revision/clarity`; сама структура `requirement` не меняется, потому что она хэшируется в `snapshot_id` и передаётся ролям. Контракт принятого индекса не редактируется — это дополнение ответа.

### 19.2 Протокол роли и запись ответа

Протокол роли не называет инструмент конкретного хоста: роль записывает только свой OUTPUT_PATH любым инструментом записи файлов, который даёт хост, и может собирать большой ответ в этом файле по частям; итог — один JSON-документ до 4 MiB (§6), формат цитат §7 неизменен. Бинарник видит только итоговый файл. Компактный формат цитат не вводится — это отдельное решение владельца по frozen §7 и REQ-SA-006.

## 20. Справочные источники ТЗ и деление большого набора

Причина редакции 0.9 — прогон пилота 2026-09-16: документ, определяющий смысл терминов раздела, пришлось исключить из scope из-за лимита 64 кандидатов на пакет, и пять норм остались ambiguous с нерешённым «см. документ-источник»; при `scopes: []` одна роль получила 49 норм и 2509 файлов (27–36 минут и 0,5–0,6 M токенов на роль). Решение владельца 2026-09-17: справочные источники вводятся отдельной группой CONFIG, лимиты и frozen-контракты не меняются; деление большого набора остаётся осознанным решением хоста (§6), бинарник лишь предупреждает. §1–10, контракт [принятого индекса](accepted-index.md) и [формат извлечения](legacy-extraction.md) не редактируются.

### REQ-SA-041 — Справочный источник без кандидатов

Условие: CONFIG с `index_mode: accepted` содержит группу `references: {paths, include, exclude}`.

Требование: файлы группы — источники ТЗ (`kind: spec`) с признаком `reference: true` в snapshot, manifest, `TaskBatch.files` и ответе `reconcile` (`source_set[].reference`); они хэшируются, входят в source_set извлечения и в проверку свежести наравне с нормативными файлами (accepted-index п.6, REQ-SA-010) и могут цитироваться кандидатами и ролями по прежним правилам (REQ-SA-006, accepted-index п.8). Они не порождают кандидатов: `reconcile` отклоняет accept/rebind/revise/split/merge, если у target нет ни одной цитаты из нормативного файла; reject/defer/retire не проверяются. Лимиты 64 кандидатов, 64 active-норм и 4 MiB не меняются — справочные файлы их не расходуют. Группа допустима только при `index_mode: accepted`, требует непустой `paths` и подчиняется правилам §6 для групп (существующие пути, glob только имени файла, файл не может попасть в две категории, reports_dir не пересекается с входным деревом). Отсутствие группы сохраняет прежние байты manifest и `snapshot_id`; её наличие и состав входят в идентичность snapshot (REQ-SA-003). Отчёт показывает справочный файл отдельной строкой без норм, не выдавая отсутствие кандидатов за отсутствие обязанностей (REQ-SA-025, REQ-SA-028). Изменение справочного файла или самой группы делает принятый индекс stale до новой полной приёмки; облегчённого rebind без нового raw нет (контракт п.4–6).

Проверка: группа без `index_mode`, с пустым `paths` или с файлом из `specs` — отказ; читающий `reconcile` показывает справочный файл с `reference:true`; кандидат с нормативной и справочной цитатами принимается с обеими цитатами, кандидат только со справочными — отказ с ID кандидата без записи в журнал, тот же кандидат как reject/defer принимается; raw без справочного файла в source_set — прежний отказ; после приёмки `prepare` передаёт обе цитаты и файл с признаком, spec-цитата роли в принятом справочном диапазоне принимается, вне диапазона — отказ; правка справочного файла и добавление группы после приёмки дают `stale`; `report` показывает секцию с `reference:true` и нулём норм и группу `reference`; manifest прежних run без группы байт-в-байт неизменен.

Источник: прогон scope финансов 2026-09-16 (пять ambiguous из-за исключённого документа-источника); решение владельца 2026-09-17. Обоснование: определяющие смысл фрагменты нужны для точной нормы (REQ-SA-016, SA-017), но извлечение из большого справочного документа исчерпывает пакет; расширение лимита или многопакетный срез меняли бы frozen-контракт. Зависимость: SA-002, SA-003, SA-006, SA-010, SA-016, SA-025, SA-028; accepted-index п.6, п.8.

### 20.1 Деление большого набора: предупреждение бинарника и правило launcher

`scopes: []` по-прежнему назначает все нормы одному scope `all`; бинарник не режет нормы по числу токенов и не создаёт scope автоматически (§6: «слишком большой scope требует осознанного деления»). Рекомендуемый размер scope — не более 24 норм (`scopeAdvisoryRequirements`): 18 норм на 50 файлов прошли сравнительный run без затруднений, 49 норм на 2509 файлов заняли 27–36 минут и 0,5–0,6 M токенов на роль; 64 остаётся жёстким пределом. `index` возвращает `advisories` — список строк по каждому scope с числом норм выше рекомендации (ключ отсутствует, когда список пуст); `index` и `prepare` дублируют каждую строку предупреждением в журнале диагностики; stdout `prepare` (TaskBatch) не меняется. Порог — эвристика по двум замерам, не измеренная граница качества.

Правило launcher: если `index` вернул `advisories` или active-набор больше 24 норм, хост до `prepare` задаёт `scopes` в scope-конфиге — группирует active ID по подразделам ТЗ в порядке первой принятой цитаты, по 16–24 нормы, `focus` называет подразделы, каждый active ID назначен ровно один раз (пропуск и повтор отклоняются, §6); после решения, добавляющего или снимающего ID, `scopes` обновляются. Список файлов роли не сужается по scope: скрытый файл даёт `unknown`, а не свидетельство. Роли разных scope выполняются параллельно в пределах доступных слотов; согласование хоста остаётся одним DECISION на run (§14). Проверка: 25 норм при `scopes: []` — одна строка `advisories`; 24 — ключа нет; явные scope 13+12 — нет; 65 при `scopes: []` — прежний отказ; корпус из пяти норм не пишет предупреждений.

## 21. Уроки второго прогона: проверка приёмки без записи, подсказки сопоставления, изоляция ролей

Причина редакции 1.0 — второй чистый прогон 2026-09-17 (scope со справочным источником и тремя scope): хост снова писал зеркало проверок raw и вычислял content hash, чтобы выбрать rebind или revise до записи; после смены source_set свежее извлечение переформулировало все кандидаты, сопоставление с прежними ID делалось вручную по пересечению цитат, rebind оказался недостижим (0 из 49) и revision выросла у всего набора без смены смысла; две параллельные роли делили общий рабочий каталог, и одна выполнила одноимённый скрипт другой. Решение владельца 2026-09-17: команда `check` по образцу `validate` (§19), подсказки сопоставления как часть её ответа, изоляция роли в собственном каталоге. §1–10 (в том числе список CLI §6), §14, контракт [принятого индекса](accepted-index.md) и [формат извлечения](legacy-extraction.md) не редактируются; облегчённая форма host DECISION (§14) отложена до следующего прогона.

### REQ-SA-042 — Проверка приёмки без записи

Условие: хост вызывает `check CONFIG RAW` или `check CONFIG RAW DECISION` при `index_mode: accepted`.

Требование: команда выполняет ровно те проверки, что применяющий `reconcile` до записи, и в том же порядке: чтение журнала (повреждённый или переросший журнал — отказ, как у apply), скан источников и чтение выбранных файлов, схема raw и лимиты, полнота и хэши source_set, точные цитаты, признак нормативной цитаты (REQ-SA-041); с DECISION дополнительно — строгий разбор решения (до чтения журнала, как у apply), точный повтор decision_id (ответ `duplicate:true` без чтения источников — исторический duplicate не подтверждает свежесть), повтор decision_id с другими байтами (отказ), лимит 128 пакетов, guard нормативной цитаты, полный прогон операций по контракту принятого индекса (base_index, raw_sha256, учёт всех кандидатов и прежних active ID, rebind/revise по content hash, выдача ID) и размер будущего журнала. Ответ без DECISION: `{"valid":true,"base_index","freshness","source_set":[{path,sha256,reference}],"candidates":[{"id","clarity","normative","matches":[…]}]}`; с DECISION дополнительно `"duplicate"`, `"next_head"`, `"assignments":[{"candidate","requirement_id","action","revision","previous":[…]}]` и `"retired":[…]` — ровно те ID и редакции, которые получил бы apply тех же байтов при неизменных источниках и журнале. Команда ничего не создаёт и не меняет: ни каталог reports_dir, ни lock, ни журнал; блокировка не берётся. Успех не гарантирует последующий apply: источники, журнал и base_index проверяются им заново под блокировкой. Тексты ошибок — те же, что у apply (первая ошибка); содержимое цитат в ошибку и журнал диагностики не попадает (REQ-SA-015).

Проверка: declared-профиль — отказ; без reports_dir — `valid:true`, `freshness:"uninitialized"`, каталог не появляется; каждая мутация raw и решения даёт тот же текст, что apply; повреждённый журнал — отказ; accept/rebind/revise/split/merge/retire/reject/defer дают предсказанные ID и редакции, последующий apply тех же файлов даёт `base_index`, равный предсказанному `next_head`, и те же assignments; точный повтор — `duplicate:true` без `freshness`; байты журнала и список файлов reports_dir до/после неизменны; вызов через процесс — один JSON в stdout, отказ — JSON в stderr.

Источник: отчёт второго чистого прогона 2026-09-17 (≈20 минут на приёмку, зеркало проверок и хэша на хосте). Обоснование: как и для ответов ролей (REQ-SA-039), проверка вне бинарника — источник расхождений; операции контракта уже реализованы чистой функцией, и предпросмотр не требует второй реализации. Зависимость: SA-012, SA-014, SA-015, SA-039, SA-041; accepted-index п.1, п.3–4, п.6–7.

### 21.1 Подсказки сопоставления

Только `check CONFIG RAW` дополняет каждого кандидата списком `matches` — до трёх active-записей принятого индекса, ранжированных по пересечению точных строк цитат: `overlap` — коэффициент Жаккара множеств строк (`quote`, разбитая по переводам строк, без нормализации) кандидата и `accepted.citations` записи, `shared_lines` — число общих строк, `revision` записи и `fields_equal` — равны ли condition, statement, exceptions, clarity и unresolved кандидата полям записи (тогда rebind с прежними title и verification даст тот же content hash). Порог включения `overlap ≥ 0,1`. Основание: замер на реальном переходе пилота между двумя приёмками (49 кандидатов с прежним ID, истина — `previous` в решении хоста) — ранжирование по Жаккару даёт верную первую подсказку в 48 случаях из 49, при пороге 0,1 истина попадает в три подсказки в 49 из 49, при пороге 0,5 — только в 28 из 49, потому что добавленные цитаты справочника размывают пересечение; метрика покрытия прежней записи ранжирует хуже (39 из 49). Пути и номера строк не участвуют, поэтому подсказки устойчивы к сдвигу текста; retired-записи не учитываются. Подсказка — не смысловая эквивалентность и не решение: бинарник по-прежнему не вычисляет эквивалентность (контракт п.3), а DECISION хоста остаётся полным и явным. Читающий `reconcile` не меняется: у него нет raw.

### 21.2 Изоляция роли и размер scope

Launcher выдаёт каждой роли собственный каталог `reports_dir/dispatch/<task_id>/` для OUTPUT_PATH и любых вспомогательных файлов и скриптов; параллельные роли не делят рабочий каталог и имена файлов. Протокол роли запрещает читать и выполнять файлы других ролей и создавать вспомогательные файлы вне каталога своего OUTPUT_PATH; это контекстное разделение, не ОС-песочница (§9). Рекомендация размера scope уточняется: около 16–24 норм, при этом подраздел ТЗ не разрезается ради нижней границы — граница подраздела важнее нижнего предела. Перед `reconcile CONFIG RAW DECISION` launcher выполняет `check CONFIG RAW` и `check CONFIG RAW DECISION`.

## 22. Уроки третьего прогона: перепривязка с сохранением содержания, подсказки, диагностика scopes

Причина редакции 1.1 — третий чистый прогон 2026-09-17 (переприёмка после правки ТЗ): свежее извлечение переформулировало все кандидаты, rebind не был доступен ни разу (0 из 50), после двух переизвлечений 33 нормы получили revision 3 без смены смысла, а ambiguous выросло с 8 до 12 из-за перефразированных unresolved; подсказки `check` дали 4 ложных первых места из 50 на строках, общих для многих кандидатов; `index` после приёмки отказал без имени scope и ID; dry-run `check` показал `freshness:"stale"` у пакета, который эту устарелость закрывает. Решение владельца 2026-09-17: новое действие `reanchor`, поле `unique_shared` и лимит четырёх подсказок, диагностика `scopes`, признак `base_index_current`. §1–10, §14, контракт [принятого индекса](accepted-index.md) не редактируются: `reanchor` реализует уже разрешённый п.3 путь «сохранение прежней принятой формулировки». Облегчённая форма host DECISION остаётся отдельным решением.

### REQ-SA-043 — Перепривязка с сохранением принятого содержания

Условие: DECISION содержит операцию `reanchor` с одним прежним active ID в `previous` и одним кандидатом в `targets`.

Требование: принятое содержание нормы — title, condition, statement, verification, exceptions, clarity, unresolved — вместе с ID, revision, content hash и parents сохраняется из прежней записи; цитаты и source берутся из кандидата. `title` и `verification` в target обязаны быть пустыми строками: хост ничего не переформулирует, а лишь утверждает, что кандидат — та же норма в новой редакции текста; за эту эквивалентность отвечает хост, бинарник её не вычисляет (контракт п.3). Кандидат учитывается ровно один раз, прежний ID получает ровно одно продолжение (п.1), guard нормативной цитаты действует (REQ-SA-041), формулировка кандидата остаётся в raw и в истории пакета. Операция не изменяет content hash и revision, поэтому счётчик редакций движется только при смысловой правке (`revise`); изменение clarity или unresolved требует `revise`. Прежние run после `reanchor` становятся историей, как после любой смены цитат (REQ-SA-010).

Проверка: после `reanchor` запись хранит прежние title/statement/verification/clarity/unresolved, content hash и revision, но новые citations и source; журнал воспроизводится детерминированно; непустой title или verification — отказ; previous не active или повторный — прежние отказы; кандидат только со справочными цитатами — отказ guard; `check CONFIG RAW DECISION` предсказывает `assignments[].action == "reanchor"` с прежней revision; после `prepare` роли получают новые цитаты, spec-цитата в старом диапазоне отклоняется.

Источник: отчёт третьего прогона 2026-09-17 (0 rebind из 50, 33 нормы на rev 3, ambiguous 8→12). Обоснование: п.3 контракта допускает сохранение прежней принятой формулировки, но без отдельной операции это возможно лишь при побайтовом совпадении текста из raw, чего свежий извлекатель не даёт; правка raw запрещена (п.1). Зависимость: SA-016, SA-041, SA-042; accepted-index п.1, п.3–4, п.8.

### 22.1 Подсказки сопоставления: `unique_shared` и четыре подсказки

Ранжирование подсказок по коэффициенту Жаккара строк цитат и порог 0,1 (§21.1) сохраняются: на двух переходах пилота (49 и 50 кандидатов с прежним ID) взвешивание строк по частоте или исключение общих строк ухудшило первый переход (верный top-1 48→43 из 49). Лимит подсказок — четыре (истина в четырёх подсказках: 49 из 49 и 50 из 50; в трёх — 49 и 49). Каждая подсказка дополняется `unique_shared` — числом общих строк цитат, которых нет ни у одной другой active-записи: у верных первых подсказок оно больше нуля в 85 случаях из 88, у ложных — ноль во всех трёх; `unique_shared: 0` означает, что подсказка держится на строках, общих с другими нормами (заголовки таблиц, вводные), и требует проверки перед `reanchor`. Подсказка по-прежнему не эквивалентность и не решение.

### 22.2 Диагностика `scopes`

Когда `scopes` в CONFIG расходятся с текущим набором норм (после приёмки, изменившей ID), `index`, `prepare` и любая команда, строящая snapshot, называют scope и ID: «scope <id>: неизвестные ID [...]; повторно назначенные [...]» для первого scope с расхождением и «не распределены по scope: [...]» для норм без владельца; списки отсортированы, не длиннее 64 элементов. Правила §6 не меняются: пустой `scopes` назначает все нормы одному scope `all`, лимиты прежние.

### 22.3 `check CONFIG RAW DECISION`: признак актуальности base_index

Успешный ответ dry-run с DECISION содержит `"base_index_current": true`: base_index решения равен текущему head, а операции применимы. Поле `freshness` в обоих режимах `check` описывает текущий принятый индекс до применения пакета (после apply source_set пакета совпадает с текущими источниками по построению); при `duplicate` и в режиме без DECISION признака нет.

## 14. Контракт согласования аудита

Для новых submit бинарник сохраняет первые принятые байты роли в прежнем results-файле и необязательный raw_sha256 в Entry. Семантически равная повторная отправка остаётся duplicate, но не заменяет первые байты; оставшийся после прерванной публикации results-файл используется только при равном Result. Read проверяет hash и соответствие state. Старые Entry без hash остаются legacy_canonical: их исходное форматирование неизвестно и не восстанавливается. Согласование старого run допустимо с явной отметкой этого ограничения; нельзя объявлять его exact raw. Retry снимает hash текущей попытки, сохраняя прежний файл. Новый бинарник читает старые run; чтение расширенного state старым бинарником не обещается.

Новая команда `review CONFIG RUN_ID [DECISION]` не заменяет `reconcile`: reconcile принимает требования, review принимает итог аудита. Без DECISION возвращается контекст согласования: run_id, snapshot_id, basis_sha256, delivery_complete, freshness, требования, entries, executions и история решений. Этот режим доступен и для stale-истории; запись требует fresh и полной доставки. Сам вызов CLI не доказывает личность автора: reviewer — подпись оператора, не криптографическая идентификация.

DECISION — строгий UTF-8 JSON до 4 MiB со всеми полями: `version:1, review_id, run_id, snapshot_id, basis_sha256, reviewer, summary, assessments, limitations`. review_id — slug; reviewer и summary непусты. assessments содержит ровно одну обычную Assessment §7 на каждую норму, с теми же правилами цитат/неоднозначности. statement объясняет выбор хоста с учётом разногласий. Если по норме одновременно есть relevant-тесты штатного пути и contradicts-тест достижимой ветки, assertion нормы — contradicts: зелёный тест, закрепляющий противоречащее норме поведение, важнее подтверждающих тестов; weak и missing contradicts не отменяют (§29). Нельзя добавлять execution status или новые нормы. Если нужен ранее отсутствовавший нормативный контекст — новый принятый индекс и run, а не цитата вне snapshot.

Основание: SHA-256 от Go `json.Marshal` объекта `{snapshot_id, state, review_head}` в указанном порядке. state — текущий State с entries/executions без производных отчётов; review_head — SHA-256 точных байтов последнего принятого DECISION либо пустая строка. Оно меняется также после нового решения хоста, чтобы параллельные решения не теряли друг друга. Это compare-and-swap, не доказательство правильности оценки.

Под общим lock run хранится `host-reviews.json`: `{version:1, records:[<точная UTF-8 строка DECISION>,...]}`, до 64 решений и 32 MiB целиком. Массив append-only; один и тот же review_id с теми же байтами — duplicate без записи, с другими — конфликт. Исторический duplicate не делает решение current. Проверки размеров/схем/цитат, CAS и повторная сверка snapshot происходят до атомарной публикации. Производные отчёты инвалидируются до изменения журнала; отказ не меняет журнал или роли.

Актуальность последнего решения проверяется относительно state/snapshot и review_head его предшественника. Состояния: missing / current / outdated. Read/report валидируют журнал и не скрывают повреждение как отсутствие решения. Старый run без журнала остаётся доступен без миграции. JSON/HTML сохраняют историю и исходные роли; `host_reconciliation_required` становится false только при current, но `semantic_completeness_proven` остаётся false. Отсутствие автоматического PASS сохраняется; это явное суждение хоста, а не сертификат бинарника.

## 23. Облегчённая форма host DECISION (version 2) и список ролей

Причина редакции 1.2 — третий чистый прогон 2026-09-17: host DECISION по §14 повторял цитаты обеих ролей (823 KB), хост тратил около четверти часа на чтение 102 оценок и сборку файла, а арифметическая ошибка в summary потребовала второй записи в append-only журнал. Решение владельца 2026-09-17: вторая, облегчённая форма решения — вердикт хоста со ссылкой на принятое свидетельство роли и машиносверяемые счётчики; полная форма §14 (`version: 1`) остаётся действительной и нужна, когда хост цитирует то, чего роли не приводили. §7, §14, основание CAS, журнал `host-reviews.json`, лимиты и состояния не меняются; журнал может содержать решения обеих форм.

### REQ-SA-044 — Вердикт хоста по свидетельствам роли

Условие: хост подаёт DECISION с `version: 2`.

Требование: документ — строгий UTF-8 JSON до 4 MiB со всеми полями: `version:2, review_id, run_id, snapshot_id, basis_sha256, reviewer, summary, verdicts, counts, limitations`; идентичность, review_id, reviewer, summary, основание, CAS, полнота доставки, дубликаты и конфликты review_id, лимиты журнала — по §14. `verdicts` содержит ровно одну запись на каждую норму run: `requirement_id, specification, implementation, assertion, concur, statement, limitations` с теми же допустимыми состояниями и правилом принятой неоднозначности, что у Assessment §7, но без цитат. `statement` может быть пустым только когда `concur: both` и вердикт совпадает с оценками обеих ролей по specification/implementation/assertion — тогда отчёт показывает стандартный текст «Совпадает с оценками обеих ролей.»; при любом расхождении или ином `concur` statement обязателен (§28.3). `concur` — `mapper`, `redteam` или `both`: свидетельствами хоста по норме считаются цитаты (spec, code, tests) названных ролей из текущих результатов run, при `both` — объединение без повторов; собственных цитат форма не содержит — для них используется `version: 3` (§25) или полная форма `version: 1`. `counts` — `supported, contradicted, implementation_unknown, relevant, weak, contradicts, missing, assertion_unknown, ambiguous`; бинарник пересчитывает их по verdicts и отклоняет решение при первом расхождении, называя поле и оба числа. Запись возможна только при полной доставке, поэтому у названных ролей всегда есть результат; журнал хранит точные байты. Отчёт и `review` показывают решение version 2 в общей форме: вердикт хоста рядом с принятыми цитатами и пометкой, чьи это свидетельства; для outdated-решения принятые цитаты берутся из текущих результатов ролей и не выдаются за цитаты момента решения — состояние outdated уже названо (REQ-SA-020), а основание §14 привязывает решение к состоянию момента записи.

Проверка: version 2 с `concur: both` принимается, состояние current, журнал содержит точные байты; `concur: mapper` даёт в отчёте только цитаты mapper; расхождение любого счётчика — отказ с именем поля; недопустимый `concur`, пропущенная или повторная норма, пустой statement при расхождении с оценкой роли или при `concur` ≠ both, принятая ambiguous-норма с `specification: clear`, `version: 3`, stale-основание, незавершённая доставка, повтор review_id с другими байтами — отказы без записи; журнал с решениями version 1 и 2 читается целиком; после `retry` роли решение становится outdated; отчёт подписывает решение хоста «свидетельства mapper / свидетельства redteam / свидетельства обеих ролей».

Источник: отчёт третьего прогона 2026-09-17. Обоснование: узкое место согласования — не запись, а чтение оценок и копирование чужих цитат; счётчики, проверенные бинарником, ловят ошибку хоста до записи в append-only журнал. Зависимость: SA-019, SA-020, SA-021, §7, §14.

### 23.1 Список ролей в ответе `review`

`review CONFIG RUN_ID` без DECISION дополняет контекст полем `roles[]` — по одной записи на задание: `task_id, role, scope, attempt, submitted` и `raw_sha256` при наличии результата; порядок — порядок entries. Поле `entries` не меняется. Ответ также содержит `form` последнего решения (`assessments` для version 1, `verdicts` для version 2) и `concur` — соответствие requirement_id → concur для version 2.

## 25. Уроки пятого прогона: цитаты хоста в решении (version 3), limitations и прошлый вердикт в `outcomes[]`

Причина редакции 1.5 — пятый чистый прогон 2026-09-17 на том же snapshot, что четвёртый: по одной норме обе роли дали supported/relevant, а вердикт хоста contradicted держался на строках, которых ни одна роль не цитирует; version 2 без собственных цитат этого выразить не может, и хост вернулся к полной форме version 1 на 726 KB ради трёх цитат. Ключевой сигнал по той же норме лежал в limitations роли при supported, а итог по всем нормам совпал с прошлым прогоном только потому, что хост помнил прошлое решение. Решение владельца 2026-09-18: форма version 3 с собственными цитатами хоста внутри вердикта; таблица `outcomes[]` показывает limitations ролей и прошлый вердикт хоста. §7, §14, §23, основание CAS, журнал и состояния не меняются; журнал может содержать решения трёх форм.

### REQ-SA-046 — Решение version 3: цитаты хоста в вердикте

Условие: хост подаёт DECISION с `version: 3`.

Требование: форма и правила — как у version 2 (§23), но каждая запись `verdicts` дополнительно содержит обязательные `spec`, `code` и `tests` — собственные цитаты хоста по правилам Assessment §7: группы `spec`/`code`/`tests` по виду файла snapshot, не более 128 цитат в группе, точные строки и quote, цитата `spec` внутри блока назначенной нормы, `test_id` у тестовой цитаты; пустые массивы допустимы и означают, что хост опирается только на свидетельства ролей. Свидетельствами хоста по норме считаются цитаты названных в `concur` ролей из текущих результатов run, объединённые с собственными без повторов; полнота §7 (spec обязательна; supported/contradicted требуют code; relevant/weak/contradicts требуют тестовый источник) проверяется на объединении при записи. При записи цитаты хоста сверяются с snapshot (sha и полные строки), как у роли; при чтении журнала проверяется форма. `concur` по-прежнему `mapper`, `redteam` или `both`: собственные цитаты дополняют свидетельства ролей, вердикт без свидетельств ролей не вводится. Отчёт и `review` показывают решение в общей форме и помечают нормы, где есть собственные цитаты хоста («… и хоста»). Version 1 и 2 остаются действительными; `draft` печатает version 3 с пустыми цитатами.

Проверка: version 3 с пустыми цитатами принимается и равна version 2 по свидетельствам; собственные `code`/`tests` по одной норме дают в отчёте объединение цитат ролей и хоста без повторов и подпись «… и хоста»; цитата с неверной quote, вне snapshot, вне группы или сверх лимита — отказ с именем нормы без записи; `null` вместо массива — отказ; журнал с решениями трёх форм читается целиком; после `retry` роли решение становится outdated.

Источник: отчёт пятого прогона 2026-09-17. Обоснование: три цитаты хоста по одной норме не должны стоить полной формы; правила цитат едины для ролей и хоста. Зависимость: SA-044, SA-045, §7, §14.

### 25.1 Limitations ролей в `outcomes[]`

Запись `roles.<role>` таблицы `outcomes[]` (§24.1) дополняется полем `limitations` — массивом limitations этой роли по норме из её текущего результата (пустой массив при отсутствии). Statement и цитаты по-прежнему остаются в `entries`.

### 25.2 Прошлый вердикт хоста

Запись `outcomes[]` получает необязательное поле `previous_host` — `{run_id, review_id, specification, implementation, assertion}`: состояния из последней записи журнала другого run того же `reports_dir`, чей `manifest.json` имеет тот же `snapshot_id` и тот же accepted head (оба без accepted — совпадение); последняя запись журнала была current на момент записи по §14. При нескольких кандидатах берётся run с самой поздней записью `review` в `tool-versions.json`, при равенстве или отсутствии — лексически больший run_id. Каталоги читаются только на чтение; повреждённые или неполные пропускаются. Поле — подсказка для чтения: бинарник не переносит прошлый вердикт в новый run, не включает его в основание §14 и в черновик `draft` (RULES: stale-свидетельства не становятся текущими автоматически).

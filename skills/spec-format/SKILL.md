# Правка ТЗ по единому формату

Навык задаёт форму записи требований, которую читают и проверяют ИИ-агенты и аудит. Смысл требований решает владелец ТЗ; агент не додумывает недостающее.

## Главное правило

Обязанность существует только в блоке нормы `REQ`. Текст вне блоков — пояснение: ничего не требует и не проверяется. Если в пояснении видна обязанность без блока — это дефект ТЗ.

## Чтение ТЗ

Не читай ТЗ целиком. Ищи нужное по ID (`rg -n "REQ-ORD-014"`), по номеру раздела (`§3.2`) или по термину и читай только найденный раздел и определения, на которые он ссылается.

## Блоки

Блок — заголовок третьего уровня `### <ID> — <Название>`. Сразу за ним поля, каждое на своей строке, в одном абзаце, без переноса строки внутри поля. Пустая строка отделяет тело блока: таблицы, списки, схемы, примеры. Блок заканчивается следующим заголовком уровня 1–3.

### Норма `REQ`

```markdown
### REQ-ORD-014 — Резерв товара при оформлении заказа

Условие: Когда покупатель подтверждает заказ, …
Требование: система должна зарезервировать каждую позицию заказа на складе до перехода заказа в оплату.
Проверка: тест — после подтверждения заказа остаток каждой позиции уменьшен на её количество.
```

- **Условие** — когда норма действует, по шаблону EARS (ниже).
- **Требование** — один наблюдаемый результат: «система должна …» / «система не должна …». Одна обязанность на блок; «и» между разными результатами — раздели блок. Исключения и границы — в этой же строке.
- **Проверка** — метод (тест, инспекция, анализ, демонстрация) и наблюдаемый критерий. Проверка не добавляет условий и механизмов, которых нет в Требовании.
- **Тело** — то, на что ссылается Требование: таблица полей, перечень значений, схема сообщения. Одна норма с таблицей вместо нормы на каждое поле. Пример — в блоке кода с подписью «Пример (не норма)»; для поведения — сценарий «Дано / Когда / Тогда».

Шаблоны EARS (ключевое слово — первое слово Условия):

| Шаблон | Условие |
|---|---|
| Всегда | `Всегда.` |
| Событие | `Когда <событие>, …` |
| Состояние | `Пока <состояние>, …` |
| Нежелательное | `Если <сбой или нежелательное событие>, то …` |
| Опция | `При наличии <функции>, …` |
| Составной | `Пока …, когда …` или `При наличии …, когда …` |

Одно событие в «Когда»; «Если … то» — только для отказов и ошибок; «Пока» — длящееся состояние; несколько событий через «или» — несколько норм или один термин `DEF`. Слова силы: «должна» — обязанность, «не должна» — запрет, «может» — разрешение. «Обычно», «как правило», «желательно», «например» в Требовании запрещены.

### Вопрос `Q`

```markdown
### Q-ORD-003 — Резервировать ли позиции предзаказа

Вопрос: резервирует ли система позиции со статусом «предзаказ», которых нет на складе?
Нормы: REQ-ORD-014
```

Вопрос — то, что текст оставляет открытым. Неясное записывается вопросом, а не догадкой в норме. Когда владелец отвечает, ответ вносится в норму, а блок вопроса удаляется. Вопросы ставятся в конце раздела, к которому относятся.

### Определение `DEF`

```markdown
### DEF-ORD-002 — Активный заказ

Определение: заказ, подтверждённый покупателем и ещё не доставленный и не отменённый.
```

Определение вводит термин и ничего не требует. Правило — это норма, а не определение.

## ID

Формат `<ВИД>-<ПРОСТРАНСТВО>-<НОМЕР>`: вид `REQ`/`Q`/`DEF`, пространство — заглавные латинские буквы или цифры, одно на файл, номер — не менее трёх цифр.

- Пространство берётся из строки `Пространство ID: ORD.` под заголовком первого уровня файла. Если строки нет, не придумывай пространство молча: предложи владельцу короткое, не занятое другими файлами ТЗ (`rg -n "Пространство ID:"`), после согласия добавь строку.
- Новый номер = наибольший номер этого вида и пространства по всем файлам ТЗ, включая разделы `## Снятые ID`, плюс один (`rg -o "REQ-ORD-[0-9]+"`).
- ID не меняется при перемещении блока и никогда не используется повторно.

## Изменения

- **Новая обязанность** — новый блок с новым номером.
- **Изменение смысла** — правка полей существующего блока; ID сохраняется.
- **Отмена** — удаление блока и запись в раздел `## Снятые ID` в конце файла: `- REQ-ORD-014 — 2026-10-01`.
- **Ответ на вопрос** — правка или новая норма, затем удаление блока `Q`.
- Ссылки — только по ID (`REQ-ORD-014`, `DEF-ORD-002`) и номеру раздела (`§3.2`), не по строкам файла. Маркеры в коде и тестах — по правилам проекта; если своих нет — `@tz REQ-ORD-014`.

## Правка старого требования

Если меняется требование, записанное ещё не блоком (абзац, пункт списка, строка таблицы), перепиши в блоки **только это требование**; соседние требования не трогай, даже если они в старой форме.

1. Найди минимальный фрагмент (предложение, пункт, строку), в котором живёт изменяемая обязанность. Если в том же фрагменте есть другие обязанности, они тоже становятся блоками — иначе потеряются; за пределы фрагмента не выходи.
2. Сначала перенеси смысл без изменений: каждая обязанность фрагмента — отдельный блок `REQ`; условия, исключения и границы переходят в поля; неясное становится блоком `Q`, а не догадкой.
3. Затем внеси правку, которую просил пользователь.
4. Поставь блоки на место фрагмента, в том же разделе; старый текст фрагмента удали — обязанность должна быть записана в одном месте. Пояснение, которое ничего не требует, можно оставить абзацем перед блоками.
5. Номера разделов (`§3.2`) не меняются. Если у фрагмента был свой якорь (`A-051`, номер пункта), найди ссылки на него (`rg -n "A-051"`); если он где-то упоминается, сохрани его в теле блока строкой `Прежний якорь: A-051.` после пустой строки.
6. В ответе пользователю раздели: что перенесено без изменения смысла, что изменено по его просьбе, какие вопросы `Q` открыты, какие ID выданы или сняты.

## Структура файла

```markdown
# Заказы

Пространство ID: ORD. Назначение раздела — одна-две фразы.

## §3.2 Резервирование

Пояснение: зачем резерв и где участвует (не норма).

### REQ-ORD-015 — Снятие резерва при отмене заказа

Условие: Когда заказ отменяется до отгрузки, …
Требование: система должна вернуть зарезервированные позиции заказа в свободный остаток склада.
Проверка: тест — после отмены заказа свободный остаток каждой позиции вырос на её количество.

## Снятые ID

- REQ-ORD-009 — 2026-10-01
```

Заголовки второго уровня сохраняют номер раздела. Файл — одна предметная область; делят файлы по смыслу, не по размеру. Документы проектирования реализации норм не вводят, а ссылаются на ID.

## Самопроверка перед завершением

- Каждое поле блока — одна строка; поля идут одним абзацем сразу после заголовка; тело отделено пустой строкой.
- В каждой норме есть Условие, Требование и Проверка; Условие начинается с ключевого слова EARS; Требование — одна обязанность со словом силы.
- Проверка не шире Требования; в Требовании нет «обычно», «желательно», «например».
- Новые ID уникальны и не встречаются среди снятых; удалённые ID записаны в `## Снятые ID`.
- Никакая обязанность не осталась в пояснении и не записана дважды.
- Если у проекта есть свои обязательные шаги после правки ТЗ (переиндексация, гейты трассировки, правила в `AGENTS.md`), выполни их: навык задаёт форму записи и их не заменяет.
- Если в проекте настроен spec-audit с профилем `declared`, запусти `spec-audit index CONFIG`: он отклоняет блок неправильной формы.
